# 260708-04 Monitoring UI PowerShell start script does not capture backend process output

## Problem Statement

The PowerShell start script for the Monitoring UI writes a startup marker to
`logs/monitoring-ui-backend.log`, but the backend process itself is launched without redirecting
stdout or stderr into that file.

This makes the log path misleading: operators are told to tail
`logs/monitoring-ui-backend.log`, and the file says the backend is starting, but runtime logs,
tracebacks, and startup failures from the backend process may go to the child PowerShell window
instead of the documented log file.

The Bash start script already captures backend output into the same log file, so the PowerShell
and Bash startup behavior diverge.

## Verified Evidence

- `scripts/deployment/monitoring-ui/start.ps1:45` writes
  `starting backend on $apiBaseUrl` to `logs/monitoring-ui-backend.log`.
- `scripts/deployment/monitoring-ui/start.ps1:49` builds `$backendCommand` as a plain invocation
  of the backend module and does not pipe `2>&1` to `Out-File`.
- `scripts/deployment/monitoring-ui/start.ps1:52-56` launches the backend via `Start-Process`
  without `-RedirectStandardOutput` or `-RedirectStandardError`.
- `scripts/deployment/monitoring-ui/start.ps1:75` prints
  `Tail backend log: Get-Content '$backendLog' -Wait`, implying backend process output will be
  visible there.
- `scripts/deployment/monitoring-ui/start.sh:23` launches the backend with
  `>>"$BACKEND_LOG" 2>&1`, so Bash captures the backend process output as expected.
- `README.md:51-60` documents the PowerShell Monitoring UI start script and names
  `logs/monitoring-ui-backend.log` as the backend log path.

## Expected Behavior

Starting the Monitoring UI with `scripts/deployment/monitoring-ui/start.ps1` should append the
backend process stdout and stderr to `logs/monitoring-ui-backend.log`, matching the operator
contract and Bash script behavior.

The log file should contain:

- the existing `starting backend on ...` marker;
- backend runtime logs emitted after the process starts;
- startup failures and tracebacks from the backend process;
- no unnecessary duplicate startup markers or noisy wrapper output.

Frontend logging behavior should remain unchanged.

## Acceptance Criteria

- The PowerShell backend launch path appends both stdout and stderr from the backend process to
  `logs/monitoring-ui-backend.log`.
- A backend startup failure is visible in `logs/monitoring-ui-backend.log` when started through
  `scripts/deployment/monitoring-ui/start.ps1`.
- Successful backend runtime logs continue appending to the same file across restarts.
- The script still writes `logs/monitoring-ui-backend.pid` for the process that stop.ps1 can
  terminate.
- Bash script behavior is unchanged.
- README logging claims remain true for both PowerShell and Bash startup paths.

## Test Plan

- Static/unit-style check: verify the PowerShell backend command or `Start-Process` call redirects
  stdout and stderr to `logs/monitoring-ui-backend.log`.
- Manual smoke test on Windows:
  - run `scripts/deployment/monitoring-ui/start.ps1`;
  - tail `logs/monitoring-ui-backend.log`;
  - confirm backend startup/runtime output appears after the marker.
- Failure smoke test:
  - temporarily start with an invalid backend environment or otherwise force backend startup
    failure;
  - confirm the exception/traceback appears in `logs/monitoring-ui-backend.log`.
- Regression check:
  - run `scripts/deployment/monitoring-ui/stop.ps1`;
  - confirm the PID file still points to a process that the stop script can terminate.

## Root Cause

The PowerShell script only wrote its own startup marker to `logs/monitoring-ui-backend.log`.
Unlike the frontend command in the same script and the Bash backend launcher, `$backendCommand`
invoked the backend module without piping stdout/stderr to `Out-File`.

## Resolution

- Updated `scripts/deployment/monitoring-ui/start.ps1` so `$backendCommand` appends the backend
  process stdout and stderr to `logs/monitoring-ui-backend.log` with `2>&1 | Out-File`.
- Kept the existing wrapper PowerShell process and PID-file behavior unchanged, so `stop.ps1`
  can still terminate the launched process tree.
- Added `tests/product_components/monitoring_ui/test_start_script.py` to assert the backend
  PowerShell command redirects output to `$backendLog` and that frontend output remains separate.

## Remaining Risks / Follow-up Actions

- Manual smoke testing on a live Windows UI start is still useful to confirm runtime log writes
  and process shutdown behavior against the local shell environment.
