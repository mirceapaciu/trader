# 260729-01 Load revisioned event taxonomy dynamically at runtime

## Parent Issue

`260728-01` — Add operator workflow for accepting controlled event-identity values.

## Problem Statement

The current decision implementation can persist accepted canonical values and mapped
aliases, but `normalize_event_identity` still relies on controlled values and aliases
compiled into Python constants. An operator decision therefore changes database metadata
without changing how subsequent analyses are classified until code is modified and
deployed.

This violates the core acceptance criterion that accepted values and aliases affect new
normalization without a deployment.

## Verified Evidence

- `src/product_components/thesis_builder/event_identity.py` owns static family, subtype,
  stage, coverage-role, participant-role, and alias collections.
- `t_event_taxonomy_values` and `t_event_taxonomy_state` can represent runtime values,
  aliases, family scope, and the active integer `taxonomy_revision`.
- Taxonomy decisions already record `effective_from_revision`, but the normalizer does
  not consume a revisioned taxonomy snapshot.

## Expected Behavior

- ThesisBuilder loads an immutable in-memory taxonomy snapshot for a requested integer
  revision.
- Live analysis uses the latest committed revision.
- Exact replay/regeneration can request an earlier revision.
- A snapshot contains canonical values, aliases, family-scoped subtype rules, and
  controlled values for every supported dimension.
- Normalization preserves unsupported proposals exactly as it does today.
- Analyses persist the exact integer `taxonomy_revision` used.
- Cache and replay keys include that revision.
- Snapshot refresh occurs atomically after a committed decision; in-flight analyses
  continue using the snapshot with which they started.
- A temporary database failure does not replace a valid loaded snapshot with an empty
  taxonomy.

## Architecture

- ThesisBuilder owns a taxonomy repository/export contract and snapshot loader.
- `normalize_event_identity` receives a snapshot explicitly; it must not query the
  database.
- The latest snapshot may be cached in-process by revision.
- Historical snapshots are reconstructed from immutable values and aliases whose
  effective revision range includes the requested revision.
- Do not create full database copies of the taxonomy for each revision.

## Acceptance Criteria

- A mapped alias is resolved by the next analysis after the decision commits, without a
  process deployment.
- An accepted canonical value is recognized by the next analysis.
- Family-scoped subtypes cannot resolve under the wrong family.
- Analyses and normalization provenance persist `taxonomy_revision`.
- Live, reprocess, regeneration, and backtest paths select a revision explicitly.
- Existing revision-1 behavior remains reproducible.
- Snapshot refresh is thread-safe and failure-safe.
- ThesisBuilder does not query taxonomy tables inside pure normalization functions.
- Design and data-model documentation describe snapshot ownership and revision use.

## Test Plan

1. Unit-test snapshot construction for canonical values, aliases, scopes, and effective
   revision ranges.
2. Verify `partnership` maps to `partnership_joint_venture` only from its effective
   revision onward.
3. Verify an accepted value is recognized without modifying Python constants.
4. Verify an older revision still reports the proposal as unmapped.
5. Test family-scoped subtype resolution.
6. Test atomic refresh while analyses use the previous snapshot.
7. Test database failure retains the last valid snapshot.
8. Test revision propagation through live analysis, regeneration, replay, and cache keys.
9. Run focused ThesisBuilder tests and the non-integration suite.

## Dependencies

None. This is the first implementation dependency for `260728-01`.

## Resolution

Implemented:

- Added immutable `EventTaxonomySnapshot` construction for canonical values,
  aliases, and family-scoped subtypes.
- Added a thread-safe provider that caches by integer revision, checks the latest
  committed revision between live analyses, and retains the last valid snapshot
  after a transient database failure.
- Made `normalize_event_identity` a pure snapshot consumer and persisted
  `taxonomy_revision` in both identity provenance and `t_news_analyses`.
- Included `taxonomy_revision` in the analysis prompt so deterministic LLM cache
  keys are revision-specific.
- Froze a revision for reprocess runs and made regeneration/backtest configuration
  select and record a requested or latest revision explicitly.
- Added lossless persisted-identity renormalization for the bounded backfill worker.

Remaining operational risk:

- Existing databases must apply the additive schema before running the new code.
- End-to-end production verification remains part of the parent issue rollout.
