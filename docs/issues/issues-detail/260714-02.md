# 260714-02 Watchlist instrument aliases lack common press names, breaking text-based attribution

## Problem Statement

Instrument-to-article attribution has two matching paths: provider ticker tags and alias
matching against article text (`_resolve_instrument_pairs` in ThesisBuilder, RSS
`ticker_matches` in NewsFetcher). The alias path reads `shared.t_instruments.aliases`
(via `t_exchange_listings`), and for several watchlist instruments that array is missing the
name the press actually uses:

- **GOOGL**: aliases are `['alphabet', 'alphabet inc. class a common stock', 'googl']` —
  **"Google" is absent**. Headlines like "Google loses final E.U. appeal over €4.1 billion
  Android fine" do not alias-match GOOGL at all.
- **NVO**: only hyphenated `novo-nordisk` variants — headlines write "Novo Nordisk" (no
  hyphen), so share-repurchase and approval announcements *about the company itself* fail to
  match.
- **BRK.A / BRK.B**: no "Berkshire", "Berkshire Hathaway", or "Buffett"-adjacent names.
- Pattern previously hit AVGO ("Broadcom" missing from RSS match terms, fixed 2026-07): the
  gap class recurs because nothing generates or validates press-style short names when a
  watchlist entry is created.

Consequences: (a) missed or late attribution for RSS articles (no provider tag to fall back
on); (b) articles genuinely about the company reach the LLM analysis stage with no textual
match and depend entirely on the LLM's judgment, inflating both `instrument_not_subject`
rejection volume (53% of all analyses, see 260714-01) and the count of "valid but instrument
never named" analyses (first-pass measurement showed 40% of valid analyses unmatched; after
correcting for these alias gaps the true read-through rate is ~5%).

A secondary trap: `shared.t_instrument_aliases` looks like the alias store but is not — it held
9 rows (AXA, RHM only) on 2026-07-14, while the registry (`PostgresSharedInstrumentRegistry`)
reads `COALESCE(i.aliases, ARRAY[]::TEXT[])` from `shared.t_instruments`. Tooling or fixes
pointed at the wrong table silently do nothing.

## Verified Evidence

- `src/product_components/shared/adapters.py:90-100` — `list_watchlist_records` sources
  aliases from `t_instruments.aliases`; `t_instrument_aliases` is not consulted.
- Production DB 2026-07-14: `shared.t_instrument_aliases` contains 9 rows (AXA/RHM);
  `t_instruments.aliases` for GOOGL/NVO/XOM/AVGO as listed above.
- `src/product_components/thesis_builder/service.py:571-579` — alias match
  (`contains_term(text, alias)`) is the only attribution path for untagged articles.
- Measurement 2026-07-14 over 1,854 valid analyses: matching against ticker +
  `t_instruments.aliases` + `display_name` left 733 (40%) "unnamed"; manual inspection showed
  the bulk were alias gaps ("Alphabet slides…", "Micron boosts…" style headlines that do name
  the company), reducing to 97 (5%) true read-throughs.
- Prior incident: AVGO late signals traced to RSS match terms lacking "Broadcom"
  (memory note 2026-07; RSS `t_rss_symbol_rules` shares the same gap class).

## Expected Behavior

1. **Backfill.** Every active watchlist instrument's `t_instruments.aliases` includes its
   press-style short name(s): the name a headline writer uses ("Google", "Novo Nordisk",
   "Berkshire Hathaway", "Exxon Mobil"/"Exxon", "Micron", …), plus common unpunctuated/
   unhyphenated variants of the legal name. Alias matching is case-insensitive
   (`contains_term`), so one casing per variant suffices.
2. **Generation at entry time.** The watchlist add flow (Monitoring UI watchlist editor /
   `instrument_lookup` providers, see 260615-11) derives candidate short names from the
   provider's company name (strip legal suffixes: Inc, Corp, Class A Common Stock, A/S, SA,
   …; emit hyphen/space variants) and stores them, so new instruments do not regress.
3. **Consistency check.** A lightweight audit (script or startup warning) flags active
   watchlist instruments whose alias set contains no alias distinct from the ticker and the
   full legal name — i.e. likely missing a press name. `SharedWatchlistRecord.has_missing_aliases`
   already exists for the empty case; extend the notion to "no usable short name".
4. **Clarify or retire `t_instrument_aliases`.** Either migrate its 9 rows into
   `t_instruments.aliases` and drop the table, or document it as the (future) authoritative
   store and make the registry read it — one source of truth, not two.
5. **RSS match terms aligned.** `t_rss_symbol_rules` / RSS `ticker_matches` for watchlist
   symbols are regenerated from the same alias source so the NewsFetcher-side matcher benefits
   too.

## Acceptance Criteria

- "Google loses final E.U. appeal…" alias-matches GOOGL; "Novo Nordisk A/S - share repurchase
  programme" alias-matches NVO (verified via `contains_term` against the stored aliases).
- All active watchlist instruments pass the short-name audit; the audit output is empty on a
  freshly backfilled production DB.
- Adding a new watchlist entry through the UI lookup flow stores derived short-name aliases
  without manual input; manual alias editing still possible.
- Exactly one alias store remains authoritative and the registry reads it; the other is
  migrated+dropped or wired in — no silent dual-table state.
- Re-running the "valid but instrument never named" measurement after backfill yields a
  read-through-only residue (no alias-gap false positives among top watchlist tickers).

## Test Plan

- Unit (alias derivation): legal-suffix stripping and variant generation for representative
  names (Alphabet Inc. Class A Common Stock → alphabet, google?; Novo-Nordisk A/S →
  novo nordisk, novo-nordisk; Exxon Mobil Corporation → exxon mobil, exxon; Berkshire
  Hathaway Inc. Class A → berkshire hathaway). Note: "Google" cannot be derived from the
  Alphabet legal name — the derivation contract must allow provider/manual curated extras;

- Unit (audit): instrument with only ticker+legal-name aliases is flagged; instrument with a
  short name passes.
- Unit (registry): aliases read from the single authoritative store; migration idempotent.
- Integration: seed a watchlist entry via the lookup flow against a fake provider, ingest an
  RSS article naming the company (no ticker tag), assert ThesisBuilder resolves the instrument
  pair via alias match.

## Resolution

Root cause: the repo had one real alias store (`shared.t_instruments.aliases`) but no shared
derivation contract for what should go into it. Provider normalization, watchlist writes, and
watchlist warnings all treated aliases differently, so common press names and punctuation variants
were easy to miss and impossible to audit consistently.

Implemented on 2026-07-14:

- Added a shared alias-derivation helper that centralizes legal-suffix stripping, short-name
  derivation, hyphen/space normalization, and curated press-name extras for exceptional symbols
  like `GOOGL`/`GOOG`, `BRK.A`/`BRK.B`, and `XOM`.
- Wired provider lookup normalization and watchlist writes through that helper so new watchlist
  entries persist derived press-name aliases automatically in `shared.t_instruments.aliases`.
- Tightened watchlist audit semantics from "no aliases at all" to "missing required press-name
  aliases", and exposed the exact missing alias set on `SharedWatchlistRecord`.
- Added `scripts/audit_watchlist_aliases.py` to report active watchlist rows with incomplete alias
  coverage and optionally backfill them through the shared admin writer.
- Updated the shared data-model doc to retire `t_instrument_aliases` as an authoritative alias
  store and document `t_instruments.aliases` as the single source of truth.
- Updated the Monitoring UI warning copy so it reflects incomplete press-name coverage instead of
  only the empty-alias case.

- The curated exceptional-alias list is intentionally small and evidence-driven. If production
  audit output shows additional common press-name gaps, they should be added to the shared helper
  rather than patched ad hoc in component-specific code.
