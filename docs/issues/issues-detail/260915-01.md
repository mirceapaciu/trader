# 260915-01 Show exact conditions and thresholds for blocked backtest candidates

## Problem Statement

The Backtester records every candidate that fails admission, market-data readiness, sizing, or a
portfolio guardrail as `exit_reason = risk_blocked`, with only a short `risk_block_rule` code. The
Monitoring UI displays the generic exit reason but does not display even that rule code. An
operator can therefore see that a candidate was blocked, but cannot see which stage rejected it,
the condition that was evaluated, the observed value, the configured threshold, or the dynamic
portfolio state that caused the decision.

The single `risk_blocked` classification is also misleading. It combines true portfolio-risk
failures with admission failures such as `review_not_approved`, data-readiness failures such as
`atr_unavailable`, and sizing failures such as `size_below_one_share`.

Reconstructing an explanation after a run is not reliable: configuration can change, and dynamic
state such as portfolio exposure, daily P&L, open positions, and portfolio headroom is not retained
on the blocked trade. The complete structured explanation must be captured at decision time.

## Verified Evidence

- The latest completed Haas backtest at investigation time,
  `bt_71c7312a86b24daa922288670c8bddba`, was created on `2026-09-15 11:42:34 UTC` and completed at
  `11:45:42 UTC`. It considered 25 cards, opened 5 trades, and recorded 20 candidates (80%) as
  `risk_blocked`.
- Those 20 rows span four distinct causes: 6 `atr_unavailable`, 7 `size_below_one_share`,
  5 `position_exists`, and 2 `review_not_approved`. Thus the headline "risk blocked" count
  combines market data, sizing, and admission outcomes; no portfolio-risk threshold actually
  blocked a candidate in this run.
- The run used `execution_model_snapshot_json.mode = live_parity`, with
  `atr_stop_mult = 1.5`, `min_confidence = 0.6`, and `take_profit_r = 2.0`. Its risk snapshot
  included `max_positions = 5`, `max_daily_trades = 10`, `max_position_usd = 3000`,
  `max_portfolio_exposure_usd = 10000`, `max_sector_exposure_usd = 2500`, and
  `daily_loss_limit_usd = 200`. These run-level thresholds are retained, but the per-candidate
  observed operands and binding constraint are not.
- `src/product_components/trade_executor/pipeline.py` represents admission and risk decisions as
  `GateOutcome` and already puts some observed values and thresholds in `GateOutcome.details`,
  including confidence, expiry, review state, daily P&L, trade count, open-position count, deployed
  capital, proposed notional, and exposure caps.
- `src/product_components/backtester/engine.py::_live_parity_execution_plan` discards those details
  and returns only `admission.reason.value` or `risk_gate.reason.value`. Missing ATR and zero-share
  sizing also return only a reason string. `_risk_blocked_trade` consequently receives and persists
  only that string.
- `size_position` returns only final quantity and notional. When quantity is zero, the result does
  not identify whether the risk budget, per-position cap, or portfolio headroom was the binding
  constraint, so even the caller cannot currently produce the required explanation.
- `backtester.t_backtest_trades` has `risk_block_rule` but no decision stage, decision timestamp,
  or structured block-detail payload. Its entry fields are null for blocked candidates, so the
  attempted entry time and candidate price are not otherwise available on the row.
- The Monitoring UI repository and API already return `risk_block_rule`, but
  `src/product_components/monitoring_ui/frontend/src/backtester/BacktesterTab.tsx` renders only
  `exit_reason` in both the card-detail trade table and the main Trades table.
- A bounded integrity check on the same run found 25 candidate rows, 5 entered rows, no
  news-readiness look-ahead, no expired-card rows, and no entered rows with missing or sub-0.95 bar
  coverage. The observed block distribution is therefore suitable evidence for this visibility
  gap rather than an artifact of a failed or incomplete run.

## Expected Behavior

Every candidate decision should retain a versioned, structured explanation recorded at the moment
the decision is evaluated. A user viewing a backtest should be able to move from the run-level
blocked count to a stage/reason breakdown and then to a candidate-level explanation containing:

- the decision stage (`admission`, `market_data`, `sizing`, or `portfolio_risk`);
- a stable machine-readable reason and check identifier;
- the failed condition or comparator;
- the observed value and required threshold, including units;
- the inputs and derived values used by the calculation;
- the binding constraint when several limits contribute to a result; and
- a reference to related state, such as the existing position that caused `position_exists`.

For example, `size_below_one_share` should show the candidate entry, ATR, ATR multiplier, stop
distance, risk budget, per-position cap, portfolio headroom, each independently calculated quantity,
the final quantity, and which constraint reduced it below one share. A portfolio-cap failure should
show deployed capital plus proposed notional compared with the configured cap. A review failure
should show the actual and required review states. An ATR failure should show the required data,
lookback/coverage information, and the safe failure category available from MarketData.

The UI should call the aggregate "Blocked candidates" or "Not entered", reserve "Portfolio risk"
for actual risk-policy failures, and present counts by stage and reason. Selecting a bucket should
filter the candidate table; selecting a candidate should open a readable explanation rather than
raw JSON.

Existing runs must remain readable. When only the legacy reason code is available, the UI should
show it and explicitly state that detailed operands were not recorded for that run. It must not
invent an exact explanation by combining historical rows with current configuration.

The explanation contract should be shared with TradeExecutor so live and simulated decisions do
not drift. This issue does not change admission, sizing, or risk policy and does not relax any
threshold.

## Acceptance Criteria

- Backtester persistence records a decision timestamp, decision stage, stable reason code, and a
  versioned structured detail payload for every blocked candidate. Schema changes are idempotent.
- The structured payload records the failing check, observed value, threshold/expected value,
  units where applicable, and the inputs needed to reproduce the decision. Dynamic values are
  captured at evaluation time rather than derived later from current state.
- Sizing reports quantity independently allowed by risk budget, per-position notional, and
  portfolio headroom, plus final quantity and the binding constraint.
- Admission outcomes distinguish expiry, confidence, watchlist, existing-position, review-state,
  and horizon-mapping failures, with relevant actual and expected values. `position_exists`
  identifies the blocking position or simulated trade when available.
- Market-data outcomes such as `atr_unavailable` identify the required metric and include bounded,
  non-secret availability/coverage context supplied by the MarketData contract.
- Portfolio-risk outcomes report their exact operands and thresholds: position count, portfolio or
  sector exposure, daily trade count, or combined daily P&L as appropriate. A daily-loss outcome
  distinguishes a newly triggered halt from a previously latched halt.
- The live-parity Backtester preserves the shared TradeExecutor decision explanation rather than
  reducing `GateOutcome` to a string. Legacy execution mode produces the same public explanation
  shape through an adapter.
- The Monitoring API exposes the structured explanation and supports filtering blocked candidates
  by stage and reason. It also exposes an aggregate count breakdown by stage and reason without
  requiring the frontend to fetch every trade row.
- The Backtester UI displays a run-level blocked-candidate count and percentage, stage/reason
  breakdown, filterable candidate rows, and a detail drawer with a plain-language explanation,
  failed comparison, inputs, derived values, threshold, and related record links when available.
- The card-detail table also exposes the block reason and provides access to the same explanation.
- Older rows with only `risk_block_rule` render a clear legacy fallback and remain API-compatible.
- User-facing labels do not describe admission, market-data, or sizing failures as portfolio-risk
  failures.
- Explanation payloads and rendered text are bounded and never include credentials, tokens, DSNs,
  request headers, or other secrets.
- No admission, sizing, execution, or portfolio-risk behavior changes as part of this issue.

## Test Plan

- Add unit tests for each admission-gate rejection proving the structured result contains the
  correct stage, reason, actual value, and expected value or threshold.
- Add sizing unit tests where each of risk budget, per-position cap, and portfolio headroom is the
  binding constraint, including a zero-share result with reproducible intermediate quantities.
- Add risk-gate unit tests for max positions, portfolio exposure, sector exposure, daily trade cap,
  newly triggered daily-loss halt, and already latched halt, asserting exact operands and limits.
- Add Backtester engine tests for both `live_parity` and `legacy_flat_percent` proving structured
  explanations survive into blocked `SimulatedTrade` rows without changing which candidates pass.
- Add repository/schema tests for idempotent migration and JSON round-trip, including legacy rows
  whose new fields are null.
- Add Monitoring UI backend tests for stage/reason aggregation, filters, structured detail
  serialization, and legacy fallback behavior.
- Add frontend tests for the blocked-candidate summary, stage/reason filtering, each explanation
  renderer, related-position links, unknown future reason fallback, and legacy rows.
- Run `uv run pytest -m "not integration"`.
- Run the Monitoring UI frontend test suite and production build.
- Run a replay backtest over a fixture containing at least one failure from each stage and verify
  that the persisted operands reproduce every decision and the UI counts match the database.
