# 260628-01 Regeneration backtest mode always fails and is an unimplemented no-op

## Problem Statement

The Backtester offers a `regeneration` run mode through the Monitoring UI, but it cannot ever succeed, and even if it could it would not do anything different from `replay`. Two independent defects combine:

1. **It always crashes on the first DB insert.** `BacktesterService.run` calls `repository.create_run` before doing any work, and `create_run` never populates the regeneration-only columns `thesis_config_snapshot_json` and `llm_token_budget_limit`. The `t_backtest_runs` table has a check constraint requiring those columns to be non-null when `mode = 'regeneration'`, so every regeneration run dies with a `CheckViolation` and no run row is ever persisted.
2. **Regeneration is a no-op stub.** Neither `BacktesterService.run` nor `BacktesterEngine.run` branches on `params.mode`. Both modes export the *existing* thesis cards for the window and simulate them against cached price bars. There is no LLM call and no thesis-card regeneration. So a regeneration run, even if the constraint allowed it, would behave identically to replay.

Net effect: an operator selecting "regeneration" in the UI gets a run that appears to start, fails silently in a background thread, and never appears in the run list. (The UI-side symptom — the button stuck on "Running…" forever — is tracked separately in 260628-02.)

## Verified Evidence

- `src/product_components/backtester/db/schema.sql:122-126` — `CONSTRAINT ck_backtest_runs_regeneration_requires_config CHECK (mode <> 'regeneration' OR (thesis_config_snapshot_json IS NOT NULL AND llm_token_budget_limit IS NOT NULL))`.
- `src/product_components/backtester/repository.py:64-91` — `create_run` inserts only `execution_model_snapshot_json` and `risk_model_snapshot_json`; it never sets `thesis_config_snapshot_json` or `llm_token_budget_limit`.
- `src/product_components/backtester/service.py:30-64` — `run` does not branch on `params.mode`; it calls `create_run` then `BacktesterEngine(...).run()` for every mode.
- `src/product_components/backtester/engine.py:87-140` — `BacktesterEngine.run` exports existing cards and simulates; no use of `mode`, no LLM/regeneration path.
- `src/product_components/monitoring_ui/frontend/src/backtester/BacktesterTab.tsx:239` — the UI presents `<option value="regeneration">regeneration</option>` and submits it.
- `logs/monitoring-ui-backend.log` (run `bt_d8e35b6ba4fb489f8c2938fedf6d55ae`, 2026-06-28 17:59:37) — `psycopg.errors.CheckViolation: new row for relation "t_backtest_runs" violates check constraint "ck_backtest_runs_regeneration_requires_config"`, raised from `service.py:37 -> repository.py:73`. The failing row shows `mode = regeneration`, `thesis_config_snapshot_json = null`, `llm_token_budget_limit = null`.
- Database: `SELECT mode, status, count(*) FROM backtester.t_backtest_runs GROUP BY 1,2` returns only `replay/completed` and `replay/failed`; zero rows with `mode = 'regeneration'` have ever persisted.

## Expected Behavior

Regeneration mode must not be reachable in a form that always fails. Either:

- **(A) Hide regeneration until it is implemented** — the UI should not offer a `regeneration` option, and the backend should reject `mode = regeneration` with a clear `422`/validation error explaining it is not yet supported; or
- **(B) Implement it end to end** — the backtester populates `thesis_config_snapshot_json` and `llm_token_budget_limit` on `create_run`, and `BacktesterService`/`BacktesterEngine` actually regenerate thesis cards (LLM path) for the window instead of replaying the existing ones.

Option A is the smaller, lower-risk change and is recommended unless regeneration is being built now. Whichever path is chosen, selecting a mode in the UI must never produce a run that silently fails on insert.

## Acceptance Criteria

- Selecting/triggering a backtest can never produce a `ck_backtest_runs_regeneration_requires_config` violation.
- If option A: the UI mode selector no longer offers `regeneration`; `start_backtest_run` (or `_build_params`) rejects `mode = regeneration` with a validating error surfaced to the operator; no regeneration run row is created.
- If option B: a regeneration run inserts the required config columns, runs a real regeneration path distinct from replay, and completes with `status = 'completed'`; the engine/service branch on `params.mode`.
- The chosen behavior is covered by tests (below) and no existing replay behavior regresses.

## Test Plan

- Add a unit test asserting that requesting `mode = regeneration` either (A) is rejected before any DB write with a clear error, or (B) inserts non-null `thesis_config_snapshot_json` and `llm_token_budget_limit` and follows a regeneration code path.
- Add a backtester service/repository test that a `replay` run is unaffected.
- If option A: add a frontend test asserting the mode selector does not render a `regeneration` option (or that submitting it is blocked client-side).
- `uv run pytest tests/product_components/backtester -q` passes.
- `uv run pytest -m "not integration"` passes.

## Root Cause

Regeneration was scaffolded (mode enum, DB columns, and a guarding check constraint) ahead of the actual implementation, but the run-creation path and engine were never taught to populate the config columns or execute a distinct regeneration flow. The UI was wired to offer the mode before the backend could honor it, so every selection fails the constraint that was added to protect the not-yet-built feature.
