# 260708-02 Cache LLM article analyses so repeated regeneration backtests don't re-pay for identical prompts

## Problem Statement

Every regeneration backtest re-runs the full LLM analysis for every article×instrument pair in
its window, even when the run repeats a window that has been analyzed before with the same model
and prompt. The analysis call is (near-)deterministic — `temperature=0` with a strict JSON
response schema — and the decision thresholds (`min_confidence`, `min_relevance`, evidence-window
settings) are applied *after* analysis during card building, so repeat runs pay full LLM cost to
recompute byte-identical answers. This is the dominant cost of a regeneration re-run, and it is
what drives token-budget starvation (issue 260708-01, run `bt_2373c76aac62411386f96c0771a20f75`):
a budget that would comfortably cover one pass over a window is exhausted again on every
subsequent pass.

A durable cache keyed on (model, max output tokens, prompt hash) would make repeat regeneration
runs over the same articles nearly free and make budget exhaustion unreachable for
already-analyzed windows.

One obstacle: the market-context snapshot embedded in the prompt carries volatile
`as_of` / `quote_fetched_at` / `bars_fetched_at` timestamps. Two runs differing only in
`card_delay_seconds` produce prompts that differ *only* in those timestamp strings while being
informationally identical (backtest context is built from daily bars, so the actual numbers only
change when analysis time crosses a session close). Without removing those fields from the
prompt, a prompt-hash cache misses on every timing variation.

## Verified Evidence

- `src/product_components/thesis_builder/llm_client.py:48-58` — `OpenAIThesisClient.analyze`
  calls the Responses API with `temperature=0` and a strict JSON schema
  (`_THESIS_ANALYSIS_RESPONSE_FORMAT`), so the response is deterministic for a given prompt for
  caching purposes.
- `src/product_components/thesis_builder/llm_client.py:169-237` — `_build_prompt` serializes
  article + instrument + market context with `json.dumps(..., sort_keys=True)`: the prompt is
  already a canonical string containing every analysis input. The embedded
  `market_context` payload, however, includes the snapshot's `as_of`, `quote_fetched_at`, and
  `bars_fetched_at` timestamps.
- `src/product_components/thesis_builder/llm_client.py:107` — `actual_tokens =
  int(raw.get("estimated_tokens") or estimated_tokens)`: a token count of `0` is falsy and falls
  back to the (large) estimate. Any mechanism for making cache hits budget-free must not rely on
  returning `estimated_tokens: 0`.
- `src/product_components/backtester/regeneration.py:135-149` —
  `ThesisRegenerationProvider.regenerate` constructs the LLM client and `ThesisAnalyzer` itself,
  and already has an injection seam (`llm_client_factory`). The caching wrapper belongs here;
  the live ThesisBuilder pipeline never touches this code path.
- `src/product_components/backtester/regeneration.py:173-197` — backtest market context is
  reconstructed from **daily bars only** (`quote=None`), so within a trading session every
  analysis time maps to the same bar-derived numbers; prompts become day-granular once the
  volatile timestamps are stripped.
- `src/product_components/thesis_builder/regeneration.py:137-190` — the same snapshot dict is
  passed both to the analyzer and to `persist_analysis_and_update_evidence`; the persisted copy
  is the no-look-ahead audit trail and must keep its timestamps. Thresholds are applied inside
  `persist_analysis_and_update_evidence`, after the LLM call — so threshold sweeps over a cached
  window would make zero LLM calls.
- `sim_bt_<run_id>` schemas are per-run and isolated; a cache stored there would not survive to
  the next run. The cache must live in the durable backtester schema.

## Expected Behavior

1. **Durable cache table.** A table in the backtester schema (not the per-run `sim_bt_*`
   schemas), e.g. `backtester.t_llm_analysis_cache`, created via idempotent
   `CREATE TABLE IF NOT EXISTS`. Cache identity is `(llm_model, max_output_tokens,
   prompt_sha256)`; `article_id`, `ticker`, `exchange_code`, and `created_at` are stored as
   supporting columns for debugging and targeted invalidation, not as part of the key. The value
   is the raw response JSON.
2. **Caching wrapper client.** A wrapper implementing the `ThesisLlmClient` protocol
   (`src/product_components/thesis_builder/llm_client.py:15-17`) that hashes the prompt, serves
   hits from the table, and delegates misses to the wrapped client. Wired only into
   `ThesisRegenerationProvider.regenerate`; the live ThesisBuilder pipeline is unchanged (live
   articles are seen once, so a live cache is pure storage cost).
3. **Cache the raw pre-parse JSON dict** returned by `client.analyze()` (after the
   `estimated_tokens` override from actual API usage), not the parsed `LlmAnalysisResult`. Future
   changes to `parse_analysis_result`/validation then still apply to cached responses, and
   rejected analyses (e.g. `instrument_mismatch`) replay deterministically. Transient failures
   (timeouts, empty or unparseable responses) are never cached.
4. **Cache hits are budget-free.** A hit must not consume the run's token budget:
   `TokenBudgetExhausted` must be unreachable on a fully cached window. Implementation must
   account for the falsy-zero fallback at `llm_client.py:107`. Run statistics should still
   distinguish real LLM calls from cache hits (e.g. tokens used counts only real calls).
5. **Prerequisite prompt change (before seeding the cache).** Strip `as_of`,
   `quote_fetched_at`, and `bars_fetched_at` from the market-context payload **at prompt-build
   time** in `_build_prompt`, leaving the snapshot persisted alongside analyses intact as the
   audit trail. These fields carry no decision-relevant signal the model can act on (the
   article's `published_at` and the bar-derived numbers are already in the prompt). After this,
   `sha256(prompt)` is a correct cache key with no separate canonicalization, and prompts are
   stable across `card_delay_seconds` variations within a trading day. Note this changes the
   production prompt too (live and regeneration share `_build_prompt`, preserving the
   regeneration invariant), so it must land before cache entries are written.

Out of scope (separate concerns): caching on the live path; a two-step (timeless/timed) analysis
prompt split; backfilling intraday bars to approximate the live quote in regeneration context;
historizing live market-context snapshots.

## Acceptance Criteria

- Regenerating an identical window+config twice makes ~0 LLM calls on the second run, reports
  ~0 tokens used, and cannot hit `TokenBudgetExhausted` on the cached portion; the second run's
  generation funnel counts (analyses, rejections, cards) are identical to the first.
- Changing the model, `max_output_tokens`, or any prompt content (article, instrument, market
  context numbers, prompt template) misses the cache; a `card_delay_seconds` change that stays
  within the same trading sessions hits it.
- Rejected analyses (e.g. `instrument_mismatch`) replay identically from cache, without a fresh
  LLM call.
- The cache survives across runs and sim-schema teardown; transient LLM failures leave no cache
  entry.
- Schema bootstrap is idempotent (re-running the backtester schema SQL on an existing database
  succeeds).
- The persisted `market_context_snapshot` on analyses still contains `as_of` (audit trail
  unchanged); only the prompt payload loses the timestamp fields.

## Test Plan

- Unit tests (`tests/product_components/`, fakes, no external deps):
  - Wrapper: miss → delegates and stores; hit → returns stored raw JSON without delegating;
    exception from the inner client → propagates and stores nothing; unparseable response →
    nothing cached.
  - Budget: `ThesisAnalyzer` over a fully cached window never raises `TokenBudgetExhausted`
    and reports ~0 tokens used (covers the falsy-zero fallback at `llm_client.py:107`).
  - Prompt stability: `_build_prompt` output is byte-identical for two snapshots differing only
    in `as_of`/`quote_fetched_at`/`bars_fetched_at`; differing bar-derived numbers change it.
  - Key sensitivity: distinct `model` or `max_output_tokens` produce distinct cache identities
    for the same prompt.
- Integration test (live Postgres, `tests/integration/`): cache table round-trip — insert via the
  wrapper, read back by key, verify idempotent schema bootstrap.
- End-to-end: run the same regeneration window twice against a real database; verify the second
  run's `llm_tokens_used ≈ 0`, no budget exhaustion, and identical funnel counts in the run
  summary.
