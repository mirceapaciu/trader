# 260816-01 Add single-admin authentication for taxonomy decisions

## Problem Statement

Taxonomy decisions require a trusted authenticated actor, but Monitoring UI currently
supports only an identity header supplied by an authenticated reverse proxy. Haas has
no such proxy contract, so taxonomy mutation must remain disabled and the operator
cannot use the completed decision workflow.

Add deliberately small, first-party authentication for exactly one administrator. The
administrator has the fixed username `admin`; there is no user database, registration,
password reset, role management, or support for additional accounts. The password is
provided to Monitoring UI through `.env.secrets` and must never be committed.

## Verified Evidence

- `MonitoringUiSettings` exposes `UI_TAXONOMY_DECISIONS_ENABLED` and
  `UI_TAXONOMY_TRUSTED_ACTOR_HEADER`, but has no administrator-password or session
  configuration.
- `_trusted_taxonomy_actor` accepts identity only from the configured request header.
- Monitoring UI has no login, logout, current-session endpoint, authentication
  middleware, or frontend login flow.
- The taxonomy decision UI already handles authorization failures, but cannot establish
  an authenticated identity itself.
- The current design requires taxonomy mutation to stay disabled on Haas until an
  authenticated reverse proxy exists.

## Expected Behavior

### Configuration and identity

- The only supported account is the fixed username `admin` and the audit actor recorded
  on taxonomy commands is `admin`.
- `UI_ADMIN_PASSWORD` contains the administrator password and is loaded from
  `.env.secrets` using the existing Monitoring UI environment-loading order.
- `.env.secrets` remains untracked; examples and documentation show only the variable
  name and a placeholder, never a real password.
- Taxonomy mutation fails closed when `UI_TAXONOMY_DECISIONS_ENABLED=true` but
  `UI_ADMIN_PASSWORD` is absent or blank. Startup emits an actionable message that does
  not reveal the password.
- The legacy trusted-proxy mode is either removed or made mutually exclusive with this
  mode. Configuration must not silently choose between two actor sources.

### Authentication endpoints and session

- Monitoring UI provides endpoints to log in, log out, and query whether the current
  browser session is authenticated.
- Login accepts username and password. Any username other than `admin`, or an incorrect
  password, returns the same generic failure response.
- Password comparison is timing-safe. Passwords and submitted credentials never appear
  in logs, API responses, metrics, URLs, or persisted application data.
- Successful login creates an opaque, random, server-side session and returns only an
  `HttpOnly` cookie with `SameSite=Strict`, a bounded lifetime, and `Secure` enabled for
  the production HTTPS deployment. Session IDs are rotated on every login.
- Sessions expire after a documented idle or absolute timeout. Logout invalidates the
  server-side session and clears the cookie. A Monitoring UI backend restart may
  invalidate all sessions; persistence across restart is not required.
- Failed login attempts are rate-limited per source without disclosing whether the
  username or password was wrong.

### Authorization and request safety

- `POST /api/thesis-builder/taxonomy-decisions` requires a valid administrator session
  and derives actor `admin` exclusively on the server. Browser payloads and arbitrary
  headers cannot select the actor.
- The taxonomy command-status endpoint requires the same session. Read-only taxonomy
  gap and canonical-value endpoints remain accessible without login.
- Cookie-authenticated mutation requests have CSRF protection. At minimum, the backend
  rejects untrusted `Origin`/`Referer` values and requires a session-bound CSRF token.
- Unauthenticated requests return `401`; authenticated requests that fail another
  authorization rule return `403`.
- Authentication failures do not change command state, publish Redis messages, or
  write taxonomy decisions.
- Production authentication is used only over HTTPS. Documentation must state that the
  password must not be sent over plain HTTP outside loopback development.

### Monitoring UI experience

- When an operator attempts a taxonomy decision without a session, the UI presents a
  login form instead of the current trusted-proxy-unavailable dead end.
- After successful login, the pending decision form is preserved and can be submitted
  without re-entering its values.
- The UI exposes a visible logout action and clearly shows that the current actor is
  `admin`.
- Expired sessions return the user to the login flow while preserving safe, unsent form
  state. The UI never stores the administrator password in local storage, session
  storage, IndexedDB, URLs, or application logs.
- Login errors are generic and actionable; taxonomy conflict, validation, command, and
  backfill errors retain their existing distinct handling.

## Out of Scope

- Multiple users, roles, registration, invitations, email, external identity providers,
  password reset, and account recovery.
- Protecting all read-only Monitoring UI pages or APIs.
- Persisting sessions across backend restarts.
- Managing or rotating `.env.secrets` outside the existing deployment process.

## Acceptance Criteria

- With taxonomy decisions enabled and a valid `UI_ADMIN_PASSWORD` loaded from
  `.env.secrets`, `admin` can log in and complete map, accept, and reject actions.
- The resulting immutable taxonomy decision records actor `admin` without accepting an
  actor from the browser.
- Missing/blank password configuration fails closed, and an incorrect login cannot
  submit or inspect a taxonomy command.
- Login, session check, decision submission/status polling, expiry, and logout work
  through the deployed UI.
- Session cookies have the specified security attributes; logout and expiry invalidate
  them server-side.
- CSRF attempts and requests from untrusted origins cannot create a taxonomy command.
- Repeated failed logins are throttled and produce no credential or username disclosure.
- Read-only taxonomy gaps and canonical values remain available without authentication.
- No credential or session token is logged, persisted in PostgreSQL/Redis, or stored by
  the frontend.
- Monitoring UI behavior/configuration docs and deployment secret templates document
  the single-admin mode and its HTTPS requirement.

## Dependencies

- Builds on the asynchronous trusted-actor command contract from `260729-02` and the
  completed Monitoring UI workflow from `260729-04`.

## Resolution

### Root cause

The completed taxonomy workflow depended on a trusted reverse-proxy identity header,
but Haas does not provide that proxy contract. As a result no operator could establish
the trusted actor required by a mutation.

### Changes made

- Replaced the Monitoring UI taxonomy identity path with a fixed `admin` account backed
  by `UI_ADMIN_PASSWORD` from `.env.secrets`; legacy header configuration is rejected
  when mutation is enabled.
- Added process-local random sessions, login throttling, HttpOnly Strict cookies,
  session-bound CSRF tokens, origin enforcement, logout, and authenticated command
  polling. Taxonomy commands always receive server-derived actor `admin`.
- Added the UI login/logout flow while preserving the open decision form, and documented
  the HTTPS and public-origin deployment requirements.
- Added backend session/configuration coverage and updated taxonomy component tests.

### Verification

### Remaining risk / follow-up

Sessions are intentionally invalidated on Monitoring UI restart and are held only in
process memory. Deployment must set `UI_ADMIN_ALLOWED_ORIGIN` and terminate TLS before
enabling the feature outside loopback development.
