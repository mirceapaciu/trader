# 260615-02 Remove ThesisBuilder direct database access to Shared contracts

## Problem Statement

ThesisBuilder currently reads watchlist and alias data directly from the `shared` schema and writes review rows directly into `shared.t_thesis_card_reviews`. Those accesses bypass the owning shared contract boundary.

## Verified Evidence

- `src/product_components/thesis_builder/repository.py:69` reads from `shared.<watchlist_table>`.
- `src/product_components/thesis_builder/repository.py:70` joins `shared.t_instrument_aliases`.
- `src/product_components/thesis_builder/repository.py:448` inserts directly into `shared.t_thesis_card_reviews`.

## Expected Behavior

ThesisBuilder should resolve instruments through a shared Instrument Registry API or adapter and should write review state through a shared review API or adapter. Direct ad hoc SQL against shared tables should be removed from ThesisBuilder repositories.

## Acceptance Criteria

- ThesisBuilder does not query shared watchlist or alias tables directly.
- ThesisBuilder does not insert review state directly into `shared.t_thesis_card_reviews`.
- Shared watchlist, alias, and review interactions are routed through shared-owned APIs or adapters.
- ThesisBuilder boundary tests fail if SQL references `shared.` directly for runtime reads or writes.

## Test Plan

- Run `uv run pytest tests/product_components/thesis_builder -q`.
- Run `uv run pytest tests/integration/test_thesis_builder_integration.py -m integration`.
- Add focused tests for shared contract adapters used by ThesisBuilder.

## Resolution

Resolved.

### Root Cause

ThesisBuilder mixed its own persistence responsibilities with shared-contract access. The repository issued direct SQL against shared watchlist and alias tables for instrument resolution, and it also wrote shared review state directly during card creation. That made the ThesisBuilder repository span two ownership boundaries instead of remaining ThesisBuilder-schema-only.

### Steps Taken

- Added shared-owned DB-backed adapters in `src/product_components/shared/adapters.py`:
  - `PostgresSharedInstrumentRegistry` for active watchlist instruments plus aliases.
  - `PostgresSharedThesisCardReviewWriter` for shared review upserts.
- Removed `shared_schema` and `watchlist_table` from `PostgresThesisBuilderRepository`.
- Removed shared-table SQL from `src/product_components/thesis_builder/repository.py`.
- Moved instrument resolution orchestration into `ThesisBuilderRunner`, which now consumes `SharedInstrumentRecord` rows from the shared registry adapter and applies the existing ticker/alias matching logic there.
- Moved the preapproved review write out of the ThesisBuilder repository and into the shared review writer adapter. The runner now upserts shared review state before publishing the signal and before marking the card as published.
- Updated ThesisBuilder runtime wiring in `main.py` and the integration test runner to construct and inject the shared-owned adapters explicitly.
- Added focused unit tests for the new shared adapters and a boundary test that asserts ThesisBuilder runtime files no longer reference shared-table SQL directly.

### Remaining Risks Or Follow-Up

- The shared adapters are in-process and DB-backed for now. That is intentional for this issue, but later issues can reuse these adapters or lift them into a broader shared service layer if needed.
- Integration tests still seed shared tables directly as setup, which is acceptable for test scaffolding and does not reintroduce the runtime boundary violation.
