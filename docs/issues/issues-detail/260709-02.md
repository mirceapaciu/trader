# 260709-02 Pre-filter articles that cannot be about the instrument before paying for full LLM analysis

## Problem Statement

37–42% of all LLM analysis spend produces `instrument_not_subject` rejections: the article is sent
to the full thesis-analysis prompt for an instrument that turns out not to be a subject of the
article at all. Across the two verified regeneration runs this was 145/348 and 130/356 analyses.
This waste directly caused both backtest windows to be truncated by token-budget exhaustion
(~40–55% of each window never analyzed), and it inflates live LLM cost for zero information gain —
the rejected analyses feed no evidence window and no card.

The default per-run budget has since been raised to 5M tokens
(`BACKTESTER_LLM_MAX_TOKENS_PER_RUN`, commit 79d4b89), which masks the symptom for typical windows
but does not remove the waste: roughly 4 of every 10 analysis calls are still spent discovering
that the article is not about the instrument — something largely determinable without the full
prompt.

## Verified Evidence

- `docs/verification-runs/260708-bt_2373c76aac62411386f96c0771a20f75.md` — 145 of 348 analyses
  (42%) `instrument_not_subject`; budget exhausted at ~55% window coverage; recommendation #3
  "pre-filter `instrument_not_subject` articles more cheaply".
- `docs/verification-runs/260708-bt_2416cea0515f427681f879f1c363ec3d.md` — 130 of 356 analyses
  (37%) `instrument_not_subject`; budget exhausted at ~39% coverage; recommendation #2 repeats the
  pre-filter recommendation.
- `src/product_components/thesis_builder/llm_client.py:184-252` — instrument-subject
  determination happens inside the full analysis prompt (`instrument_grounding_rules`), i.e. at
  full analysis cost per (article × instrument) pair.
- `src/product_components/backtester/settings.py:123` — budget default now 5,000,000 (raise
  already applied; the waste itself is not addressed).
- Related but distinct: 260708-01 (make exhaustion visible) — visibility only; explicitly leaves
  cheaper pre-filtering out of scope.

## Expected Behavior

Before invoking the full thesis-analysis prompt for an (article, instrument) pair, ThesisBuilder
applies a cheap subject screen. In order of preference:

1. **Deterministic screen (free):** the instrument's ticker or any registered alias (shared
   instrument registry) must appear in the article headline, summary, or provider ticker tags.
   Pairs failing the screen are persisted as analyses with a distinct reason code (e.g.
   `prefiltered_not_subject`) without any LLM call, keeping the funnel auditable.
2. **Optional cheap-model screen:** for pairs passing the deterministic screen, an optional
   low-cost classification call (small max-output, cheap model) may decide subjecthood before the
   full prompt. This tier is configurable and may ship later; the deterministic tier alone must
   land.

The screen must be conservative: when in doubt (ticker mentioned anywhere relevant), proceed to
full analysis — false negatives suppress evidence and are worse than the token waste. The
filter's hit rate is observable (counts by reason code) so its precision can be verified against
historical data where full-prompt ground truth exists.

## Acceptance Criteria

- Replaying a historical window shows a measurable reduction (target: majority) of
  `instrument_not_subject` full-prompt analyses, with **zero** loss of analyses that previously
  returned `instrument_is_subject = true` (validate against cached/persisted past analyses).
- Prefiltered pairs are persisted and countable by reason code; monitoring/funnel numbers still
  reconcile (articles → pairs → analyses → valid).
- Token usage per covered window-day drops accordingly in a regeneration run over a previously
  verified window.
- The screen is configuration-documented in `thesis-builder/configuration.md` and can be disabled.

## Test Plan

- Unit tests: deterministic screen against fixtures — ticker in headline (pass), alias in summary
  (pass), ticker only in provider tags (pass), no mention anywhere (prefiltered), case/format
  variants (BRK.B style) resolved via the alias registry.
- Unit test: prefiltered pair persists an analysis row with the new reason code and no LLM client
  call (fake client asserts zero invocations).
- Regression test over the cached analyses from consumed windows (LLM cache, 260708-02): no pair
  that historically returned `instrument_is_subject = true` is prefiltered.
- Integration test: end-to-end consume of a news event with two mapped instruments, one mentioned
  and one not — exactly one LLM call, two persisted analyses.
