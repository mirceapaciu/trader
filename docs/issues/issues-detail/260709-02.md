# 260709-02 Two-tier pre-filter (deterministic screen + small-LLM triage) before paying for full LLM analysis

## Problem Statement

37–42% of all LLM analysis spend produces `instrument_not_subject` rejections: the article is sent
to the full thesis-analysis prompt for an instrument that turns out not to be a subject of the
article at all. Across the two verified regeneration runs this was 145/348 and 130/356 analyses.
This waste directly caused both backtest windows to be truncated by token-budget exhaustion
(~40–55% of each window never analyzed), and it inflates live LLM cost for zero information gain —
the rejected analyses feed no evidence window and no card.

The default per-run budget has since been raised to 5M tokens
(`BACKTESTER_LLM_MAX_TOKENS_PER_RUN`, commit 79d4b89), which masks the symptom for typical windows
but does not remove the waste.

Note that two deterministic screens already exist and the waste **survives both**: the NewsFetcher
relevance filter is article-level only (any watchlisted tag or include-keyword accepts the whole
article), and ThesisBuilder's pairing step `_resolve_instruments` already requires a provider
ticker tag or an alias text match before creating an (article, instrument) pair. Every
`instrument_not_subject` analysis passed that mention check — the waste population is pairs where
the instrument is *mentioned* (promiscuous provider tags, listicles tagged with many names,
incidental alias hits in the URL string) but is not the article's *subject*. Mention is checkable
deterministically; subjecthood is not — so the bulk of the reduction must come from a cheap LLM
triage, with only marginal deterministic refinements available.

## Expected Behavior

Before invoking the full thesis-analysis prompt for an (article, instrument) pair, ThesisBuilder
applies a two-part screen. Both parts are in scope for this issue:

1. **Tier 0 — refine the existing deterministic pairing** (`_resolve_instruments`), which already
   enforces mention. Two marginal improvements, not a new mention check:
   - Drop `article.url` from the alias-match text — URL slugs produce incidental matches that
     provider tags and headline/summary matching would not.
   - Optional listicle heuristic behind config (default off until cache-validated): an article
     tagged with more than `N` watchlist instruments and matching none of them by alias in the
     headline is treated as a roundup, and its pairs are persisted with reason code
     `prefiltered_roundup` without any LLM call. This targets the observed waste population
     (listicles/sector roundups) but carries recall risk, so it ships behind the same
     cache-validation gate as tier 1.
2. **Tier 1 — small-LLM triage (the main reduction):** surviving pairs go through a narrow, short-output
   classification call (subjecthood + `content_type` only — no sentiment, thesis, or evidence
   bullets) before the full analysis prompt. Requirements:
   - **Recall-biased by contract:** the prompt instructs "when unsure, pass through". A false
     negative here is amplified by the evidence gate — losing 1 of 3 required articles kills an
     entire card — so the triage must only reject clear non-subjects (listicles, sector roundups,
     incidental mentions). Rejections persist with reason code `triage_not_subject` /
     `triage_not_catalyst` plus the triage output for audit.
   - **Configurable and disableable:** model (`THESIS_BUILDER_TRIAGE_MODEL`, may differ from the
     analysis model), max output tokens, and an enable flag; disabled means tier 0 → full
     analysis directly.
   - **Budget-accounted:** triage tokens count against the daily/run token budgets and API usage
     accounting like any other LLM call.
   - **Cache-validated before rollout:** replayed against the persisted full-prompt analyses
     (LLM cache, 260708-02) to measure recall on pairs that historically returned
     `instrument_is_subject = true`; the measured recall gates enabling it by default.
   - **Live-parity:** regeneration backtests run the same two-tier screen so backtest funnels
     match live funnels.

Related, out of scope here: reordering `_build_prompt` so static rules precede the article
(currently `sort_keys=True` puts the variable `article` key first, defeating provider prompt-prefix
caching), and the tier-2 card-synthesis pass (260709-06).

## Acceptance Criteria

- Replaying a historical window shows a measurable reduction (target: majority) of
  `instrument_not_subject` full-prompt analyses.
- Tier 0 refinements cause **zero** loss of analyses that previously returned
  `instrument_is_subject = true` (URL-match removal validated against the cached population; the
  listicle heuristic stays default-off unless the cache replay shows zero true-subject loss).
  Tier 1's measured recall on that same cached population is reported, and tier 1 ships
  default-disabled unless recall is ≥99% on the available sample.
- Prefiltered and triaged-out pairs are persisted and countable by their reason codes;
  monitoring/funnel numbers still reconcile (articles → pairs → triage → analyses → valid).
- Total token usage per covered window-day drops in a regeneration run over a previously verified
  window (triage tokens included in the accounting).
- Both tiers are configuration-documented in `thesis-builder/configuration.md`; tier 1 is
  independently disableable; regeneration backtests apply the same configuration.

## Test Plan

- Unit tests (tier 0): alias present only in the URL no longer creates a pair; alias in
  headline/summary and ticker-in-tags still pair as today; listicle heuristic — article tagged
  with >N watchlist instruments and no headline alias match → pairs persisted with
  `prefiltered_roundup` and no LLM call; heuristic disabled → current pairing unchanged.
- Unit tests (tier 1): fake triage client — clear non-subject rejected with `triage_not_subject`
  and no full-analysis call; subject pass-through invokes the full prompt; ambiguous fixture
  passes through (recall bias); triage LLM failure falls through to full analysis (fail open for
  triage — the expensive call is the safe default); disabled flag bypasses tier 1 entirely.
- Unit test: prefiltered/triaged pair persists an analysis row with the reason code and the
  triage output; fake full-analysis client asserts zero invocations for rejected pairs.
- Regression test over the cached analyses from consumed windows (LLM cache, 260708-02): tier 0
  drops no historical `instrument_is_subject = true` pair; tier 1 recall measured and asserted
  against its rollout threshold.
- Integration test: end-to-end consume of a news event with two mapped instruments, one mentioned
  and one not — exactly one full-analysis LLM call, two persisted analyses.
- Budget test: triage tokens are debited from the daily/run budget and appear in API usage rows.

## Resolution

Root cause: ThesisBuilder only had a mention-level pairing gate before the full analysis prompt.
Provider ticker tags and alias hits were enough to invoke full analysis, and aliases were matched
against URL slugs as well as headline/summary text. The expensive prompt then performed the actual
subjecthood/content-type rejection.

Implemented on 2026-07-09:

- Removed URL slugs from deterministic alias matching while preserving provider ticker tags and
  headline/summary alias matches.
- Added an optional deterministic roundup prefilter
  (`THESIS_BUILDER_LISTICLE_PREFILTER_ENABLED`, default `false`) that persists tagged roundup pairs
  as `prefiltered_roundup` without an LLM call.
- Added optional recall-biased small-LLM triage
  (`THESIS_BUILDER_TRIAGE_ENABLED`, default `false`) before full analysis. Clear rejects persist as
  `triage_not_subject` or `triage_not_catalyst`; ambiguous cases and triage failures pass through
  to the full prompt.
- Threaded the same configured behavior through live processing, historical reprocess, and
  regeneration backtests. Regeneration config snapshots now include the prefilter/triage settings.
- Updated ThesisBuilder configuration and behavior docs.

Verification:

- `uv run pytest tests/product_components/thesis_builder/test_service.py tests/product_components/thesis_builder/test_llm_client.py tests/product_components/thesis_builder/test_settings.py tests/product_components/thesis_builder/test_regeneration.py tests/product_components/backtester/test_backtester_regeneration.py`
  passed (`39 passed`).

Remaining risk:

- Triage remains default-disabled until a replay over cached analyses validates recall on historical
  `instrument_is_subject=true` pairs. ThesisBuilder now debits triage tokens against the analyzer
  budget and persists them on triage-rejected analysis rows; the broader shared API-usage ledger for
  ThesisBuilder LLM calls is still a separate instrumentation gap because full-analysis LLM calls did
  not previously write those rows either.
