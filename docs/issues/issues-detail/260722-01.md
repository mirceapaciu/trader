# 260722-01 Zero-overlap story verification fragments paraphrased coverage of the same event

## Problem Statement

ThesisBuilder treats zero surviving story-token overlap as conclusive proof that an incoming
article and an existing evidence window describe different underlying events. In
`_verify_story_assignment_target`, `overlap == 0` deterministically changes an LLM-selected
`window:<id>` or `card:<id>` target to `new_story` with
`verification_reason_code='story_text_mismatch'`. The semantic same-event check is invoked only
when exactly one token overlaps.

Zero lexical overlap is not evidence of different event identity. Two outlets can describe the
same announcement with disjoint vocabulary, especially after ThesisBuilder removes the subject
company and generic domain terms such as `profit`, `revenue`, `sales`, `quarter`, and `guidance`.
The deterministic verifier can therefore overrule a correct semantic assignment using weaker
evidence, fragmenting one event across multiple collecting windows and delaying or preventing
card creation.

This is a focused follow-up to resolved issue `260716-01`. That issue identified both
over-matching and under-linking in the bag-of-words verifier, but its final three-band fix sends
only the single-token band to semantic confirmation. The zero-token band remains an
unconditional downgrade.

The decisive assignment row is analysis 2629:

```text

```

The assignment model had selected the existing AT&T Q2-results window. The verifier removed
the subject company and generic earnings-domain vocabulary, leaving disjoint token sets:

- Window 309 retained terms such as `fiber`, `postpaid`, `service`, `investment-led`, and
  `adds`.
- The incoming article retained terms such as `earnings`, `beat`, `expectations`, `cash`,
  `flow`, and `rises`.

Because the overlap was empty, the verifier did not call `confirm_same_event`. It forced
`new_story` and created window 310 even though both articles covered the same released AT&T Q2
earnings occurrence.

Blast radius:

- Window 309 remains `collecting` with only analysis 2626 and never reaches its required
  evidence count of three.
- Window 310 contains analyses `[2629, 2631, 2638]`, reaches `satisfied`, and creates the valid
  card at 13:12:38 CEST.
- Correctly merging analysis 2629 into window 309 would preserve the earliest official-results
  evidence and avoid the artificial singleton. With the current three-evidence requirement,
  the card could have satisfied when analysis 2631 completed at approximately 12:55:38 CEST,
  rather than waiting for analysis 2638 at 13:12:38 CEST.

This finding is a `missed_match` with `card_minted` blast radius: the final card exists, but the
same event was fragmented and the earlier evidence was stranded outside it.

## Root Cause

The verifier assigns decision authority to lexical absence:

```text
overlap == 0  -> deterministic new_story
overlap == 1  -> semantic same-event check
overlap >= 2  -> deterministic pass
```

This assumes that zero overlap means "clearly a different story." That assumption is false for
paraphrased coverage. Token overlap can be a useful candidate-ranking and confidence signal,
but absence of overlap cannot establish event incompatibility.

The architecture also lets a weaker deterministic heuristic veto the stronger semantic
assignment without contradictory structured evidence. A deterministic veto should require an
actual incompatibility, such as different fiscal periods, different announcement dates,
different counterparties/deals, or preview versus released results—not merely different words.

## Expected Behavior

Zero distinctive-token overlap means `lexically_inconclusive`, not `different_event`.

For an assignment that selects an existing window or card:

1. Strong distinctive overlap may remain a cheap positive signal.
2. Zero or one distinctive shared token enters semantic same-event confirmation when that
   confirmation is enabled and available.
3. `same_event=true` preserves the selected target and records the semantic confirmation.
4. `same_event=false` downgrades to `new_story` with an event-level mismatch reason.
5. If semantic confirmation is unavailable, budget-exhausted, malformed, or fails in transport,
   zero-overlap assignments retain the current safe fallback to `new_story`; the news loop must
   not crash.
6. Explicit structured event incompatibilities may deterministically downgrade without an LLM
   call when such fields are available and reliable.

The change must not loosen story identity to "same ticker" or "same theme." The contract remains
the same underlying announcement, filing, report, deal, or occurrence.

## Acceptance Criteria

- `_verify_story_assignment_target` treats `overlap == 0` as an inconclusive band and invokes
  `event_confirmer` when configured.
- A zero-overlap `same_event=true` result preserves the selected `window:<id>` or `card:<id>` and
  persists `verification_status='passed'` with `verification_details_json.event_check='same'`.
- A zero-overlap `same_event=false` result resolves to `new_story` and persists an event-level
  mismatch reason such as `story_event_mismatch`, with
  `verification_details_json.event_check='different'`.
- A zero-overlap indeterminate result (`None`) remains safely resolved to `new_story` and carries
  enough audit detail to distinguish "lexically inconclusive, semantic check unavailable" from
  a confirmed different event.
- The AT&T analysis-2629 case is added to
  `tests/product_components/thesis_builder/fixtures/story_assignment_corpus.jsonl` as a
  self-contained `missed_match` regression expecting window 309.
- A focused regression test proves that differently worded official-results and
  results-reaction coverage can join the same event window despite zero token overlap.
- Existing zero-overlap different-event corpus cases remain `new_story`, including unrelated
  same-ticker/same-theme articles caught by issue `260715-05`.
- Existing preview-versus-actual-result separation remains intact unless a future explicit
  design change redefines those phases as one story.
- Live processing, reprocessing, and regeneration backtests use the same verification policy;
  any additional LLM usage and cache-key consequences are documented.
- `docs/design/product_components/thesis-builder/behavior.md` and the relevant configuration or
  data-model documentation describe zero overlap as inconclusive and document the fallback and
  audit semantics.

## Remaining Risks and Follow-up

- Sending zero-overlap matches to semantic confirmation increases assignment-model latency and
  token cost. Measure the zero-overlap band frequency before deployment.
- Semantic confirmation can itself be wrong. Corpus replay and persisted event-check outcomes
  remain mandatory; enabling the strong-model synthesis coherence gate is a complementary
  final defense.
- This issue fixes window fragmentation, not evidence independence. Multiple articles derived
  from one press release must not automatically count as independent corroboration; that remains
  governed by deduplication and issue `260709-07`.
- Even after correct merging, the three-evidence threshold imposes latency. A trusted-source
  fast path for authoritative earnings releases would be a separate policy change.

## Resolution

Resolved on 2026-07-23.

- `_verify_story_assignment_target` now treats zero and one surviving distinctive tokens as
  lexically inconclusive and invokes the configured event confirmer for either band.
- A `same_event=true` result preserves the selected existing target and records
  `verification_status=passed` / `event_check=same`; `false` continues to resolve to
  `new_story` with `story_event_mismatch` / `event_check=different`.
- A zero-overlap assignment with no semantic decision now safely resolves to `new_story` with
  `story_event_check_unavailable` / `event_check=unavailable`, so an unavailable LLM cannot
  crash the loop or silently merge evidence.
- Added the self-contained AT&T analysis-2629 missed-match case as corpus case `CS-0074` and
  focused verification-band coverage for semantic same, semantic different, and unavailable
  results.

The remaining cost and semantic-error risks above remain applicable. Live processing,
reprocessing, and regeneration share this repository verifier, so no separate policy path or
cache-key change is required.
