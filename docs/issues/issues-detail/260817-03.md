# 260817-03 Instruct the analysis LLM to select from the active event taxonomy before proposing new values

## Problem Statement

ThesisBuilder asks the full-analysis LLM to return `event_identity`, but the request
contains only the selected `taxonomy_revision`; it does not show the model the canonical
values, family-scoped subtypes, or mapped aliases effective at that revision. The prompt
says to use canonical values without defining them, and the structured-output schema
currently accepts an arbitrary `event_identity` object.

The model therefore invents natural-language synonyms such as `announcement`,
`acquisition`, `earnings_call`, and `earnings guidance`. Normalization correctly retains
unrecognized values as lossless candidates, but synonym-only candidates create noisy
taxonomy gaps and unnecessary operator work.

The model must receive the exact active `EventTaxonomySnapshot` used by normalization. It
must choose an exact canonical value whenever one adequately fits, place values in the
correct taxonomy dimension, and use a separate candidate field only when no canonical
value fits. The change must reduce synonym-only gaps without forcing novel concepts into
an inaccurate existing category.

## Verified Evidence

- `_build_prompt()` currently accepts `taxonomy_revision: int` rather than an
  `EventTaxonomySnapshot` and emits only that integer in the request.
- The prompt instructs the model to use a canonical event family but supplies no list of
  families, subtypes, stages, coverage roles, participant roles, or aliases.
- `_THESIS_ANALYSIS_RESPONSE_FORMAT` defines `event_identity` as an object with
  `additionalProperties: true`; controlled identity fields are not constrained to the
  active taxonomy values.
- `parse_analysis_result()` receives the selected snapshot only after the model response
  is returned, then preserves non-matching values as candidate fields.
- A bounded, read-only Haas query on 2026-08-17 found 83 open taxonomy-gap proposals
  representing 562 occurrences. The sampled representative analyses all recorded
  `provenance.source=full_analysis_llm` and model `gpt-4o-mini`.
- High-frequency Haas proposals include:

  | Dimension | Proposal | Occurrences | Existing intended concept |
  |---|---|---:|---|
  | event stage | `announcement` | 181 | `announced` |
  | coverage role | `announcement` | 113 | usually `primary_announcement` |
  | event stage | `upcoming` | 54 | usually `scheduled` |
  | event stage | `reported` | 29 | usually `announced` or `completed` |
  | event stage | `actual` | 20 | usually `completed` |
  | event family | `earnings_call` | 18 | family `earnings_results`, subtype `earnings_call` |
  | event family | `acquisition` | 12 | `merger_acquisition` |
  | event family | `earnings announcement` | 8 | `earnings_results` plus a coverage role/stage |
  | event family | `dividend announcement` | 7 | family `dividend`, role `primary_announcement` |
  | event family | `partnership` | 7 | `partnership_joint_venture` |

- Representative raw responses also use improvised fields such as `fiscal_period` at the
  top of `event_identity`, showing that the current loose object schema does not reliably
  communicate the intended identity shape.
- `OpenAIThesisClient` already uses the Responses API with JSON-schema Structured
  Outputs, `temperature=0`, and `store=False`. Official OpenAI documentation confirms
  that `gpt-4o-mini` supports Structured Outputs and pinned snapshots:
  <https://developers.openai.com/api/docs/models/gpt-4o-mini>.

## Expected Behavior

### Snapshot-driven prompt

- `ThesisAnalyzer.analyze_article()` selects one immutable `EventTaxonomySnapshot` before
  building the request and passes that same object to prompt construction, response-schema
  construction, and response normalization.
- The full-analysis prompt includes a compact, deterministically ordered taxonomy block
  derived from the selected snapshot, not from hardcoded parallel lists:

  ```json
  {
    "taxonomy_version": "event-taxonomy-v1",
    "taxonomy_revision": 3,
    "canonical_values": {
      "event_family": ["..."],
      "event_stage": ["..."],
      "coverage_role": ["..."],
      "participant_role": ["..."]
    },
    "subtypes_by_family": {
      "earnings_results": ["annual_results", "earnings_call", "..."]
    },
    "aliases": {
      "event_family": {
        "earnings_report": "earnings_results"
      }
    }
  }
  ```

- Canonical values, dimensions, subtype families, and aliases are sorted so identical
  snapshots produce byte-identical prompts and stable analysis cache keys.
- Historical reprocessing and regeneration include the values effective at the explicitly
  selected historical revision, not the latest values.
- Full live analysis checks the latest committed revision between articles as it does
  today; one article keeps the snapshot with which it started.
- Triage, story assignment, and card synthesis receive no redundant taxonomy payload
  unless they independently need to generate controlled taxonomy fields.

### Selection contract given to the model

The prompt must state these rules directly and concisely:

1. Classify the underlying occurrence, not the article's trading interpretation.
2. For each controlled dimension, return an exact canonical token whenever one adequately
   represents the article evidence.
3. Never return an alias or natural-language synonym in a canonical field; resolve it to
   the displayed canonical target.
4. Select an event subtype only from the list scoped to the selected event family.
5. Keep dimensions separate: event family describes what occurred; event stage describes
   lifecycle state; coverage role describes how this article covers the occurrence; and
   participant role describes an entity's relationship to it.
6. If no canonical value adequately fits, return `null` in the canonical field and place
   one concise, lossless proposed token in the corresponding `_candidate` field.
7. Do not choose a vaguely related canonical value merely to avoid proposing a candidate.
8. Use canonical `unknown` only where that dimension defines it and the article lacks
   enough evidence; do not use `unknown` to hide a confidently observed novel concept.
9. Canonical fields and their candidate fields are mutually exclusive.

Examples should explicitly cover the observed Haas mistakes:

- acquisition announcement -> family `merger_acquisition`, stage `announced`, coverage
  role `primary_announcement`;
- scheduled earnings call -> family `earnings_results`, subtype `earnings_call`, stage
  `scheduled`, coverage role `primary_announcement`;
- earnings preview -> family `earnings_results`, stage `scheduled`, coverage role
  `preview`;
- quarterly results report -> family `earnings_results`, subtype `quarterly_results`,
  coverage role `results_report`;
- genuinely unsupported event -> canonical family `null` and a lossless
  `event_family_candidate`.

### Snapshot-driven Structured Outputs

- Replace the unconstrained identity object with a strict, explicit event-identity shape
  generated for the selected snapshot.
- Canonical controlled fields accept only `null` or values from the corresponding active
  snapshot list. Candidate fields accept `null` or a bounded string.
- The schema contains explicit subject, participants, period, occurrence, identifiers,
  attributes, and confidence properties; unexpected replacements such as top-level
  `fiscal_period` are rejected by strict schema validation.
- Participant `role` is constrained to the active participant-role values while
  `role_candidate` preserves unsupported roles.
- Event subtype enumeration contains active subtypes, but application normalization still
  enforces the selected family's scope because JSON Schema alone does not replace the
  domain validator.
- If the current client abstraction cannot provide a per-request response format, extend
  the `ThesisLlmClient.analyze()` contract so `ThesisAnalyzer` can pass the
  snapshot-derived format. Do not let the OpenAI adapter query PostgreSQL or independently
  load taxonomy state.
- Refusals, incomplete responses, unsupported schema errors, and malformed outputs follow
  the existing bounded retry/DLQ behavior with actionable error codes.

Structured Outputs constrain the shape and allowed canonical tokens; they do not replace
the candidate contract or semantic evaluation. A syntactically valid forced fit remains
incorrect and must be detected by tests.

### Normalization and provenance

- Normalize the response using the exact snapshot used to construct its prompt and schema.
- Preserve the existing lossless provenance raw response, prompt version, taxonomy
  revision, and analysis model.
- Increment the event-identity prompt version because the model-visible contract changes.
- Existing persisted analyses remain immutable unless processed through an explicitly
  requested reprocess/backfill workflow.
- New synonym-only candidate values continue to be recorded as gaps if they occur; do not
  silently auto-map unexpected output outside the controlled response contract.

### Cost, observability, and caching

- Measure the input-token increase from including the complete active taxonomy and report
  it in the implementation notes. Keep the representation compact and avoid repeated
  display descriptions that provide no classification value.
- The token-budget reservation must include the larger prompt before an API call.
- Emit aggregate metrics for full analyses, candidate fields by dimension, candidate
  occurrences per 100 analyses, invalid family/subtype combinations, input tokens, output
  tokens, latency, and selected taxonomy revision. Do not log API keys or full article
  bodies.
- Prompt/cache identity changes whenever taxonomy content or revision changes and remains
  stable for identical article inputs and identical snapshots.

## Acceptance Criteria

- Full-analysis prompts contain the exact active canonical values, subtype scopes, and
  aliases from the selected `EventTaxonomySnapshot`.
- Prompt construction has no independent hardcoded copy of taxonomy membership.
- Canonical controlled response fields are dynamically constrained to the selected
  snapshot while candidate fields remain available for unsupported concepts.
- The same immutable snapshot instance/revision is used for prompt construction,
  response-format construction, parsing, normalization, and provenance.
- Known synonyms from the Haas corpus resolve to appropriate canonical values and no
  longer create synonym-only candidate fields at the acceptance threshold defined by
  `260817-01`.
- `earnings_call` is returned as an `earnings_results` subtype rather than an event family.
- Coverage role, event stage, event family, subtype, and participant role remain distinct.
- A genuinely novel corpus case remains lossless as a candidate and is not forced into an
  inaccurate canonical value.
- Historical revision analysis receives and records the taxonomy content effective at
  that revision.
- Dynamic operator-accepted values become model-selectable on the next live analysis
  without a process deployment.
- Strict response-schema failures and API failures remain bounded and observable.
- Analysis prompt version and cache behavior are updated deliberately.
- The added taxonomy payload stays within the configured token budget; measured token and
  latency impact is documented.
- ThesisBuilder behavior and configuration documentation describe the model-facing
  taxonomy contract and candidate fallback.

## Test Plan

1. Unit-test that prompt taxonomy content exactly matches a supplied snapshot for every
   dimension, subtype scope, alias, revision, and deterministic ordering.
2. Unit-test that two identical snapshots produce byte-identical prompts and schemas, and
   that a revision/value change changes both the prompt and cache key.
3. Unit-test the dynamic response schema: canonical enums, nullable candidate fields,
   explicit object properties, bounded strings, and no unexpected properties.
4. Unit-test the selection rules and examples in the full-analysis prompt; verify triage
   and unrelated prompts do not receive the taxonomy payload.
5. Use a recording fake client through `ThesisAnalyzer.analyze_article()` to prove that
   the selected snapshot reaches the real prompt and response-format arguments and that
   the same snapshot normalizes the returned identity.
6. Test canonical output produces no taxonomy gaps for every controlled dimension.
7. Test unsupported output preserves the exact normalized candidate and creates the
   expected bounded gap through repository persistence.
8. Test family-scoped subtype validation even when the subtype exists elsewhere in the
   active snapshot.
9. Test a historical revision and the latest revision with different canonical values;
   each request must expose and accept only its selected revision.
10. Test an operator-accepted value becomes available after provider refresh and changes
    the prompt/schema without restarting the process.
11. Run the Haas-derived corpus through the opt-in `llm_eval` suite from `260817-01`, using
    the current prompt as baseline and the snapshot-aware prompt as treatment.
12. Measure canonical accuracy, synonym-gap reduction, wrong-dimension rate, forced-fit
    rate, genuine-candidate retention, repeated-run stability, tokens, and latency.
13. Run a small disposable PostgreSQL/Redis ThesisBuilder smoke path and verify canonical
    cases persist no gap while a genuine novel case persists exactly one gap.
14. Run `uv run pytest -m "not integration"` and the ordinary non-LLM integration suite
    to ensure neither makes paid API calls.

## Dependencies and Scope

- Depends on `260817-02` for a complete, database-authoritative active snapshot. It may be
  developed against the current snapshot interface, but must not ship with a second
  taxonomy authority embedded in the prompt builder.
- `260817-01` supplies the opt-in real-model evaluation corpus and acceptance harness for
  proving this change improves behavior.
- Reuses the lossless candidate and taxonomy-gap behavior from `260723-01` and runtime
  revision loading from `260729-01`.
- This issue does not accept or reject existing taxonomy gaps, rewrite historical
  analyses, change card/trading policy, or migrate the configured model.

## Resolution

- Full-analysis now serializes the immutable selected snapshot, including sorted aliases,
  and provides direct canonical-selection, candidate-fallback, dimension, and common
  mistake examples to the model.
- The OpenAI request receives a snapshot-derived strict response schema: controlled
  fields are nullable enums, candidates are bounded nullable strings, and event identity
  has an explicit closed shape.
- The same snapshot is used for prompt, schema, parsing, and normalization; the updated
  prompt changes cache identity. Event-identity provenance is now `event-identity-v2`.
- Existing lightweight/cache test clients remain compatible while clients supporting the
  extended contract receive the per-request schema.
