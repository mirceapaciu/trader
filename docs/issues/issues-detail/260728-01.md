# 260728-01 Add operator workflow for accepting controlled event-identity values

## Problem Statement

ThesisBuilder now preserves unsupported values from the value-controlled
`event_identity` fields and exposes them through the Monitoring UI taxonomy-gaps view.
The view is read-only. An operator can see a proposal such as
`event_family_candidate="partnership"` or `event_stage_candidate="announcement"`,
but cannot map it to an existing canonical value, accept it as a new canonical value,
or reject it as noise.

This leaves the taxonomy workflow incomplete:

- unsupported values remain permanently open;
- repeated analyses continue to produce the same gap;
- the active taxonomy cannot evolve without manual database or code changes;
- there is no immutable record of who made a classification decision and why;
- affected analyses and evidence windows cannot be reclassified deterministically.

In this issue, "story identity" means the value-controlled `event_identity` fields used
by ThesisBuilder to determine whether articles refer to the same underlying occurrence.
The persisted and API field name remains `event_identity`; this issue must not introduce
a competing `story_identity` contract.

## Verified Evidence

- `GET /api/thesis-builder/taxonomy-gaps` exposes taxonomy gaps to Monitoring UI but
  there is no decision endpoint or command.
- `t_event_taxonomy_decisions` exists for an immutable decision log, but no runtime
  workflow writes decisions through a ThesisBuilder-owned service.
- Production card `c3b8c994-4b7e-5b33-87a7-18ce25595fdf` demonstrated the need for
  reviewable proposals: an analysis returned `partnership` and `announcement`, which
  are not canonical values in their supplied forms.
- Issue `260723-01` defines map, accept, and reject decisions, taxonomy revisions,
  bounded backfill, and immutable published-card behavior, but the operator workflow
  remains unimplemented.

## Scope

### Controlled dimensions

The workflow applies to:

- `event_family`;
- `event_subtype`, scoped to its canonical family;
- `event_stage`;
- `coverage_role`;
- `participant_role`;
- controlled family-specific attributes added to the taxonomy registry.

Free-form evidence, identifiers, raw participant names, provenance, and uncontrolled
attributes must remain outside this workflow.

### Supported decisions

An authorized operator can make exactly one of these decisions for an open gap:

1. **Map to existing**
   - Select an active canonical value in the same dimension.
   - For a subtype, restrict choices to the selected/known event family.
   - Store the proposal as an immutable alias of the canonical value with the integer
     taxonomy revision from which the mapping becomes effective.
2. **Accept as new**
   - Create a new canonical controlled value.
   - Require canonical value, display name, description, and rationale.
   - Require family scope and identity discriminator policy where the dimension needs
     them.
3. **Reject**
   - Mark the proposal as invalid, irrelevant, or model noise.
   - Require a rationale.

Decisions are immutable. Correcting a bad decision requires a new superseding decision;
existing decision rows are never edited or deleted.

## Ownership and Architecture

- ThesisBuilder owns validation, canonical-value lookup, taxonomy revision allocation,
  decision persistence, alias resolution, and reclassification/backfill.
- Monitoring UI owns presentation, form state, confirmation, and operator-visible
  status. It must not execute SQL against ThesisBuilder-owned tables.
- Monitoring UI submits a command through a ThesisBuilder-owned command/API contract.
- The ThesisBuilder runtime consumes the command, performs the transaction, and exposes
  command status through a read contract.
- The command transport should follow the existing ThesisBuilder reprocess-command
  pattern unless a dedicated component API is introduced first.
- Actor identity must come from authenticated request context or an explicitly
  configured operator identity. The browser must not supply an arbitrary trusted actor
  string.

## Command Contract

### Request

```json
{
  "gap_id": 42,
  "expected_gap_status": "open",
  "action": "map_existing",
  "target": {
    "canonical_value": "partnership_joint_venture"
  },
  "rationale": "Partnership is an established alias for the existing family.",
  "idempotency_key": "operator-generated-stable-key"
}
```

For `accept_new`, `target` additionally contains:

```json
{
  "canonical_value": "new_canonical_value",
  "display_name": "New canonical value",
  "description": "Operator-facing definition.",
  "family_scope": null,
  "identity_discriminators": []
}
```

For `reject`, `target` is omitted.

### Validation

- The gap exists and is still `open`.
- `expected_gap_status` implements optimistic concurrency.
- The action is valid for the dimension.
- Mapping targets an active value in the same dimension and compatible family scope.
- New canonical values use normalized snake_case, are length-bounded, and do not
  collide with active values or aliases.
- The rationale is non-blank and length-bounded.
- The idempotency key prevents duplicate decisions and duplicate version increments.
- Raw proposals are data only; they never become SQL identifiers, routes, or executable
  code.

### Result and status

Command submission returns `202 Accepted` with a command ID. A read endpoint exposes:

- `accepted`, `running`, `completed`, or `failed`;
- the gap ID and requested action;
- resulting integer taxonomy revision when completed;
- bounded error code and operator-safe message when failed;
- backfill status and affected-row counts.

## Simple Taxonomy Revision Semantics

Use one monotonically increasing positive integer named `taxonomy_revision`.

- The initial controlled taxonomy has revision `1`.
- Each successful map, accept, or reject decision increments the active revision exactly
  once.
- Canonical values, aliases, and decisions record `effective_from_revision`.
- An optional `effective_to_revision` is used only when a later immutable decision
  supersedes a value or alias.
- Each normalized analysis records the exact `taxonomy_revision` it used.
- Normal live processing always uses the latest committed revision.
- Exact replay requests may load the taxonomy as it existed at a specified earlier
  revision.

Do not introduce semantic versions, named releases, parallel taxonomy branches, or
copies of the complete taxonomy for every revision. ThesisBuilder reconstructs a
revision from the immutable value, alias, and decision records whose effective revision
range includes the requested integer.

For a successful decision, ThesisBuilder performs one transaction that:

1. locks and revalidates the open gap;
2. inserts the immutable decision row;
3. inserts or updates the taxonomy value/alias record as required;
4. marks the gap `mapped`, `accepted`, or `rejected` with structured resolution data;
5. increments the single active taxonomy revision exactly once;
6. records an idempotent backfill job referencing the decision and resulting revision.

The active taxonomy revision changes only when the decision transaction commits.
Concurrent decisions against the same gap produce one winner; stale commands fail with
`taxonomy_gap_conflict`.

Runtime normalization must resolve active aliases and accepted canonical values from a
ThesisBuilder taxonomy snapshot at the requested integer revision. It must not require a
code deployment to use an accepted value.

## Backfill and Historical Behavior

- Backfill is bounded, resumable, idempotent, and auditable.
- It re-normalizes affected `t_news_analyses.event_identity_json` values using the
  decision and new taxonomy revision.
- Open evidence windows may be updated only through explicit ThesisBuilder policy with
  an audit record.
- Published thesis cards remain immutable.
- Historical cards may display an audit-only "newer taxonomy classification available"
  annotation, but are not rewritten or republished.
- Reprocessing/regeneration may create new cards under the new taxonomy through the
  existing explicit workflows.

## Monitoring UI Specification

### Taxonomy gaps list

Add these capabilities to the existing Taxonomy Gaps panel:

- filter by dimension, status, and first/last-seen range;
- sort by occurrence count and last seen;
- display proposal, raw value, dimension, family scope, occurrence count, first/last
  seen, and representative analyses/headlines;
- distinguish open, command pending, mapped, accepted, rejected, and failed states;
- refresh command state without losing filters or selection.

### Gap detail drawer

Selecting a row opens a detail drawer containing:

- the proposal and normalized form;
- dimension and family scope;
- representative analyses with links to analysis detail;
- current canonical values valid for that dimension/scope;
- occurrence history;
- previous/superseding decisions where applicable;
- one action selector: **Map to existing**, **Accept as new**, or **Reject**.

### Forms

**Map to existing**

- searchable canonical-value selector;
- target description and scope preview;
- required rationale.

**Accept as new**

- canonical value with normalized preview;
- display name;
- description;
- family scope where applicable;
- identity discriminator configuration where applicable;
- required rationale.

**Reject**

- required rationale;
- optional controlled rejection reason.

### Confirmation and feedback

- Show a confirmation dialog summarizing proposal, action, target, and consequences.
- Disable duplicate submissions while a command is pending.
- On conflict, reload the gap and explain that another operator already decided it.
- On success, show the new integer taxonomy revision and backfill status.
- Do not optimistically mark a decision complete before ThesisBuilder confirms it.
- Keyboard navigation, focus management, labels, and error summaries must be accessible.

## API Surface

Names are illustrative; the implementation may use equivalent ThesisBuilder-owned
contracts:

- `GET /api/thesis-builder/taxonomy-gaps`
- `GET /api/thesis-builder/taxonomy-values?dimension=...&family_scope=...`
- `GET /api/thesis-builder/taxonomy-gaps/{gap_id}`
- `POST /api/thesis-builder/taxonomy-decisions`
- `GET /api/thesis-builder/taxonomy-decisions/{command_id}`

Mutation endpoints enqueue/submit ThesisBuilder commands. Monitoring UI adapters must
not directly update `t_event_taxonomy_values`, `t_event_taxonomy_gaps`, or
`t_event_taxonomy_decisions`.

## Expected Behavior

- Controlled canonical values remain deterministic for story grouping and reporting.
- Previously unknown input remains lossless and visible.
- Operators can evolve the taxonomy without source-code edits or database access.
- Every decision is authorized, idempotent, tied to one revision, and auditable.
- New analyses use the latest committed taxonomy revision and aliases.
- Incomplete taxonomy never rejects an otherwise valid analysis.

## Acceptance Criteria

- An authorized user can map an open proposal to an existing active value from the UI.
- An authorized user can accept a proposal as a new canonical value from the UI.
- An authorized user can reject a proposal from the UI.
- All actions require rationale and explicit confirmation.
- ThesisBuilder, not Monitoring UI, validates and persists decisions.
- Each successful action creates one immutable decision row and increments the taxonomy
  revision exactly once.
- Duplicate idempotency keys do not duplicate decisions or versions.
- Concurrent decisions on one gap are conflict-safe.
- Canonical selectors are dimension- and family-scope-aware.
- Accepted values and mapped aliases are used by subsequent normalization without a
  deployment.
- Failed commands remain visible with actionable, non-secret error information.
- Backfill is bounded, resumable, idempotent, and never mutates published cards.
- UI and API expose command and backfill status.
- Monitoring UI performs no direct ThesisBuilder table writes.
- Documentation identifies `event_identity` as the canonical contract name.

## Risks and Follow-up

- Accepting excessively narrow values can fragment story identity; the UI must show
  existing nearby canonical values before allowing a new one.
- Mapping semantically distinct values can merge unrelated events; representative
  examples and family scope must be visible at decision time.
- Taxonomy changes affect replay comparability; every analysis/cache/regeneration path
  must record the exact integer taxonomy revision.
- Authentication and operator roles may require a separate platform-level issue if the
  Monitoring UI has no trusted identity context when implementation begins.

## Local Implementation Verification

All four child implementations now pass locally against real PostgreSQL and Redis.
An authenticated `accept_new` request returned `202`, completed asynchronously,
activated taxonomy revision `2` for subsequent normalization, and completed a bounded
backfill with one changed row and zero failures. Redis had zero pending commands, and
published-card/evidence-window checksums were unchanged.

The parent remains open until Haas has an authenticated reverse proxy that strips
client-supplied principal headers and the same workflow is exercised there. The
mutation endpoint must remain disabled on Haas until that trusted identity boundary
