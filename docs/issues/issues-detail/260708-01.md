# 260708-01 Token-budget exhaustion in regeneration backtests must be visible, not silent

## Problem Statement

When a regeneration backtest exhausts its LLM token budget mid-window, analysis stops silently:
the remaining articles are never analyzed, no cards can be generated for the uncovered part of the
window, and the run still finishes with `status = 'completed'`. The result presents itself as a
full-window backtest that happens to have few cards, which sends diagnosis in the wrong direction
(article supply, thresholds) instead of the actual cause (the run never saw 40%+ of the window).

Concrete instance: run `bt_2373c76aac62411386f96c0771a20f75` (window 2026-06-15 → 2026-06-26)
exhausted its 500k budget after 348 analyses; the last analyzed article was published 2026-06-22
04:55 — ~40% of the window was never analyzed — yet the run row reads `completed` and
`summary_md` says only "1 closed trades…". See
`docs/verification-runs/260708-bt_2373c76aac62411386f96c0771a20f75.md`.

Today the only signals are:

- an INFO log line (`Regeneration token budget exhausted …`), and
- `summary_json.regeneration.budget_exhausted`, surfaced in the UI solely as a subordinate text
  fragment in the Regeneration panel subtitle — visible only after selecting the run and scrolling
  to that panel, and stating nothing about how much of the window was covered.

The Recent Runs table, the Run Summary header, and the headline metrics are indistinguishable
from a fully covered run.

## Verified Evidence

- `src/product_components/thesis_builder/regeneration.py:116-118, 149-155` — the article loop
  `break`s on `TokenBudgetExhausted`; remaining articles are skipped without any per-run record of
  where coverage stopped.
- `src/product_components/backtester/service.py:162-178` — `budget_exhausted` is buried in
  `summary_json.regeneration`; the run is finalized as a normal success (`status='completed'`).
- `backtester.t_backtest_runs` — has `llm_token_budget_limit` but no columns for tokens actually
  used or the coverage boundary (`analysis stopped at` timestamp); `summary_md` for the run above
  does not mention exhaustion.
- `src/product_components/monitoring_ui/backend/models.py:618-640` — `BacktestRunSummary` (the
  runs-list projection) carries no budget/coverage field, so the list endpoint cannot flag it.
- `src/product_components/monitoring_ui/backend/service.py:1270-1281` — `budget_exhausted` is
  projected only into the run **detail** response.
- `src/product_components/monitoring_ui/frontend/src/backtester/BacktesterTab.tsx:583` — the sole
  UI surfacing: `" · token budget exhausted (window not fully covered)"` appended to the
  Regeneration panel subtitle.
- `src/product_components/monitoring_ui/frontend/src/backtester/BacktesterTab.tsx:446-475`
  (Recent Runs table) and `:548-572` (Run Summary header) — no indication of partial coverage.

## Expected Behavior

A budget-exhausted regeneration run is visibly a **partial-window** run everywhere a user can
encounter it:

1. **Persisted facts (Backtester).** The run row records, as first-class columns (idempotent
   `ADD COLUMN IF NOT EXISTS`): `llm_tokens_used`, `budget_exhausted`, and
   `analysis_coverage_until_at` — the `published_at` of the last article analyzed before the
   budget died (null when coverage is complete). `summary_md` states exhaustion and coverage
   explicitly, e.g. "token budget exhausted: analysis covers 2026-06-15 → 2026-06-22 (55% of
   window)". `RegenerationResult` already carries `budget_exhausted`; it must also carry the
   coverage boundary so the service can persist it.
2. **API (Monitoring UI backend).** `BacktestRunSummary` (runs list) gains
   `budget_exhausted: bool | null` and `analysis_coverage_until_at: datetime | null`, so the list
   endpoint can flag partial runs without fetching each detail. The detail response's
   `BacktestRegenerationStats` additionally carries `llm_tokens_used`, the budget limit, and the
   coverage timestamp/fraction.
3. **UI (Recent Runs table).** Budget-exhausted runs show a warning chip next to the status chip
   (e.g. `partial` in warning styling) with a tooltip/subtext giving the covered range. The
   status enum itself is unchanged (`completed` remains `completed` — the simulation over the
   covered portion is valid).
4. **UI (Run Summary panel).** The header line for a budget-exhausted run shows the same warning
   inline (e.g. "completed · ⚠ token budget exhausted — analyzed through 2026-06-22, 55% of
   window") so it cannot be missed even if the Regeneration panel is below the fold.
5. **UI (Regeneration panel).** Keeps its note, upgraded from subtitle text to a visible warning
   style, and adds tiles for tokens used vs budget and window coverage.

Out of scope (separate concerns): raising the default budget, cheaper pre-filtering of
`instrument_not_subject` articles, and any change to how the budget is enforced.

## Acceptance Criteria

- Re-running a regeneration backtest that exhausts its budget produces a run row with
  `budget_exhausted = true`, `llm_tokens_used` ≈ the budget, and `analysis_coverage_until_at`
  equal to the last analyzed article's `published_at`; a run that completes its window has
  `budget_exhausted = false` and null coverage boundary.
- `summary_md` for an exhausted run names the covered range and coverage share.
- `GET /api/backtests` (runs list) exposes the flag and coverage timestamp for each run;
  `GET /api/backtests/{run_id}` exposes tokens used, budget limit, and coverage.
- In the UI, an exhausted run is distinguishable from a complete one in **both** the Recent Runs
  table and the Run Summary header without opening the Regeneration panel.
- Schema change is idempotent; pre-existing run rows (null new columns) render unchanged, with no
  false "partial" flags.
- Replay-mode runs (no LLM usage) never show the warning.

## Test Plan

- Unit tests (`tests/product_components/`, fakes, no external deps):
  - `RegenerationRunner` with a fake analyzer that raises `TokenBudgetExhausted` mid-stream →
    result carries `budget_exhausted = true` and the correct coverage boundary; without
    exhaustion → `false`/null.
  - Backtester service persists the three new run-row fields and the enriched `summary_md` in
    both cases.
  - Monitoring UI backend projection: run row with/without the new columns → list and detail
    models populate flag, tokens, and coverage correctly (nulls for legacy rows and replay runs).
- Frontend (Vitest): Recent Runs row and Run Summary header render the warning when
  `budget_exhausted` is true; no warning for false/null; Regeneration panel shows tokens-used and
  coverage tiles.
- Schema bootstrap test: re-running `db/schema.sql` on an existing database succeeds.
- End-to-end: one regeneration run with a deliberately tiny token budget over a real window;
  verify the warning chip in the runs list, the header note, and the persisted columns.
