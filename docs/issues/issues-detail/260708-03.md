# 260708-03 Historize live market-context snapshots so regeneration can replay the exact context live analyses saw

## Problem Statement

Live ThesisBuilder analyses and regeneration backtests of the same articles see different market
context, and the live version is unrecoverable after the fact.

The live pipeline feeds the LLM a market-context snapshot that includes a real-time quote
(`current_price`, intraday `return_1d`). That snapshot is stored in
`market_data.t_market_context_snapshots` as **one mutable "now" row per instrument** — the
primary key is `(ticker, exchange_code)` and every refresh upserts over the previous values. Once
overwritten, "what was the quote for AAPL at Tuesday 10:03" exists nowhere in that table.

The regeneration backtester therefore cannot reconstruct live context. It falls back to the
conservative option: rebuild context from daily bars only (`quote=None`), using only bars closed
at or before analysis time (no look-ahead). This is the correct trade-off — look-ahead silently
inflates backtest results, while missing information degrades fidelity in a known direction — but
it leaves a real gap: regeneration's LLM cannot apply "this move is already priced in" reasoning,
so regeneration likely **over-generates** cards on news the live pipeline would have tempered.

This issue proposes changing snapshot storage semantics from "one mutable now-row per instrument"
to "immutable observations at points in time" (append-only history), so that future backtest
windows can replay the exact context live analyses saw.

## Verified Evidence

- `src/product_components/market_data/db/schema.sql:98-122` — `t_market_context_snapshots` has
  `PRIMARY KEY (ticker, exchange_code)`: one row per instrument, no history.
- `src/product_components/market_data/storage_adapter.py:354-407` — `upsert_context_snapshot`
  does `ON CONFLICT (ticker, exchange_code) DO UPDATE`, overwriting all fields including `as_of`
  and `current_price` on every refresh.
- `src/product_components/backtester/regeneration.py:173-197` — regeneration rebuilds context
  from stored daily bars with `quote=None`; the docstring states this is deliberate (no
  look-ahead, no live quote available historically).
- `src/product_components/thesis_builder/regeneration.py:137-190` and the live service path —
  each analysis persists the `market_context_snapshot` it saw alongside the analysis row. This is
  already a partial historization: exact snapshots exist, but only at the moments an analysis
  actually ran, only for the instruments analyzed.
- The daily-bars part of a snapshot is reconstructable later (bars are stored historically, which
  is why the backtester can rebuild that part at all); it is only the quote-derived fields that
  are one-shot observations lost on overwrite.

## Why this makes sense

- **Exact replayability going forward.** For windows after historization ships, a same-config
  regeneration could feed the LLM the very snapshot live saw, eliminating the live-vs-backtest
  context divergence instead of approximating it.
- **Cheap and low-risk to write.** An append-only insert (or a parallel history table) alongside
  the existing upsert; no live read path changes. The "latest row" consumers keep working.
- **Enables measurement.** A snapshot history makes it possible to quantify how often and how far
  intraday context diverges from bar-only context, feeding the decision in the open questions
  below.

## Why this may NOT be worth doing

- **Forward-only.** It fixes nothing for any window before it ships. Past windows remain
  bar-only forever.
- **The value is unmeasured.** If the intraday quote barely changes LLM judgments, historization
  adds storage and lookup complexity for nothing — and the cheaper fix is the opposite one:
  drop the quote from the **live** prompt too, making live and backtest context identical by
  construction and dissolving the gap entirely.
- **A competing alternative works retroactively.** Historical intraday bars (1m/5m) can be
  fetched from IB after the fact — the bar-coverage schema already supports intraday intervals
  (`schema.sql:94-95`). Approximating the quote as the last intraday bar close at or before
  analysis time closes most of the gap **including for past windows**, without new storage
  semantics. If that is good enough, historization is redundant.
- **Partial coverage even when shipped.** Snapshots exist at refresh cadence for watchlisted
  instruments. A regeneration with a different `card_delay_seconds`, or over instruments added to
  the watchlist later, still finds no matching snapshot and needs the bar-only fallback — so the
  fidelity gap narrows but does not close, and runs mix two fidelity levels.
- **Unbounded growth.** Per-refresh, per-instrument rows accumulate indefinitely without a
  retention policy.
- **The per-analysis snapshots may already suffice.** Live analyses persist their exact snapshot
  today. For same-timing regeneration and for the measurement question, that record — at exactly
  the moments that matter — may make a general snapshot history unnecessary.

## Open Questions (gate the implementation)

1. **Does the intraday quote actually change LLM outputs?** Measure first: regenerate a window
   where live also ran (same config) and diff analyses per article×instrument against the live
   rows, and/or A/B a sample of analyses with and without the quote fields. If the effect is
   negligible, the right resolution of this issue is *"remove the quote from the live prompt"*,
   not historization. This question decides the issue's direction.
2. **Historization vs intraday-bar backfill.** If the quote does matter, is replaying exact live
   snapshots materially better than approximating from backfilled 1m/5m bars — given that the
   bar approach also covers past windows?
3. **Storage design (if historization wins).** Append-only rows in the existing table with
   `as_of` added to the key, vs a separate history table; write cadence (every refresh vs only
   when an analysis consumes the snapshot); retention policy.
4. **Consumption semantics.** How does regeneration select a snapshot for analysis time `t` —
   nearest at-or-before `t` with a staleness cap? What is the fallback when none exists
   (bar-only reconstruction), and should each regenerated analysis record which fidelity level
   its context had?
5. **Interaction with 260708-02 (LLM analysis cache).** None required: historized context changes
   the prompt, so such analyses simply miss the cache — the correct behavior, no coordination
   needed. Recorded here so it is not re-litigated later.

## Expected Behavior

Staged, because Open Question 1 determines whether the storage change should exist at all:

1. **Stage 1 — measure.** Quantify live-vs-regenerated analysis divergence attributable to the
   quote fields (method per Open Question 1) and record the result in this issue.
2. **Stage 2 — decide and implement one of:**
   - *Quote does not matter:* remove quote-derived fields from the analysis prompt on the live
     path; live and backtest context become identical by construction; no historization. Close
     this issue with that outcome documented.
   - *Quote matters:* resolve Open Questions 2-4 and implement the chosen mechanism
     (snapshot historization and/or intraday-bar backfill) so regeneration context for future
     windows includes point-in-time quote information with no look-ahead.

## Acceptance Criteria

- Stage 1's measurement result is recorded in this issue (effect size and sample), and the
  Stage 2 branch taken is justified by it.
- If historization ships: live snapshot writes preserve history (no overwrite of prior
  observations); regeneration for a post-ship window consumes point-in-time snapshots with
  at-or-before-`t` selection (never a snapshot from after analysis time); analyses record their
  context fidelity level; a retention policy exists; existing "latest snapshot" consumers are
  unaffected; schema bootstrap remains idempotent.
- If the quote is dropped instead: live and regeneration prompts for the same
  article×instrument×bars are byte-identical, and the backtester's `quote=None` reconstruction is
  thereby exact rather than approximate.

## Resolution

**Status: resolved — Stage 2 branch taken: "the quote does not matter", quote-provenanced
fields dropped from the analysis prompt. No historization.**

### Stage 1 — measurement (recorded)

Method: diffed **already-persisted** analyses with **zero new LLM spend**. Live analyses
store the exact `market_context_snapshot` (quote-bearing) they saw; regeneration sim
schemas (`sim_bt_*`) store their bar-only (`quote=None`) snapshot. Compared output fields
per article×instrument, plus a live-vs-live control for LLM stochasticity. Live analyses:
5017; regeneration overlap measured against sim `030e39f8…` (the one whose live join had
quotes); n = 154 matched pairs with a live quote; live↔live control n = 183.

Findings (all decisive toward "the quote is inert in this deployment"):

1. **The live quote was almost always absent, and never fresh.** Of 5017 live analyses,
   only **532 (10.6%)** had `current_price`/`return_1d`, and **all 532 were `stale`** —
   `source_status` was `stale` 532×, `missing` 2833×, null 1652×; **zero `fresh`**.
2. **The quote carried no intraday move.** Across all 532 quote-bearing live analyses,
   `return_1d` was **0.0 in 100%** of them (max |return_1d| = 0.0). So the deterministic
   already-priced gate (`_direction_aligned_market_move`, which keys off `return_1d` on the
   stored snapshot) had `return_1d = 0` on both live and backtest — **zero gate divergence
   attributable to the quote**.
3. **Output divergence is bar-driven, not quote-driven.** live-quote vs regen-bar-close:
   suggested_action differs 2.6%, direction 2.6%, content_type 3.3%, is_market_moving 5.2%;
   mean |Δsentiment| 0.038, |Δrelevance| 0.068, |Δconfidence| 0.037. The live↔live control
   (same pair re-analyzed) was action 0.55%, direction 0.0%, |Δconfidence| 0.010. The
   excess over the noise floor tracks the **bar set** used (live's latest daily bar vs the
   regenerator's as-of reconstruction), since `current_price` differed while `return_1d`
   was 0 on both sides — i.e. the difference is the last close, not an intraday quote.

Conclusion: the intraday quote had **no isolable effect** on LLM outputs and **zero effect**
on the deterministic gate. This answers Open Question 1 in the negative and selects the
"quote does not matter" Stage-2 branch. Historization (Stage 2b) is **rejected**: it is
high-complexity, forward-only, and would faithfully replay a quote that carries no signal
and was never fresh.

### Stage 2 — implementation (drop the quote from the prompt)

`thesis_builder/llm_client.py::_prompt_market_context` now excludes the quote-provenanced
snapshot fields (`current_price`, `previous_close`, `return_1d`, `return_5d`, `return_20d`,
`drawdown_from_high_20d`, `source_status`) in addition to the volatile timestamps it
already stripped. Both the live path and the regeneration backtester build the prompt
through this one function, so **the analysis prompt is now byte-identical for identical bar
inputs whether or not a live quote was present** — the live-vs-backtest context divergence
is eliminated by construction, and the backtester's `quote=None` reconstruction is exact
for prompt purposes rather than approximate.

Scope decisions:
- **Storage/UI/gate unchanged.** The full quote-bearing snapshot is still persisted for
  display and audit; the deterministic already-priced gate still reads the stored snapshot.
  No change was needed there because the measurement showed the gate's `return_1d` input is
  already 0 on both paths (finding 2) — the gate never diverged, so touching it would add
  risk for no benefit.
- **Bar-derived features are preserved** in the prompt (`sma_20d`, `sma_50d`, `atr_20d`,
  `volatility_20d`, `volume_ratio_20d`, `recent_high_20d`, `recent_low_20d`), so the LLM
  retains price-level and volatility context; only the quote-provenanced fields are removed.

### Verification

- Unit test `test_build_prompt_identical_for_quote_bearing_and_bar_only_context`
  (`tests/product_components/thesis_builder/test_llm_client.py`) builds context from
  identical bars with a fresh realtime quote (whose `last_price` deliberately differs from
  the last bar close) and with `quote=None`, and asserts the two `_build_prompt` outputs are
  byte-identical while the raw snapshots differ on the quote-provenanced fields. Full
  thesis_builder + backtester suites pass (159 tests).
- The Stage-1 numbers above were computed directly against the live Postgres
  (`thesis_builder.t_news_analyses` and the `sim_bt_*` schemas).

### Remaining risks / follow-ups

- **Forward parity now holds by construction**, so a future *fresh* quote (data type
  `realtime` within max age) would still not leak into the prompt — good. Should a decision
  ever be made to *use* an intraday quote for signal, that would need the historization work
  this issue evaluated and rejected, plus a re-run of the Stage-1 measurement to justify it.
- The live pipeline still fetches quotes (used by other consumers, e.g. the trade
  executor) and still stores them on the snapshot; only their contribution to the analysis
  prompt was removed. Dropping the quote fetch from ThesisBuilder entirely was out of scope.

## Test Plan

- Stage 1 is an analysis task; its deliverable is the recorded measurement, not tests.
- If historization ships:
  - Unit: storage adapter writes are append-only (two refreshes yield two observations);
    point-in-time lookup returns the nearest at-or-before snapshot and never a later one;
    fallback to bar-only reconstruction when no snapshot qualifies.
  - Integration (live Postgres): history round-trip; idempotent schema bootstrap on an existing
    database; "latest" read path still returns the newest observation.
  - End-to-end: regeneration over a post-ship window uses historized snapshots (verify via the
    per-analysis fidelity marker) and produces analyses whose persisted context matches the
    stored observations.
- If the quote is dropped instead: unit test that the live prompt builder emits no quote-derived
  fields and that live and regeneration prompts are byte-identical for identical bar inputs.
