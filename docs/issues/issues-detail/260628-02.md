# 260628-02 Backtest background-thread failures leave the UI stuck on "Running…" forever

## Problem Statement

When a backtest run fails inside the background thread *before* its run row is persisted, the Monitoring UI shows the "Run backtest" button stuck on "Running…" indefinitely, with no error surfaced to the operator. The run never appears in the run list, so the UI has no terminal status to clear its local "active run" state.

Sequence:

1. `POST /api/backtests` returns `202 Accepted` with a `run_id` immediately; the actual run executes in a daemon thread.
2. The frontend stores that `run_id` as `submittedRunId` and disables the button, showing "Running…".
3. `submittedRunId` is only cleared once a run with that id appears in the polled run list with a terminal status (`completed`/`failed`).
4. If the background run throws before `create_run` persists the row (e.g. the regeneration constraint violation in 260628-01, or any failure in `export_cards`/`bootstrap_schema`/param building), no row is ever written. The exception is caught and logged only; nothing is surfaced.
5. The poll for that `run_id` returns `404`, the list never contains it, and the button stays "Running…" until the page is reloaded.

The in-memory `_active_run_id` guard compounds this: it is cleared in the `finally` block of the failed thread, but because the failure is invisible, the operator believes a long run is in progress.

## Verified Evidence

- `src/product_components/monitoring_ui/backend/backtest_runner.py:52-66` — `start_run` starts a daemon thread and returns the `run_id` immediately.
- `src/product_components/monitoring_ui/backend/backtest_runner.py:93-141` — `_run_in_background` wraps the whole run in `try/except Exception: LOGGER.exception(...)`; a failure that occurs before `create_run` persists nothing and surfaces nothing to any API consumer.
- `src/product_components/monitoring_ui/backend/service.py:866-887` — `start_backtest_run` returns `BacktestStartRunResponse(run_id=..., status="running")` synchronously.
- `src/product_components/monitoring_ui/frontend/src/backtester/BacktesterTab.tsx:62-92` — `submittedRunId` is set on mutation success and only cleared by the effect that looks for the run in `runs` with a `RUN_TERMINAL_STATES` status; `effectiveActiveRunId` keeps the button disabled while it is set.
- `logs/monitoring-ui-backend.log` (2026-06-28 17:59:37) — `POST /api/backtests` returned `202`, the background run for `bt_d8e35b6ba4fb489f8c2938fedf6d55ae` failed with a `CheckViolation`, and subsequent `GET /api/backtests/bt_d8e35b6ba4fb489f8c2938fedf6d55ae` polls returned `404 Not Found` — the run never entered the list, so the UI could not clear its state.

## Expected Behavior

A backtest that fails to start must be observable by the operator within a normal poll interval, and the "Run backtest" button must recover without a page reload. Specifically:

- A background failure that occurs before the run row is created should still produce a discoverable, terminal record (e.g. persist a minimal `failed` run row up front, or expose the failure via the start response / a status endpoint), so the polled run list reflects it.
- The frontend should clear `submittedRunId` and re-enable the button when the submitted run resolves to a terminal/failed state, or when a polled lookup for it returns `404` after a grace period, and should display the failure reason.

## Acceptance Criteria

- When a backtest run fails before persistence, the operator sees a failed run (or an inline error tied to the submission) without reloading the page.
- The "Run backtest" button returns to its enabled "Run backtest" label after such a failure within one poll cycle.
- The failure reason (e.g. error code) is surfaced in the UI, not only in the backend log.
- Successful and normally-failing (`finalize_run_failure`) runs continue to behave as today.
- The in-memory `_active_run_id` guard cannot leave the system believing a run is active when none is.

## Test Plan

- Add a backtester runner test asserting that a failure raised before `create_run` results in a discoverable terminal outcome (persisted `failed` row or surfaced status), not a silent log-only failure.
- Add a frontend test (`BacktesterTab.test.tsx`) asserting that when the submitted run resolves to `failed` (or a `404` after the grace period), the button re-enables and an error is shown.
- `uv run pytest tests/product_components/monitoring_ui -q` passes.
- `npm test` in `src/product_components/monitoring_ui/frontend` passes.

## Root Cause

The start flow is fire-and-forget: the HTTP layer returns `202` before the run is durably recorded, and the only place a run becomes visible is the polled list, which is populated by `create_run`. Failures upstream of `create_run` therefore have no representation anywhere except the backend log, and the frontend's "active run" state has no terminal signal to clear against, so it latches on "Running…".
