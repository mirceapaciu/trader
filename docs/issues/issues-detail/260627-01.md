# 260627-01 Move thesis reprocessing out of Monitoring UI into ThesisBuilder via Redis command stream

## Problem Statement

The Monitoring UI backend runs `ThesisBuilderReprocessor` in-process — making OpenAI LLM calls, writing directly to ThesisBuilder-owned Postgres tables, and hardcoding ThesisBuilder configuration values. This has four concrete consequences:

1. The UI backend needs `OPENAI_API_KEY` and `LLM_MODEL` (issue 260626-02), which are ThesisBuilder's concern.
2. The reprocess blocks the HTTP response thread for the duration of up to 200 sequential LLM calls, which can take several minutes.
3. The UI reprocessor can race with the live ThesisBuilder consumer on the same evidence windows if both run concurrently.
4. ThesisBuilder configuration values (`min_confidence`, `min_relevance`, `risk_max_loss_usd`, `default_time_horizon`, `max_evidence_age_minutes`, `required_evidence_count`) are hardcoded in the UI service rather than owned by ThesisBuilder settings.

## Verified Evidence

- `src/product_components/monitoring_ui/backend/service.py:504-542` — `reprocess_thesis` instantiates `ThesisAnalyzer`, `OpenAIThesisClient`, `PostgresThesisBuilderRepository`, and `ThesisBuilderReprocessor` directly and calls `reprocessor.reprocess()` synchronously inside the HTTP handler.
- `src/product_components/monitoring_ui/backend/settings.py:38-39` — `openai_api_key` and `llm_model` are required fields on `MonitoringUiSettings` solely to support this call path.
- `src/product_components/monitoring_ui/backend/service.py:529-534` — six ThesisBuilder configuration values are hardcoded in the UI service.
- `src/product_components/thesis_builder/redis_io.py:76` — `RedisThesisBuilderIo` already exists and owns the ThesisBuilder Redis connection; a reprocess command stream can follow the same pattern.

## Expected Behavior

The Monitoring UI backend should publish a reprocess command to a ThesisBuilder-owned Redis stream. ThesisBuilder should consume that command and run the reprocess in a background thread so the live news consumer loop continues processing without interruption. ThesisBuilder should persist the result so the UI can poll for it. The UI should return an accepted response immediately rather than blocking until the reprocess finishes.

The reprocess runs in a background thread within the ThesisBuilder process. This is safe because `reprocess_run_id` already namespaces reprocess evidence windows separately from live-consumer windows (`reprocess_run_id = NULL`), so concurrent DB writes do not collide.

## Acceptance Criteria

- `src/product_components/monitoring_ui/backend/service.py` imports nothing from `src.product_components.thesis_builder`.
- `MonitoringUiSettings` no longer contains `openai_api_key` or `llm_model`.
- `POST /api/thesis-builder/reprocess` returns immediately with a `run_id` and a `status: accepted` field; it does not block until the reprocess finishes.
- ThesisBuilder owns a new Redis stream (e.g. `reprocess_command_queue`) and a new polling endpoint or DB-backed status table that the UI can query for run completion and result counts.
- ThesisBuilder reads reprocess configuration (`min_confidence`, `min_relevance`, `required_evidence_count`, etc.) from its own `ThesisBuilderSettings`, not from values supplied by the UI.
- The UI exposes a status-polling endpoint (e.g. `GET /api/thesis-builder/reprocess/{run_id}`) backed by a ThesisBuilder-owned read adapter.
- The reprocess runs in a background thread; the live news consumer loop is not paused or blocked while a reprocess is in progress.
- A concurrency guard in ThesisBuilder prevents a new reprocess run from starting while one is already in progress.
- Existing frontend behaviour (submit reprocess, display result counts) works against the new async flow.

## Root Cause

The reprocess feature was implemented by wiring the existing `ThesisBuilderReprocessor` directly into the UI service layer as a shortcut. No ThesisBuilder-owned command channel or async result store existed at the time, so the synchronous in-process approach was taken instead.

## Resolution

Resolved (verified 2026-07-09). Reprocessing now runs asynchronously inside the ThesisBuilder process, commanded over a ThesisBuilder-owned Redis stream:

- ThesisBuilder owns the `reprocess_command_queue` stream (`ThesisBuilderSettings.reprocess_command_queue`) and a dedicated consumer group in `redis_io.py` (`read_reprocess_commands` / `ack_reprocess`).
- `src/product_components/thesis_builder/reprocess_gateway.py` provides the component-owned surface: `ThesisReprocessGateway.request_reprocess` inserts an `accepted` run row and publishes the command; a partial unique index (`uq_reprocess_runs_active`) is the hard concurrency guard against overlapping runs.
- The ThesisBuilder service consumes commands and executes the reprocess in a background thread (guarded by a lock), updating the run row to running/completed/failed, so the live news consumer loop keeps processing.
- The Monitoring UI backend publishes via the gateway and returns immediately; run status is polled through a gateway-backed endpoint. `ThesisBuilderReprocessor`, `OpenAIThesisClient`, and `openai_api_key` no longer appear anywhere under `monitoring_ui`, and reprocess configuration comes from `ThesisBuilderSettings`.

Deviation from the original acceptance criteria: the UI still imports ThesisBuilder-owned Python surfaces (`reprocess_gateway`, `ThesisBuilderSettings`) rather than being import-free of the component — consistent with the repo-wide pattern that component boundaries are enforced at the storage/API level via component-owned adapters, not at the Python import level.
