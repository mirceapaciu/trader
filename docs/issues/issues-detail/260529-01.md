# 260529-01 Add NewsFetcher provider cycle status

## Problem Statement

The Monitoring UI used checkpoint updates as a proxy for provider liveness. Empty NewsFetcher cycles do not advance checkpoints, so the UI could show stale liveness even while the fetcher was actively polling.

## Verified Evidence

- `news_fetcher.t_source_checkpoints.updated_at` only changes when a checkpoint advances.
- Empty batches return before checkpoint advancement in the ingestion engine.
- The Monitoring UI read `last_cycle_end_at` from checkpoint `updated_at`.

## Expected Behavior

The NewsFetcher should persist last-cycle telemetry for every provider cycle, including empty cycles and provider failures. The Monitoring UI should use that telemetry for provider liveness.

## Acceptance Criteria

- `news_fetcher.t_provider_cycle_status` exists in the NewsFetcher schema.
- NewsFetcher records one row per source key and updates it every cycle.
- Empty cycles update `last_cycle_finished_at`.
- Monitoring UI provider status reads from `t_provider_cycle_status`.
- Relevant unit tests pass.

## Test Plan

- Run `python -m pytest tests/product_components/news_fetcher tests/product_components/monitoring_ui -q`.

## Resolution

Implemented a provider cycle status table, a Postgres writer in the NewsFetcher storage adapter, service-level cycle status recording, and Monitoring UI provider reads from the new table.

Verification:
- Focused NewsFetcher and Monitoring UI tests passed.
- Local schema was applied and a one-shot Finnhub cycle wrote `news_fetcher.t_provider_cycle_status`.
