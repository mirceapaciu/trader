# 260929-01 Let backtest trades run past the card-selection window through their strategy horizon

## Problem Statement

The Backtester currently uses `window_end_at` for two different purposes: it is the upper bound
of the thesis-card population selected for the run, and it is also the upper bound of historical
market data used to simulate every selected trade. A position that remains open when those bars
end is forcibly closed on the last available bar with `exit_reason = window_end`.

This truncates trades opened near the end of the selected card window even when the strategy on
the thesis card permits a longer holding period. The resulting exit time and realized P&L are
artifacts of the operator's backtest-window selection, not outcomes of the simulated strategy.
It also makes otherwise identical cards behave differently solely because of their position
within the requested window.

The card-selection window and the trade-simulation horizon must be separate. During market-data
warm-up, the Backtester must inspect the selected thesis cards and load price bars through the
last trading day required by each card's strategy/time horizon. A selected trade must then
continue after `window_end_at` until the first applicable strategy exit. Its latest possible exit
is the time exit derived from the thesis card's strategy/time horizon, capped by the last
completed market day available to the run.

## Verified Evidence

- The latest Haas backtest was reported by the operator to contain many trades with
  `exit_reason = window_end`, exposing this behavior in a real run.
- `src/product_components/backtester/engine.py` calls `historical_bars(..., end=params.window_end_at)`
  for the intraday series used to enter and exit each trade. The cache therefore contains no
  post-window bars even when a card's holding horizon extends beyond the selected window.
- `src/product_components/backtester/service.py::_prewarm_market_data` also prefetches only through
  `params.window_end_at`, establishing the same limit before simulation begins.
- `src/product_components/backtester/engine.py::_live_parity_execution_plan` correctly derives
  `time_exit_at` from the filled entry bar, the card's `time_horizon`,
  `TIME_HORIZON_DAYS_MAP`, and the trading calendar.
- `src/product_components/backtester/engine.py::_find_exit` checks stop loss, take profit,
  reversal, and `time_exit_at`, but if the series ends before any of them fires it returns the
  last bar with `ExitReason.WINDOW_END`.
- `tests/product_components/backtester/test_backtester_engine_behaviors.py::test_window_end_exit`
  explicitly locks in the truncating behavior by expecting a distant strategy time stop to be
  replaced by `window_end`.
- `docs/design/product_components/backtester/behavior.md` currently specifies that a position is
  closed at the last available bar with `exit_reason = window_end`; the design therefore requires
  an intentional update, not only a code change.

## Expected Behavior

`window_start_at` and `window_end_at` define which thesis cards/candidates belong to a backtest
run. They do not force-close positions created by those cards.

For each filled trade, the Backtester must:

1. derive a warm-up coverage deadline for every selected thesis card from that card's simulated
   entry time and `time_horizon`, using the trading calendar, and prefetch bars through the last
   required trading day before trade simulation begins;
2. derive the exact strategy exit deadline from the trade's actual fill time and the thesis card's
   `time_horizon`, using the same trading-calendar and `TIME_HORIZON_DAYS_MAP` semantics as
   TradeExecutor;
3. evaluate bars after the card-selection window and continue applying stop-loss, take-profit,
   reversal, and time-stop rules in their existing priority order; and
4. stop no later than the earlier of the strategy exit deadline and the last completed market
   session available when the run starts.

Warm-up may combine requests by instrument, but the combined end boundary must be the latest
card-derived coverage deadline required for that instrument. The global warm-up progress and
coverage result must reflect those extended ranges. Every deadline is capped at the run's captured
last completed market session so warm-up never requests future or incomplete-session bars.

When the strategy deadline is reached, the exit reason is `time_stop`. When the run is executed
before that deadline and the last completed market session is therefore the limiting boundary,
the trade is valued/closed on the last eligible completed bar with a distinct reason such as
`market_data_end`. It must not be labeled `window_end`, because the card-selection window did not
cause the exit. A missing or failed data response before the expected boundary must remain a
market-data coverage failure; it must not be mistaken for the legitimate last market day.

The run must persist enough boundary information to reproduce the result, including the effective
post-window simulation end and the last-completed-session cutoff used by the run. Run details and
the Monitoring UI must clearly distinguish the card-selection window from the execution/valuation
horizon. Existing runs containing `window_end` remain readable for backward compatibility.

Post-window bars are execution data only. They must not admit additional thesis cards, evidence,
or reversal signals outside the selected card population. Fetching should be bounded to the
maximum horizon needed by selected cards rather than extending every historical run to the
present day.

## Acceptance Criteria

- The card population is still selected exclusively by the requested `[window_start_at,
  window_end_at]` semantics; extending market data does not add cards or evidence to the run.
- A trade entered near `window_end_at` can use later bars through its card-derived strategy
  horizon and is not exited merely because `window_end_at` was reached.
- Live-parity time exits continue to use the actual fill time, the card's `time_horizon`,
  `TIME_HORIZON_DAYS_MAP`, and the shared trading calendar. The strategy deadline is not computed
  as elapsed wall-clock days.
- Before simulation begins, market-data warm-up calculates a coverage deadline for every selected
  thesis card from its simulated entry timestamp and card `time_horizon`, then loads bars through
  that horizon's last trading day.
- When several selected cards share an instrument, warm-up may issue one combined request whose
  end is the latest required card-derived deadline for that instrument. It must not use
  `window_end_at` as the market-data end merely because it is the card-selection boundary.
- Market-data prewarming and any fallback per-instrument bar loading use the same derived boundary,
  capped at the latest completed market session as of a run-level captured timestamp.
- The post-window fetch range is bounded by the longest horizon required by the selected card
  population; a backtest over an old window does not fetch bars from that window through today
  when every strategy horizon ends earlier.
- Existing first-touch precedence for stop loss, take profit, reversal, and time stop remains
  unchanged on the extended bar series.
- Reaching the strategy deadline produces `time_stop`. Reaching the last completed market session
  before the strategy deadline produces a distinct, documented terminal reason such as
  `market_data_end`; new runs no longer produce `window_end` solely because the selection window
  ended.
- The last-session cutoff uses the relevant exchange calendar and only completed bars/sessions;
  weekends, holidays, and an incomplete current session do not become artificial exit points.
- Missing expected data before the effective simulation boundary is surfaced as incomplete market
  data with actionable coverage details, rather than silently treated as the last market day.
- Run persistence/API responses expose the original card-selection window and the effective
  simulation/market-data cutoff used for reproducibility. The Monitoring UI labels these concepts
  separately.
- Equity-curve and summary calculations include exits after `window_end_at` without changing the
  selected-card denominator or admitting post-window candidates.
- Historical `window_end` rows remain readable through the repository, API, and UI. Any schema
  evolution is idempotent and backward-compatible.
- Backtester behavior, data-model, configuration, and Monitoring UI design documentation is
  updated to define the two boundaries and terminal-reason semantics.

## Root Cause

The Backtester treated `window_end_at` as both the thesis-card selection boundary and the end of
the price series supplied to every simulated position. Market-data prewarming and the engine's
fallback read both stopped there, and `_find_exit` converted exhaustion of that artificially
truncated series into `window_end`. Fixed-horizon diagnostics, the final equity point, and exposure
calculation repeated the same coupling.

There was also no persisted distinction between the selected-card window, the latest completed
market session known when the run started, and the effective execution-data end derived from the
selected cards.

## Changes Made

- Added run-level `market_data_cutoff_at` and `simulation_end_at` boundaries plus per-instrument
  execution-data ends carried in immutable run parameters.
- Added a trading-calendar operation that captures the latest completed session close once at run
  start, excluding an in-progress session.
- Derived warm-up deadlines from every selected card's ideal/actual timing scenario and thesis-card
  `time_horizon`. Cards sharing an instrument use the latest required deadline for that instrument,
  capped by the captured completed-session cutoff.
- Extended the MarketData prefetch contract to accept per-instrument ends while retaining one
  shared rate limiter and one global progress sequence.
- Made engine fallback reads use the same derived instrument boundary as warm-up. Exit evaluation
  now continues past the card-selection end, uses bar-end semantics at a session close, records
  `time_stop` at the strategy deadline, and records `market_data_end` when the captured completed
  session is the earlier boundary.
- Added an actionable market-data coverage failure when returned bars end before the promised
  execution boundary, rather than silently treating truncated data as a legitimate terminal exit.
- Retained legacy `window_end` enum/schema/API/UI compatibility without producing it merely because
  a new run reaches the card-selection boundary.
- Moved fixed-horizon diagnostic bounds, equity-curve termination, and exposure duration to the
  effective execution-data horizon so post-window trades remain internally consistent.
- Added idempotent schema evolution for the two run boundaries and the `market_data_end` reason,
  including replacement of the existing exit-reason check constraint.
- Exposed both boundaries through the Monitoring API and UI. The UI labels the card-selection
  window, execution-data end, and last completed market session separately and identifies old
  `window_end` outcomes as legacy.
- Updated Backtester and Monitoring UI design documentation for the new boundary semantics.
