# 260615-01 Remove ThesisBuilder direct database access to NewsFetcher

## Problem Statement

ThesisBuilder currently reads NewsFetcher-owned tables directly and also declares a cross-schema foreign key into the `news_fetcher` schema. That violates the component database encapsulation rule and couples ThesisBuilder runtime behavior to NewsFetcher storage internals.

## Verified Evidence

- `src/product_components/thesis_builder/repository.py:57` loads articles from `news_fetcher.t_news_articles`.
- `src/product_components/thesis_builder/repository.py:398` reloads evidence articles from `news_fetcher.t_news_articles`.
- `src/product_components/thesis_builder/db/schema.sql:7` defines `thesis_builder.t_news_analyses.article_id` with `REFERENCES news_fetcher.t_news_articles(id)`.

## Expected Behavior

ThesisBuilder should consume accepted article snapshots from `news_raw_queue` and use a NewsFetcher-owned API for any required rehydration or replay recovery. ThesisBuilder persistence should store copied article ids and audit snapshots without direct reads from or foreign keys into NewsFetcher-owned tables.

## Acceptance Criteria

- ThesisBuilder runtime code does not query `news_fetcher` tables directly.
- ThesisBuilder repositories do not accept `news_schema` as a direct SQL dependency for runtime article reads.
- `thesis_builder` schema no longer declares foreign keys into `news_fetcher`.
- ThesisBuilder uses queue payloads or a NewsFetcher API/adapter for article access.
- ThesisBuilder tests cover article rehydration through the owning component boundary.

## Test Plan

- Run `uv run pytest tests/product_components/thesis_builder -q`.
- Run `uv run pytest tests/integration/test_thesis_builder_integration.py -m integration`.
- Confirm there are no direct `news_fetcher.` table references left in ThesisBuilder runtime code.

## Resolution

Resolved.

### Root Cause

ThesisBuilder was implemented with a repository-level fallback to NewsFetcher storage instead of treating the accepted article event payload as its runtime input contract. The same assumption also leaked into the ThesisBuilder schema through a cross-schema foreign key and into evidence aggregation through a second reload from `news_fetcher.t_news_articles`.

### Steps Taken

- Changed ThesisBuilder message handling to build `NewsArticle` objects directly from the `news_raw_queue` payload instead of loading them from NewsFetcher tables.
- Updated ThesisBuilder persistence to copy the consumed article snapshot into `thesis_builder.t_news_analyses.article_snapshot`.
- Reworked evidence-card assembly to read copied article snapshots from ThesisBuilder-owned analysis rows instead of re-querying NewsFetcher tables.
- Removed the `news_schema` SQL dependency from `PostgresThesisBuilderRepository`.
- Removed the cross-schema foreign key from `thesis_builder.t_news_analyses.article_id`.
- Added `ALTER TABLE ... DROP CONSTRAINT IF EXISTS t_news_analyses_article_id_fkey` so upgraded databases also shed the old NewsFetcher foreign key.
- Updated unit and integration tests so NewsFetcher articles are supplied through queue payloads rather than seeded into `news_fetcher.t_news_articles`.

### Remaining Risks Or Follow-Up

- ThesisBuilder now fails closed with `missing_article_payload` when a queue message does not carry the required article snapshot. A future NewsFetcher-owned rehydration API can provide a recovery path for malformed or legacy messages without reintroducing direct database access.
