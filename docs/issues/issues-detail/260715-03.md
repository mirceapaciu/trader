# 260715-03 Article publication time is treated as event time; recap articles of old events pass every freshness and already-priced gate

## Problem Statement

Every freshness measure in ThesisBuilder keys off `article.published_at` — the time the feed
published the article — and nothing in the pipeline ever establishes when the *reported event*
happened. An article that recaps an old event under a fresh timestamp is therefore
indistinguishable from breaking news, and it defeats both deterministic gates at once:

- The card freshness gate (`repository.py:442-446`) computes evidence age as
  `now - published_at`, so a recap scores as brand-new and `stale_evidence` never fires.
- The already-priced gate (`repository.py:1350-1377`) measures the direction-aligned 1-day
  return / ATR move from the market-context snapshot taken at analysis time. For an event
  several days old the move has already settled, so the aligned return is near zero and the
  gate reads the card as *not yet priced* — the recap looks **less** priced-in than genuinely
  fresh news would.

The analysis prompt requires a "concrete, datable event" for `content_type=news_catalyst`
(`llm_client.py:518`) but never asks for the date, so the model judges datability and throws
the date away. A days-old announcement is still a concrete, datable event, so classification
legitimately passes. The synthesis prompt's "reject stale evidence" instruction is advisory
prose with no signal to act on: the only timestamp it sees is the fresh `published_at`.

Story scoping does not cover this either: it only matches a recap to an existing story if the
original article was ingested when the event happened; a recap of an event the pipeline never
saw enters as a brand-new story, and `dedupe_key` never matches because the recap is a
different URL and text.

Observed instance (2026-07-15): the MU evidence window contains "Micron (MU) To Boost US
Investment, Here's What You Should Know" — published ~2026-07-15 but reporting a 2026-07-09
event ("On July 9, Micron Technology, Inc. (NASDAQ:MU) said that it will boost US investment
to more than $250 billion by 2035"). The event is six days old; the article passes the
freshness gate as zero-age evidence, and any resulting card candidate would also pass the
already-priced gate because the July 9 move no longer shows in the 1-day return.

## Verified Evidence

- `src/product_components/thesis_builder/repository.py:442-446` — card staleness is
  `max(now - published_at)` over selected evidence, against `max_evidence_age_minutes`.
- `src/product_components/thesis_builder/repository.py:407-411` — evidence-window rolling
  retention cutoff likewise uses `published_at` only.
- `src/product_components/thesis_builder/repository.py:1350-1377` — `_already_priced_rejection`
  thresholds the direction-aligned recent return / ATR move at analysis time; a settled
  days-old move passes.
- `src/product_components/thesis_builder/llm_client.py:518-527` — `content_type_rules` demand
  a "concrete, datable event" but no date field exists in `required_json_fields`
  (`llm_client.py:579-599`); the article payload carries only `published_at`
  (`llm_client.py:567-576`, triage: `llm_client.py:633`).
- `src/product_components/thesis_builder/models.py:53-62` — `NewsArticle` carries `headline`,
  `summary`, `published_at`, `fetched_at`; no event-time concept. Repo-wide grep for
  `event_occurred|event_date|recap` in `thesis_builder` returns nothing.
- MU article "Micron (MU) To Boost US Investment, Here's What You Should Know" present in the
  active MU evidence window on 2026-07-15, reporting the July 9 investment announcement.

## Expected Behavior

1. **The full-analysis LLM extracts the event date.** `_build_prompt` gains an optional
   required-output field `event_occurred_at` (ISO 8601 date or datetime, null when the text
   does not date the event) plus event-dating rules: `published_at` is feed publication time,
   not event time; extract the date the reported event actually occurred or was announced from
   the headline/summary text ("On July 9 ..."), resolving relative expressions ("last week",
   "earlier this month") against `published_at`; when the event materially predates
   publication the article is a recap, not fresh news. The triage prompt is unchanged (triage
   is a cheap pass-through gate; the deterministic enforcement happens at window/card level).
2. **Parsing degrades gracefully.** An absent or unparseable `event_occurred_at` degrades to
   null and never fails the whole analysis — same convention as `price_impact_magnitude` /
   `impact_horizon` — so historical/cached responses that predate the field stay parseable.
3. **The value is persisted** on `thesis_builder.t_news_analyses` as a nullable
   `event_occurred_at` column for funnel attribution and offline measurement.
4. **Deterministic gates use an effective evidence timestamp.** Define per analyzed article
   `effective_evidence_at = min(published_at, event_occurred_at)` when the event date is
   present, else `published_at`. Both the evidence-window retention cutoff
   (`repository.py:407-411`) and the card freshness gate (`repository.py:442-446`) measure age
   from `effective_evidence_at`. When the freshness limit is exceeded and the violation only
   exists because of an article's `event_occurred_at` (its `published_at` age alone would have
   passed), the rejection reason code is `stale_event`; otherwise it remains `stale_evidence`.
   Both produce non-executable audit cards, no shared review row, no signal.
5. **No new configuration.** The existing `THESIS_CARD_MAX_EVIDENCE_AGE_MINUTES` and
   `THESIS_BUILDER_EVIDENCE_COLLECTION_MAX_MINUTES` limits apply to the effective timestamp;
   a separate event-age knob is not warranted until measurement says otherwise.
6. **Regeneration parity.** Live processing, reprocess, and regeneration share the prompt
   builders and gate code, so sim funnels stay comparable. As with 260715-02, changing the
   prompt text invalidates `backtester.t_llm_analysis_cache` keys; the first regeneration run
   after deploy re-pays for analyses, which is expected and acceptable.
7. **Monitoring surfaces the new code passively.** `stale_event` appears through the existing
   generic rejection-reason funnel; the `stale_evidence`-specific aggregations in Monitoring UI
   backend are unchanged in this issue. The operator-facing UI label for both codes is `stale`.

Non-goals: anchoring the already-priced return measurement to the event date (with the
~23-hour evidence age ceiling, the 1-day return window and the event-age gate overlap; an
event old enough to have escaped `return_1d` is rejected by the event-age gate first), and any
NewsFetcher change to fetch full article bodies. Note the prompt only sees headline +
summary; date sentences usually sit in the lede, which feed summaries include. If offline
measurement shows dates routinely live only in article bodies, passing a body excerpt through
is a follow-up issue.

## Acceptance Criteria

- The analysis prompt JSON contains the event-dating rules and `event_occurred_at` in
  `required_json_fields`; the response JSON schema accepts a nullable date/datetime; the
  triage prompt is byte-identical to today.
- Replaying the MU recap article (published 2026-07-15, event 2026-07-09) produces an analysis
  row with `event_occurred_at=2026-07-09`, and a card candidate whose evidence includes it is
  rejected `stale_event` with no shared review row and no published signal.
- A same-day article whose text does not date the event yields `event_occurred_at=null` and
  behavior identical to today, including cached historical LLM responses parsing unchanged.
- An article whose event date equals its publication date passes exactly as today (the
  effective timestamp equals `published_at`).
- Counterfactual sim (per the sim-schema workflow): re-running a recent `sim_bt_*` window under
  the new prompt reports (a) the fraction of analyses with a non-null `event_occurred_at`
  materially predating `published_at`, and (b) which previously-valid cards flip to
  `stale_event` — reviewed before production enable.

## Test Plan

  `event_occurred_at` in required fields, triage prompt unchanged; parser tests for valid

- Unit (repository): effective-timestamp gate tests — event older than limit with fresh

- Integration: replay a synthetic MU-style recap (fresh `published_at`, week-old event in the

  signal.
- Counterfactual: regenerate one existing sim window under the new prompt and diff the
  freshness/rejection funnel against the cached baseline.

## Resolution

Root cause: ThesisBuilder treated feed `published_at` as the only evidence timestamp. Full analysis asked the LLM to identify a concrete datable event but did not request or persist the event date, so recaps of old events could look fresh to both the rolling evidence window and the card freshness gate.

Implemented fix:
- Added nullable `event_occurred_at` to `LlmAnalysisResult`, persisted analyses, and `thesis_builder.t_news_analyses`.
- Added full-analysis prompt rules and strict response-schema support for nullable `event_occurred_at`; invalid, absent, or historical cached values degrade to null. The triage prompt remains unchanged.
- Changed evidence-window retention, window timestamps, card freshness metrics, and card evidence snapshots to use `effective_evidence_at = min(published_at, event_occurred_at)` when an event time is available.
- Added `stale_event` for recap-only freshness violations while preserving `stale_evidence` for ordinary old publications.
- Updated Monitoring UI token formatting so both `stale_event` and `stale_evidence` display as operator label `stale`.
- Updated the ThesisBuilder behavior design doc to mark event dating implemented.
