# 261007-01 Reuse historical market-data cache across non-trading periods

Status: resolved

## Problem Statement

Repeated backtests over the same dates fetch historical intraday bars again even though the first
run persisted those bars and recorded the requested range in the market-data coverage ledger. The
cache-validity check compares the first and last stored bar timestamps with the literal requested
calendar bounds. A range beginning or ending outside an exchange session can therefore never pass:
weekends, holidays, pre-market time, after-hours time, and early closes contain no bars by design.

This causes unnecessary provider requests, longer prewarming, and avoidable use of rate-limited or
paid market-data APIs. Stored historical bars and successful coverage records have no application
TTL, so identical completed ranges should remain reusable without another provider call.

## Verified Evidence

- Two completed Haas replay runs used the same card-selection range,
  `2026-08-17T00:00:00Z` through `2026-08-29T23:59:59Z`:
  `bt_6a384f1242194d08bdccadb5bf476aea` and
  `bt_f6e36ddd6e5f4c5b8e6d4a81a1aa08b2`.
- Monitoring UI logs for the later run reported `market data fetched` for all 15 instruments,
  rather than `cached`, despite the earlier run covering the same dates.
- The requested start is outside a trading session and the requested end extends beyond the last
  eligible session bar. Real one-minute bars therefore cannot span the literal request bounds.
- `src/product_components/market_data/service.py::prefetch_historical_bars` loads persisted bars
  and delegates cache validity to `_is_covered` before making a provider request.
- `MarketDataService._is_covered` uses `earliest <= start and latest >= end` whenever any bars are
  present. It consults `t_market_bar_coverage` only when the stored bar list is empty.
- `_fetch_historical_bars` persists bars with upsert semantics and records the requested range in
  `t_market_bar_coverage` after a provider call returns successfully. Neither table defines an
  application-level expiration policy.
- The coverage table is explicitly documented as representing already-fetched ranges that may be
  sparse because of weekends, holidays, or pre-market time, but the current non-empty-bar branch
  bypasses that evidence.

## Expected Behavior

Historical-bar prewarming must distinguish expected non-trading gaps from incomplete provider
responses. After a provider request has completed successfully and its coverage has been persisted,
an identical or contained request for the same instrument, exchange, provider, interval, and
adjustment mode must use the stored bars without another provider call.

The prewarming phase may still run on every backtest to validate availability and report progress.
For a covered range it must report `cached` and proceed immediately to simulation. Missing bars on
weekends, exchange holidays, outside regular session hours, or after an early close must not cause
a refetch.

Coverage must not conceal a genuinely partial response. Provider retrieval must distinguish a
completed response from an interrupted or failed paginated response, and coverage must advance only
for a range known to have completed. Where individual bars are validated, completeness must be
evaluated against the relevant exchange calendar and expected session/bar boundaries rather than
the literal wall-clock start and end.

## Acceptance Criteria

- Repeating a backtest with identical market-data bounds performs no historical-bar provider calls
  for instruments whose matching coverage record already contains the requested range.
- A request wholly contained by an existing covered range is served from PostgreSQL and reports
  `cached` during prewarming.
- Weekend, exchange-holiday, pre-market, after-hours, daylight-saving, and early-close boundaries
  do not make an otherwise covered range appear incomplete.
- Cache identity continues to distinguish ticker, exchange, provider, bar interval, and adjusted
  mode so incompatible data is not reused.
- Extending a request beyond recorded coverage triggers retrieval for missing coverage rather than
  silently treating the larger range as cached.
- Failed, timed-out, or interrupted partial provider responses do not advance coverage through an
  unconfirmed range.
- Sparse but successfully completed responses, including ranges containing no trading sessions,
  can be represented as covered without requiring fabricated bars.
- Existing stored bars remain reusable indefinitely unless an explicit retention or invalidation
  operation removes them; no TTL is introduced by this change.
- Progress and logs clearly distinguish `cached`, `fetched`, and `unavailable` outcomes.
- Relevant MarketData and Backtester design documentation describes the authoritative coverage and
  non-trading-period semantics.

## Implementation Rationale

The root cause was that `MarketDataService._is_covered` treated stored bar endpoints as more
authoritative than a successfully persisted provider-request range. Real bars cannot reach literal
wall-clock bounds across closed sessions, so any non-empty cache spanning those bounds was forced to
refetch forever. At the same time, IBKR pagination converted timeouts and other interrupted walks
into ordinary partial lists, which made it unsafe to trust the coverage ledger unconditionally.

Coverage is now the authoritative completion signal. Provider clients return normally only after
all pages or chunks complete; an interrupted retrieval raises a completion-aware exception carrying
any bars from confirmed pages. MarketData keeps those partial bars but advances coverage only for a
normal, fully completed return. This separates expected market-calendar sparsity from transport
incompleteness without fabricating bars or adding a TTL.

## Changes

- Made persisted coverage authoritative for identical and contained historical-bar requests,
  including sparse and empty ranges, and report such prewarming outcomes as `cached`.
- Fetch only the continuous uncovered extension of an existing coverage interval. Disjoint
  requests include the intervening gap before the interval endpoints are merged.
- Added `adjusted` to the coverage table identity and supplied an idempotent schema upgrade for
  existing installations.
- Added an explicit incomplete-fetch contract for Polygon and IBKR pagination. Completed-page bars
  survive failures, while failed, timed-out, page-limited, unavailable, or unresolved requests do
  not advance coverage.
- Made IBKR continue through empty weekend/holiday chunks instead of treating the first empty chunk
  as the end of history.
- Standardized prewarming progress states as `cached`, `fetched`, or `unavailable`.
- Updated MarketData behavior/data-model documentation and the Backtester warmup contract.
- Added regression coverage for non-trading boundaries, contained and extended ranges, empty
  completed ranges, identity isolation, and interrupted provider pagination.
