# 260716-01 Story-assignment verification is bag-of-words; same-company/same-domain articles about different events still pass on a single generic token

## Problem Statement

The deterministic story-assignment verifier added in 260715-05 and calibrated in commit
`c324d63` (`_verify_story_assignment_target` in `repository.py`) decides "same underlying event"
by **token-set overlap** between the incoming article and the target `story_narrative`: if the
two share ≥1 distinctive token (after excluding the subject instrument's name tokens, a 99-word
generic stoplist, and pure numbers), the match passes; otherwise it downgrades to `new_story`.

Bag-of-words overlap is structurally too weak to express event identity. Two articles about the
**same company** in the **same domain** but describing **different events** routinely share a
single generic-domain token (`cloud`, `network`, `enterprise`, `chip`, `data`, …) that is not
in the stoplist and cannot be added to it without blinding the gate on legitimate stories. On
that single token the verifier passes an off-story match.

This is the residual left by 260715-05's calibration, not a regression of it. 260715-05 raised
the corpus catch rate from ≤8/31 to 28/31; the 3 misses that remain are all single generic-token
overlaps of exactly this shape.

`docs/verification-runs/story-assignment/260716-stage6-replay.md`) leaves 3 cross-story
misassignments passing, each on one generic token:

| corpus case | assignment | ticker | narrative it wrongly joined | article's actual event | sole overlap token |
| --- | --- | --- | --- | --- | --- |
| CS-0004 | 57 | NVDA | Nokia/Nvidia AI-RAN partnership (card e3ba0bbe, **published**) | Saturn Cloud/Lilac GPU network | `network` |
| CS-0021 | 32 | MSFT | Microsoft Frontier $2.5B initiative (card eee8899a, **published**) | 3M/Microsoft Azure optical partnership | `enterprise` |
| CS-0036 | 58 | ORCL | Oracle Japan government-cloud contract (card accdd8e0, **published**) | "Oracle down 60%" valuation piece | `cloud` |

CS-0004 is the original 260715-05 lead defect (assignment 57): the calibrated token verifier
still does not catch it, because the Saturn Cloud article ("GPU **network** provider") and the
Nokia narrative ("AI-native **network** platform") share `network`.

Threshold analysis (in the replay report): requiring ≥2 overlapping tokens catches all 3 but
**breaks a genuinely correct match** — CS-0029 (assignment 46, the real "Apple to spend $30B
with Broadcom" deal → the Apple/Broadcom partnership window), whose only surviving token after
entity exclusion is `apple`. So the ceiling cannot be raised by tightening the same
bag-of-words rule; the correct-match guardrail forbids it.

## Expected Behavior

Pair the cheap deterministic token floor (keep it as the fast pre-filter) with an **event-level
check** that only runs on the ambiguous band — a match that survives on thin overlap (e.g. a
single shared token, or Jaccard below a small threshold). Options, not mutually exclusive:

- **Entity/number corroboration:** require the incoming article and the target narrative to
  share a *second distinct entity* (a counterparty company, product, or specific figure), not
  just the subject company + one domain word. CS-0004 (Saturn/Lilac vs Nokia), CS-0021 (3M vs
  Frontier/Unilever), CS-0036 (valuation vs Japan-government) each fail this — different
  counterparties.
- **LLM confirm-the-event on the thin band only:** a narrow strong-model check asked solely
  "same underlying event, yes/no?" for the small number of matches in the ambiguous overlap
  band, reusing the 260709-06 synthesis infrastructure. Cost is bounded because the token floor
  already resolves the clear cases.

Whichever is chosen, the corpus is the regression gate: the 3 residual rows must flip to
`new_story` and no `correct` row (especially CS-0029) may break.

### Escalation (post-fix pass 260716-97-155): first PUBLISHED cross-story signal

On a heavy news day, this residual produced its first **published** cross-story card. MSFT card
`76df158d` (published) blends two distinct MSFT-bullish-into-earnings events: a "skyrocket after
July 29" earnings-date prediction and an **Evercore price-target hike**, the latter admitted on
the single token `performance` — and doubled via two feeds (compounding 260709-07). Last pass the
residual only reached an already-priced-*rejected* card; now it reaches the executor queue.
Severity for this class is therefore `published_signal`, not just window pollution. Corpus
CS-0061.

**Third facet — counterparty-entity leakage.** The entity exclusion added in the 260715-05
calibration strips only the **subject** instrument's own name tokens. **Counterparty** entity
names still leak: assignment 149 (an NVDA-tagged article about *TSMC's* Arizona investment) passed
into the *TSMC Q2-results* window on the token `tsmc`. Any fix should also exclude prominent
counterparty entities named in the article/narrative, or require a *distinctive non-entity*
shared token, so a shared third-party name can't by itself satisfy the overlap. Corpus CS-0059.

Same pass: 16/16 verifier downgrades were correct and story separation on a multi-story day
worked well (TSMC coverage split cleanly into 3 coherent cards) — the residual is a precision gap
in an otherwise-working gate, not a reason to loosen it.

**Second facet — under-linking.** An earlier pass found the ≥1-token rule also *fragments*
genuinely-related coverage: assignment 89 (TSMC Q2 **results**, "profit jumps 77%") was
downgraded away from the TSMC Q2 **preview** window because results-vocab and expectation-vocab
share no distinctive token. A robust event check should recognize preview↔actual of the same
scheduled event as one story, not two. (Recorded as uncertain, not corpus-frozen.)

## Resolution

Status: resolved on 2026-07-16.

Root cause: the deterministic token-overlap verifier admitted a match on **any** shared token
(`overlap >= 1`). A single shared token is as often incidental — same company, same counterparty,
same sector/theme, different event — as it is genuine, and the corpus proved the two are not
separable by token identity or count (CS-0029 `apple` is a correct single-token match; CS-0059
`tsmc` and CS-0061 `performance` are wrong single-token matches; CS-0066 is a correct match on
*generic* tokens).

Fix: story-assignment verification is now **three-band** (`_verify_story_assignment_target`):

- **overlap == 0** → downgrade to `new_story` (`story_text_mismatch`) — deterministic, unchanged.
- **overlap >= 2** → pass — deterministic, no LLM call.
- **overlap == 1** (the ambiguous band) → consult a cheap LLM **same-event check**
  (`ThesisStoryAssigner.confirm_same_event` → `_STORY_EVENT_RESPONSE_FORMAT`, `{same_event: bool}`
  on `story_assignment_model`). `false` → downgrade with `verification_reason_code =
  'story_event_mismatch'` and `verification_details.event_check = 'different'`; `true` → pass
  (`event_check = 'same'`). The check **fails open** to the prior single-token pass when disabled,
  unsupported, budget-exhausted, or on transport error, so it can never crash the news loop or
  regress below prior behaviour.

Guarded by `THESIS_BUILDER_STORY_EVENT_CHECK_ENABLED` (default true; off in backtests/tests).
Only single-token-overlap assignments (a minority) incur the extra call.

Validation: corpus replay of the band logic with a correct event decision keeps **12/12**
`correct` rows and catches **49/50** cross-story rows (the token floor + event check). The one
residual, CS-0047, is a `>=2`-token same-product-line case (`delivery`/`eats`/`potential`, Uber
Eats appearing in both a partnership and an M&A) that lands in the deterministic auto-pass band;
event-checking the `>=2` band would risk 6 correct rows to catch it, so it is left as a known
limitation. Unit tests: `tests/product_components/thesis_builder/test_story_event_verification.py`
(band routing + `confirm_same_event` fail-safes). `uv run pytest tests/product_components/thesis_builder
tests/product_components/backtester -m "not integration"` → 217 passed.

Remaining risk / follow-up:
- The live catch rate now depends on the LLM's accuracy on the single-token band; the
  `verify-story-assignment` loop measures it via `verification_status='downgraded'` with
  `reason_code='story_event_mismatch'` and audits the resulting decisions.
- Counterparty-entity leakage is now caught by the event check on the single-token band, but a
  `>=2`-token counterparty overlap could still auto-pass (as CS-0047 shows). Excluding prominent
  counterparty entities from the token sets remains a possible deterministic hardening.
- **Boilerplate-token auto-pass (observed live, CS-0071).** The evidence-bullet generator emits
  stock sentiment phrasing ("Positive sentiment around AI infrastructure…") on most narratives,
  so two unrelated same-ticker stories can share `>=2` boilerplate tokens (`around`, `positive`,
  `sentiment`, `indicating`, `potential`) and auto-pass above the event-check band. Assignment
  175 (Palantir/Nvidia partnership → the Nebius bear-case window) did exactly this. Cheap
  deterministic hardening: add these narrative-boilerplate tokens to `_STORY_GENERIC_TOKENS` so
  such matches fall to the event-checked (overlap==1) or downgrade (overlap==0) band. Low risk —
  they carry no story identity — but validate against the corpus so a genuine `>=2` match that
  happens to include one of them isn't pushed below the pass threshold.
- Regeneration/backtest parity: the event check defaults **off** in the backtester
  (`event_check_enabled=False`), so sim funnels apply only the deterministic bands. Enable it
  there if before/after sim comparisons must include the LLM band (re-pays LLM cost).
