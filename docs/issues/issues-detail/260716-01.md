# 260716-01 Story-assignment verification is bag-of-words; same-company/same-domain articles about different events still pass on a single generic token

## Problem Statement

The deterministic story-assignment verifier added in 260715-05 and calibrated in commit
`c324d63` (`_verify_story_assignment_target` in `repository.py`) decides "same underlying event"
by **token-set overlap** between the incoming article and the target `story_narrative`: if the
two share ≥1 distinctive token (after excluding the subject instrument's name tokens, a 99-word
generic stoplist, and pure numbers), the match passes; otherwise it downgrades to `new_story`.

Bag-of-words overlap is structurally too weak to express event identity. Two articles about the
**same company** in the **same domain** but describing **different events** routinely share a
single generic-domain token (`cloud`, `network`, `enterprise`, `chip`, `data`, …) that is not
in the stoplist and cannot be added to it without blinding the gate on legitimate stories. On
that single token the verifier passes an off-story match.

This is the residual left by 260715-05's calibration, not a regression of it. 260715-05 raised
the corpus catch rate from ≤8/31 to 28/31; the 3 misses that remain are all single generic-token
overlaps of exactly this shape.

## Verified Evidence

Corpus replay of the calibrated verifier over the labeled backlog
(`tests/product_components/thesis_builder/fixtures/story_assignment_corpus.jsonl`, 41 rows;
`docs/verification-runs/story-assignment/260716-stage6-replay.md`) leaves 3 cross-story
misassignments passing, each on one generic token:

| corpus case | assignment | ticker | narrative it wrongly joined | article's actual event | sole overlap token |
| --- | --- | --- | --- | --- | --- |
| CS-0004 | 57 | NVDA | Nokia/Nvidia AI-RAN partnership (card e3ba0bbe, **published**) | Saturn Cloud/Lilac GPU network | `network` |
| CS-0021 | 32 | MSFT | Microsoft Frontier $2.5B initiative (card eee8899a, **published**) | 3M/Microsoft Azure optical partnership | `enterprise` |
| CS-0036 | 58 | ORCL | Oracle Japan government-cloud contract (card accdd8e0, **published**) | "Oracle down 60%" valuation piece | `cloud` |

CS-0004 is the original 260715-05 lead defect (assignment 57): the calibrated token verifier
still does not catch it, because the Saturn Cloud article ("GPU **network** provider") and the
Nokia narrative ("AI-native **network** platform") share `network`.

Threshold analysis (in the replay report): requiring ≥2 overlapping tokens catches all 3 but
**breaks a genuinely correct match** — CS-0029 (assignment 46, the real "Apple to spend $30B
with Broadcom" deal → the Apple/Broadcom partnership window), whose only surviving token after
entity exclusion is `apple`. So the ceiling cannot be raised by tightening the same
bag-of-words rule; the correct-match guardrail forbids it.

## Expected Behavior

Pair the cheap deterministic token floor (keep it as the fast pre-filter) with an **event-level
check** that only runs on the ambiguous band — a match that survives on thin overlap (e.g. a
single shared token, or Jaccard below a small threshold). Options, not mutually exclusive:

- **Entity/number corroboration:** require the incoming article and the target narrative to
  share a *second distinct entity* (a counterparty company, product, or specific figure), not
  just the subject company + one domain word. CS-0004 (Saturn/Lilac vs Nokia), CS-0021 (3M vs
  Frontier/Unilever), CS-0036 (valuation vs Japan-government) each fail this — different
  counterparties.
- **LLM confirm-the-event on the thin band only:** a narrow strong-model check asked solely
  "same underlying event, yes/no?" for the small number of matches in the ambiguous overlap
  band, reusing the 260709-06 synthesis infrastructure. Cost is bounded because the token floor
  already resolves the clear cases.

Whichever is chosen, the corpus is the regression gate: the 3 residual rows must flip to
`new_story` and no `correct` row (especially CS-0029) may break.

## Acceptance Criteria

- Replaying the corpus, the 3 residual cases (CS-0004, CS-0021, CS-0036) resolve to `new_story`,
  and all 10 `correct` rows — including the ≥2-token casualty CS-0029 — still resolve to their
  labeled target.
- The added check runs only on the thin-overlap band (clear-overlap matches keep passing on the
  deterministic path; no new per-assignment LLM cost for them).
- Outcome remains queryable per assignment via the existing `verification_status` /
  `verification_reason_code` / `verification_details_json` columns (new reason code if a new
  mechanism rejects).
- With `THESIS_BUILDER_STORY_SCOPING_ENABLED=false`, behavior is unchanged.

## Test Plan

- Unit: an off-story article sharing exactly one generic-domain token with the target narrative
  is rejected by the event-level check; a same-event article sharing one *distinctive* token
  (e.g. a shared counterparty) passes.
- Unit: CS-0029-shaped input (correct match whose only entity token is a shared counterparty)
  passes.
- Corpus replay (committable once corpus rows carry `summary` + full narrative inline — today
  they carry headlines only): assert 31/31 misassigned → `new_story`, 10/10 correct preserved.
- Counterfactual: re-run a recent `sim_bt_*` window with the event-level check on the thin band;
  report how many additional cross-story matches are caught and confirm no correct match is lost.
