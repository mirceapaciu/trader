# 260615-11 Add Monitoring UI watchlist editor with ticker lookup and alias management

## Problem Statement

Monitoring UI does not currently provide an operator workflow for editing the ticker watchlist or completing missing instrument aliases. Operators must manage watchlist membership and alias metadata outside the UI, which makes ticker onboarding slower and increases the chance that news mentioning only company names will not be attributed correctly.

## Verified Evidence

- `src/product_components/monitoring_ui/backend/repository.py:725` loads active watchlist membership for NewsFetcher-related UI state but does not expose a watchlist editing workflow.
- `src/product_components/shared/adapters.py:38` defines the shared instrument registry contract used to supply active instruments and aliases.
- `src/product_components/thesis_builder/service.py:270` resolves instruments from article ticker metadata or alias matches in article text.
- `docs/design/product_components/news-fetcher/news-sources.md:99` documents that reusable instrument names and aliases are part of the attribution model for watchlist news.

## Expected Behavior

Monitoring UI should provide a watchlist-management screen where an operator can:

- View current watchlist tickers and their alias completeness state.
- Add a new watchlist ticker through typeahead lookup that shows suggestions in `ticker:market-code` format.
- Select a suggested instrument and review the alias data that will be stored for that ticker before saving.
- See warnings for existing watchlist tickers that do not have aliases.
- Select a warning to trigger automatic alias discovery for that ticker.
- Manually enter aliases when automatic alias discovery does not return a usable result.

The browser workflow should call the Monitoring UI HTTP API. Monitoring UI backend should delegate external ticker lookup, alias discovery, and result caching to a shared-owned instrument-registry/admin capability rather than calling market-data providers directly from browser code or embedding ad hoc lookup persistence in the UI repository.

## Acceptance Criteria

- Monitoring UI exposes a dedicated watchlist editing screen for shared watchlist membership.
- New ticker entry uses an external lookup source and displays suggestions as `ticker:market-code`.
- Selecting a suggestion shows the alias data that will be added for the ticker before the operator confirms the change.
- Existing watchlist rows with no aliases are clearly flagged with warnings in the UI.
- Selecting a warning attempts automatic alias discovery for that ticker.
- If automatic alias discovery fails or returns incomplete data, the operator can enter aliases manually and save them.
- Browser code performs lookup and save actions only through the Monitoring UI HTTP API.
- Monitoring UI backend delegates external lookup, alias discovery, and cache access to a shared-owned instrument-registry/admin service or adapter.
- Lookup and alias-discovery responses may be cached behind that shared-owned service, but the cache is not the source of truth for watchlist membership or persisted instrument metadata.
- Saved changes update the shared watchlist and shared alias/instrument metadata through a shared-owned admin/API surface rather than ad hoc UI-owned SQL.
- UI and backend validation prevent empty ticker submissions and duplicate watchlist entries for the same `ticker` and `exchange_code`.

## Assumptions

- The issue should specify an external lookup source for ticker suggestions, not a shared-registry-only search.
- External lookup, alias discovery, and any related caching are owned by a shared instrument-registry/admin capability; Monitoring UI backend is the caller, not the owner of provider integration.
- MarketData may contribute reusable normalization utilities, but it is not the owning component for watchlist admin lookup or alias discovery.
- Other runtime components such as ThesisBuilder continue to consume persisted shared instrument/alias data rather than calling the external lookup path during normal operation.
- The issue should stay feature-level and not lock in a specific vendor/API for ticker lookup or alias discovery.
- The workflow targets the shared watchlist and shared instrument registry, not only the NewsFetcher test filter watchlist.

## Root Cause

Monitoring UI only exposed read-only operational dashboards plus NewsFetcher filter-config editing. The shared instrument registry already held canonical watchlist and alias data, but there was no shared-owned admin workflow or UI/API surface for operator-driven watchlist management, external ticker discovery, or alias repair.

## Resolution

- Added a shared-owned instrument-registry admin capability for watchlist list/add/update/deactivate flows, external ticker lookup, alias discovery, and Postgres-backed lookup caching.
- Added Monitoring UI backend endpoints for watchlist listing, lookup, alias discovery, add/update, and soft-disable.
- Added a new top-level Monitoring UI `Watchlist` tab with search, preview, manual add fallback, warning-driven alias repair, and deactivate actions.
- Added shared schema support for instrument lookup cache persistence and updated design docs for the new watchlist workflow and configuration.
- Added backend and frontend tests covering shared adapter behavior, lookup fallback/caching, Monitoring UI delegation, and Watchlist tab rendering.

## Remaining Risks / Follow-up

- Massive is the primary lookup provider and Alpha Vantage is only a best-effort fallback; broader exchange coverage may need a richer fallback source later.
- Alpha Vantage fallback normalization currently only supports the exchange suffixes already relevant to the app's canonical MIC mappings.
- The Watchlist tab tests cover the new UI flow, but broader browser-level integration coverage would still be useful if the workflow grows further.
