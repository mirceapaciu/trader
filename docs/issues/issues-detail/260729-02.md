# 260729-02 Add asynchronous taxonomy-decision commands and trusted actor identity

## Parent Issue

`260728-01` — Add operator workflow for accepting controlled event-identity values.

## Problem Statement

The current taxonomy-decision endpoint executes synchronously inside the Monitoring UI
backend and attributes every action to the placeholder
`configured-monitoring-operator`. It has no accepted/running/completed/failed lifecycle,
no status polling contract, and no trusted user identity.

Deploying this mutation surface would make audit attribution unreliable and couple an
operator HTTP request directly to ThesisBuilder persistence.

## Verified Evidence

- `ThesisTaxonomyDecisionGateway` calls the ThesisBuilder repository synchronously.
- The gateway actor defaults to `configured-monitoring-operator`.
- `POST /api/thesis-builder/taxonomy-decisions` exists, but no corresponding
  `GET .../{command_id}` status endpoint exists.
- ThesisBuilder already has a Redis command-stream pattern for reprocessing that can be
  reused without inventing a second ownership model.

## Expected Behavior

- Monitoring UI submits a ThesisBuilder-owned taxonomy command and receives
  `202 Accepted` with a stable command ID.
- ThesisBuilder consumes and validates the command asynchronously.
- Status transitions are `accepted -> running -> completed|failed`.
- The status response includes bounded error information, resulting taxonomy revision,
  and associated backfill job state.
- Idempotency keys deduplicate submission and execution.
- Optimistic concurrency rejects a decision if the gap is no longer open.
- Audit actor identity comes from trusted authentication context, not browser payload.
- The mutation endpoint remains disabled when trusted actor identity is unavailable.

## Actor Identity Decision

Before enabling the endpoint, select and document one trusted source:

- authenticated Monitoring UI session identity; or
- an authenticated reverse proxy that supplies a verified principal header and strips
  client-provided copies.

A configured shared actor is acceptable only for an explicitly single-operator local
development mode and must be visibly labeled as such. It is not acceptable for Haas.

## Command and Status Contract

- Persist commands durably with command ID, gap ID, action, idempotency key, actor,
  requested timestamp, status, error code, result revision, and backfill job ID.
- Acknowledge the Redis message only after durable command state exists.
- Recover accepted/running commands safely after consumer restart.
- Multiple deliveries must not duplicate decisions or revision increments.
- API conflicts and validation failures use stable operator-safe error codes.

## Acceptance Criteria

- Submission returns `202`, not a synchronous completed decision.
- Status can be polled by command ID.
- Commands survive process restart and Redis redelivery.
- Duplicate idempotency keys return the same command/result.
- Concurrent commands for one gap produce one winner.
- The immutable decision row records the authenticated actor.
- Haas cannot enable mutation with the placeholder actor.
- Monitoring UI performs no direct ThesisBuilder table writes.
- Logs contain command IDs and safe error codes without secrets or raw credentials.

## Test Plan

1. Unit-test command parsing, actor validation, and status transitions.
2. Test idempotent duplicate submission and redelivery.
3. Test optimistic-concurrency conflict.
4. Test consumer restart with accepted and running commands.
5. API-test `202`, status polling, authorization failures, validation errors, and safe
   error responses.
6. Verify the persisted decision actor comes from trusted context.
7. Verify the endpoint is disabled when trusted identity is unavailable.
8. Run Redis integration coverage for command delivery and acknowledgement.

## Dependencies

- `260729-01` must define how a completed decision activates a new runtime taxonomy
  snapshot.

## Resolution

The synchronous gateway and placeholder actor were the root cause. Taxonomy decisions
are now persisted as ThesisBuilder-owned commands before being published to a dedicated
Redis stream. The runtime claims and executes commands with durable
`accepted -> running -> completed|failed` status, idempotent decision execution, stale
command recovery, safe error codes, and a polling endpoint that includes the linked
backfill status.

Monitoring UI mutation is disabled by default. It can be enabled only with an explicit
trusted-proxy principal-header configuration; the request body cannot provide the
actor, and the placeholder actor is rejected.

Remaining operational dependency: Haas must keep mutation disabled until its
authenticated reverse proxy strips client-supplied copies of the configured header.

Runtime verification:

- A trusted-header request returned `202 Accepted` and persisted the authenticated
  actor `runtime.operator@example.test`.
- ThesisBuilder consumed the real Redis command, moved it through
  `accepted -> running -> completed`, and acknowledged the stream message.
- `GET /api/thesis-builder/taxonomy-decisions/{command_id}` returned `200` with
  revision `2`, completed backfill state, and no command error.
- The Redis consumer group reported zero pending messages.
- The combined ThesisBuilder, Monitoring UI backend, Backtester, and taxonomy
  integration suite passed (`360 passed`).

Root causes fixed during runtime verification:

- The scoped taxonomy-value query left an optional parameter untyped, which PostgreSQL
  rejected. Explicit `text` casts now make both scoped and unscoped lookup deterministic.
- The frontend used `discriminators` while the API contract used
  `identity_discriminators`; the UI now sends the canonical contract field unchanged.
