# 260817-01 Add real-LLM integration tests for ThesisBuilder event-taxonomy selection

## Problem Statement

ThesisBuilder has deterministic tests for prompt construction, response parsing,
event-identity normalization, and taxonomy persistence, but it has no automated test
that calls the configured LLM through the same analysis path used by the application.
Consequently, tests cannot establish whether exposing the active controlled taxonomy to
the model actually reduces synonym-only gaps, preserves genuinely novel proposals, and
avoids forcing an incorrect canonical value.

The live test must exercise `ThesisAnalyzer.analyze_article()` with
`OpenAIThesisClient`, a real taxonomy snapshot, and the production structured-response
parser. A small persistence smoke test must then exercise the normal ThesisBuilder
workflow with disposable integration PostgreSQL and Redis infrastructure. A direct API
call built independently in the test is insufficient because it would bypass application
prompt construction, taxonomy-revision selection, parsing, normalization, token
accounting, and gap persistence.

## Verified Evidence

- `_build_prompt()` currently receives and emits only `taxonomy_revision`; it does not
  receive the active canonical values or family-scoped subtype map.
- `ThesisAnalyzer.analyze_article()` is the application boundary that selects a taxonomy
  snapshot, builds the prompt, invokes the LLM client, parses the structured response,
  and normalizes `event_identity`.
- `PostgresThesisBuilderRepository.save_analysis()` derives taxonomy-gap writes from the
  normalized identity's lossless candidate fields.
- The existing pytest configuration defines only the `integration` marker. There is no
  separately selectable marker for integration tests that spend tokens and require
  external network access.
- The repository's environment loader can load a selected file without printing it and
  can preserve a pre-existing CI environment variable with `override_existing=False`.
- A bounded, read-only Haas query on 2026-08-17 found 83 open taxonomy-gap proposals
  representing 562 occurrences. Every sampled representative analysis recorded
  `provenance.source=full_analysis_llm` and `llm_model=gpt-4o-mini`.
- Official OpenAI guidance notes that model outputs and prompting behavior can vary
  between snapshots and recommends pinned model versions plus evals for application
  behavior: <https://developers.openai.com/api/reference/overview#backwards-compatibility>.

## Expected Behavior

### Test separation and invocation

- Add an `llm_eval` pytest marker in `pyproject.toml` in addition to the existing
  `integration` marker.
- Put the live suite in
  `tests/integration/test_thesis_builder_taxonomy_llm_integration.py` and mark the module
  with both `pytest.mark.integration` and `pytest.mark.llm_eval`.
- The suite is excluded from ordinary unit tests and from the ordinary infrastructure
  integration suite. It runs only when explicitly selected, for example:

  ```powershell
  $env:RUN_LLM_INTEGRATION = "1"
  uv run pytest -m "integration and llm_eval" \
      tests/integration/test_thesis_builder_taxonomy_llm_integration.py
  ```

- The ordinary infrastructure integration category can be selected explicitly without
  paid model calls using `uv run pytest -m "integration and not llm_eval"`.

- Collection remains safe when live tests are not enabled. When
  `RUN_LLM_INTEGRATION=1`, a missing API key is a clear configuration failure rather
  than an unexplained skip or attempted unauthenticated request.

### Secrets and configuration

- Before constructing settings or an OpenAI client, the live-test fixture calls the
  existing `load_env_files()` with the repository root,
  `filenames=(".env.secrets",)`, and `override_existing=False`.
- `OPENAI_API_KEY` is read from the resulting process environment. The key is never
  copied into test data, parametrization IDs, assertion messages, logs, snapshots, or
  CI artifacts.
- Loading only `.env.secrets` prevents production database, Redis, queue, and other
  service settings from leaking into the integration test. Test infrastructure settings
  remain explicit and must pass the existing safe-test database and Redis guards.
- The model is selected by a dedicated non-secret test setting such as
  `THESIS_BUILDER_LLM_INTEGRATION_MODEL`. The documented/default value should be a pinned
  snapshot supported by the account. Changing the model is an explicit eval-baseline
  change.
- Use `temperature=0`, `store=False`, the production structured-output schema, bounded
  output tokens, the production request timeout, and bounded transport retries.
  Transport retries must not retry a semantic assertion until it happens to pass.

### Application path under test

The main corpus test must construct real `NewsArticle` objects from committed fixtures
and call:

```text
NewsArticle
  -> ThesisAnalyzer.analyze_article()
  -> production prompt builder with the selected EventTaxonomySnapshot
  -> OpenAIThesisClient / Responses API
  -> production structured-response parser
  -> normalize_event_identity()
  -> LlmAnalysisResult
```

It must not duplicate `_build_prompt()` or call the OpenAI SDK directly from the test.
Most cases should stop at `LlmAnalysisResult`, which gives semantic coverage without
unnecessary PostgreSQL/Redis setup.

Add one small end-to-end smoke test using the existing safe integration helpers and the
normal ThesisBuilder runner/repository path:

```text
test Redis article event
  -> ThesisBuilder runner
  -> real ThesisAnalyzer and OpenAIThesisClient
  -> test PostgreSQL t_news_analyses
  -> optional test PostgreSQL t_event_taxonomy_gaps
```

The smoke test uses one known-synonym case and one genuinely novel candidate case. It
must verify persistence and gap behavior without satisfying the evidence count needed
to publish a card or signal.

### Assertions and scoring

Parse and normalize every live result with the active application snapshot. Tests score
semantic fields, not full-response text:

- required canonical family and subtype, where unambiguous;
- coverage role and event stage, allowing an explicit small set where the article is
  legitimately ambiguous;
- absence of a candidate for every dimension with a fitting canonical value;
- family/subtype scope validity;
- exact preservation of a candidate when no canonical value fits;
- no dimension swapping, such as returning `earnings_call` as an event family or
  `announcement` as an event family;
- valid structured output, ticker/exchange identity, taxonomy revision, model name, and
  non-zero actual token usage.

Hard safety assertions must always pass: structured output parses, output canonical
values exist in the supplied snapshot, family-scoped subtypes are valid, and novel raw
candidates are not silently discarded. Corpus-quality assertions use an aggregate
threshold so one defensible ambiguous classification does not make the suite flaky.
Initial acceptance thresholds are:

- at least 90% of required unambiguous canonical fields match;
- at least 90% reduction in synonym-only candidate fields compared with the stored Haas
  baseline outputs for the same cases;
- zero known cases where a value is placed in the wrong taxonomy dimension;
- zero loss of required genuine-novel candidates;
- no more than 2% forced-fit rate once the corpus contains at least 50 labeled cases.

Persist a concise per-case result artifact containing only fixture ID, selected model,
taxonomy revision, expected fields, actual normalized fields, pass/fail reasons, token
count, and latency. Never include the API key or request headers.

## Acceptance Criteria

- A committed, reviewed JSONL corpus contains the Haas-derived cases above plus at least
  one genuine-novel synthetic case, without secrets or production URLs.
- Live tests explicitly load `.env.secrets` with the existing environment loader before
  reading `OPENAI_API_KEY`.
- Live tests are opt-in through both a pytest marker and an explicit run flag.
- `ThesisAnalyzer.analyze_article()` and `OpenAIThesisClient` are used; the test does not
  reimplement the prompt or call the SDK directly.
- The active taxonomy snapshot, including family-scoped subtypes and a test-only dynamic
  canonical value, is visible to the model through the production prompt path.
- The corpus test implements hard safety assertions and aggregate quality thresholds.
- A safe disposable-infrastructure smoke test verifies the persisted analysis identity
  and presence/absence of the corresponding taxonomy-gap row.
- No live test writes to Haas or any production database, Redis instance, queue, OpenAI
  storage, or taxonomy table.
- API errors, semantic failures, model name, revision, token use, and latency are
  distinguishable in test output without exposing credentials or full request headers.
- The normal unit suite and ordinary integration suite remain free of paid LLM calls.
- README or ThesisBuilder test documentation explains prerequisites, explicit commands,
  expected cost-bearing behavior, and how to update the pinned model/baseline.

## Test Plan

1. Add deterministic unit tests proving the active snapshot's canonical values and
   family-scoped subtype map are serialized into the production analysis prompt in a
   stable order.
2. Add a deterministic unit test proving a newly loaded runtime taxonomy revision changes
   the prompt and therefore its analysis cache key.
3. Add deterministic parser/normalizer tests for canonical output, wrong-dimension input,
   unknown candidates, and family-scoped subtype rejection.
4. Add the opt-in live corpus test through `ThesisAnalyzer.analyze_article()` and the
   real `OpenAIThesisClient`.
5. Score required fields, accepted alternatives, synonym-gap reduction, wrong-dimension
   errors, candidate preservation, tokens, and latency.
6. Run the corpus at least three times before establishing the initial pinned-model
   baseline; record per-case stability instead of choosing the best run.
7. Add the two-case runner/repository smoke test with the existing safe PostgreSQL and
   Redis helpers; verify one canonical case creates no gap and one novel case creates
   exactly one bounded gap.
8. Verify `uv run pytest -m "not integration"` makes no external request and still passes.
9. Verify `uv run pytest -m integration` does not run paid LLM tests unless explicitly
   enabled.
10. Verify the explicit live-test command loads `.env.secrets`, makes real API calls, and
    reports actionable authentication, rate-limit, timeout, schema, and semantic errors.

## Dependencies and Scope

- Depends on the prompt change that supplies the active `EventTaxonomySnapshot` values,
  not only its revision, to the model.
- Reuses the runtime taxonomy loader from issue `260729-01` and the lossless candidate
  behavior from issue `260723-01`.
- The pytest suite is the initial implementation. Migrating the corpus to or additionally
  publishing it through the OpenAI Evals API is optional follow-up work, not required for
  this issue.
- This issue does not authorize production taxonomy decisions, Haas writes, model
  migration, or changes to trading/card-generation policy.

## Resolution

### Root Cause

The production analysis path selected a taxonomy snapshot for normalization but exposed
only its revision to the model. There was no opt-in test harness that exercised the
real `OpenAIThesisClient` through `ThesisAnalyzer` or checked persisted gap behavior.

### Resolution Steps

- Added the `llm_eval` marker and an explicitly flag-gated real-model corpus suite.
- Committed a de-identified Haas-derived JSONL corpus plus a novel out-of-taxonomy
  case, with baseline candidate patterns for aggregate synonym-gap scoring.
- Included the selected snapshot's stable canonical values and family-scoped subtype
  map in the production analysis prompt, making the prompt cache-sensitive to runtime
  taxonomy changes.
- Added a disposable PostgreSQL/Redis runner smoke test for canonical and novel gap
  persistence, and documented the cost-bearing invocation and pinned-model override.

### Remaining Risks and Follow-up

The live suite is intentionally not part of ordinary CI because it depends on external
model availability and incurs cost. Run it before changing the pinned model or taxonomy
prompt, review its artifact, and update the baseline deliberately rather than treating
model variability as a reason to weaken the safety assertions.
