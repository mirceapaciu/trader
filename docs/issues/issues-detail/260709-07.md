# 260709-07 Soft dedupe is scoped per source; the same story ingested via two providers counts twice

## Problem Statement

Soft deduplication only compares an incoming article against previously persisted articles from
the **same** `source` value (`rss`, `finnhub`, `marketaux`). The same story arriving through two
providers is persisted twice, analyzed twice by ThesisBuilder (two triage/analysis LLM calls),
and can contribute **two** evidence entries to the same thesis window — false corroboration for
the `THESIS_CARD_REQUIRED_EVIDENCE_COUNT` gate, which is supposed to measure independent
confirmation of a story.

This was a latent issue while providers had little overlap. With per-symbol Finnhub company-news
polling (implemented 2026-07-09), overlap becomes routine: Finnhub aggregates the same publishers
the Yahoo RSS batches poll (a live company-news fetch for AVGO returned Yahoo-hosted articles),
so most watchlist stories will now arrive on both channels.

The per-source restriction is not a deliberate corroboration semantic: within `source='rss'`,
articles from *different outlets* already dedupe against each other (observed on 2026-07-08:
CNBC's "Apple commits $30 billion to Broadcom" was `rejected_soft_duplicate` at similarity ~0.99
against an earlier Yahoo-feed copy). The system's unit of corroboration is therefore already
"distinct story content", not "distinct channel"; the candidate query scope just does not match
that intent.

## Verified Evidence

- `src/core_components/event_ingestion_engine/engine.py:82-88` — dedupe candidates are loaded with
  `source=canonical.source`.
- `src/product_components/news_fetcher/storage_adapter.py:76-91` —
  `list_soft_dedupe_candidates` filters `WHERE source = %s`.
- `src/core_components/event_ingestion_engine/canonicalization.py:72-91` — the canonical id
  (hard-dedupe identity) hashes `source` into the digest, so even the exact same URL ingested via
  two providers produces two distinct rows.
- Production data 2026-07-08: `news_fetcher.t_news_filter_results` shows cross-outlet
  soft-duplicate rejections *within* `source='rss'` (CNBC vs Yahoo copies of the Broadcom/Apple
  deal story), while nothing prevents cross-source copies.
- Live check 2026-07-09: `FinnhubCompanyNewsProvider` fetch for AVGO returned 131 articles/24h,
  including Yahoo-hosted URLs that the Yahoo RSS batch also delivers.

## Expected Behavior

1. **Policy-driven scope, not a silent query change.** `SoftDedupePolicy` (event ingestion
   engine) gains a dedupe scope option (e.g. `cross_source: bool` or a scope enum). The engine
   passes it through to `list_soft_dedupe_candidates`; the Postgres adapter drops the
   `source = %s` predicate when scope is cross-source. The ingestion engine is reusable core
   technology, so the default for the engine itself stays backward-compatible (per-source);
   NewsFetcher configures cross-source explicitly.
2. **Reproducibility.** The scope is recorded alongside the existing dedupe parameters
   (`dedupe_algorithm`, `dedupe_similarity_threshold`, `dedupe_lookback_hours`) in the filter
   config, its fingerprint, and the `t_news_filter_runs` snapshot, so filter-quality replays and
   production runs remain comparable.
3. **Winner selection unchanged.** The earliest persisted copy wins (existing behavior), which
   favors the lowest-latency channel; the rejected copy keeps the standard
   `rejected_soft_duplicate` result row with `matched_article_id` pointing across sources.
4. **Hard dedupe unchanged.** Canonical identity continues to include `source`; same-URL
   cross-source copies are handled by soft dedupe (title similarity dominates the score at 0.70
   weight; identical locators contribute 0.10 plus the tie-break).

## Acceptance Criteria

- An article whose text is a near-duplicate (≥ threshold) of an already persisted article from a
  **different** source is rejected as `rejected_soft_duplicate` with `matched_article_id` set to
  the cross-source original, and is not published to `news_raw_queue`.
- With scope configured per-source (engine default), behavior is byte-identical to today —
  existing engine consumers are unaffected without opt-in.
- NewsFetcher production config runs with cross-source scope; the scope value appears in the
  filter config snapshot JSON persisted with each filter run and changes the config fingerprint.
- Distinct stories below the similarity threshold continue to flow from both providers.
- Documentation: dedupe scope documented in the news-fetcher configuration doc and the event
  ingestion engine's dedupe contract notes.

## Test Plan

- Unit (deduplication/engine): cross-source candidate above threshold → rejected with matched id;
  same input with per-source scope → accepted; below-threshold cross-source pair → accepted.
- Unit (storage adapter): `list_soft_dedupe_candidates` includes/excludes other-source rows
  according to scope; lookback window still applied in both modes.
- Unit (filter config): fingerprint changes when scope changes; snapshot JSON carries the scope.
- Integration: ingest the same story via a fake RSS provider and a fake Finnhub company-news
  provider in one service cycle → exactly one accepted article, one `rejected_soft_duplicate`
  result, one published queue entry.
