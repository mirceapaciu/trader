# 260707-01 Backtester should invoke TradeExecutor's pure decision logic instead of reimplementing diverging trading rules

## Problem Statement

The Backtester simulates trading rules that diverge from the rules the live TradeExecutor
actually runs, so backtests measure a strategy nobody trades. The live decision logic already
exists as a pure, side-effect-free module (`trade_executor/pipeline.py` — its own docstring: "no
database, Redis, or broker dependency"), but the Backtester maintains an independent,
hand-rolled approximation. The divergences are material:

1. **Brackets**: live uses ATR-based stops with R-multiple targets (`construct_levels`); the
   Backtester uses flat +3% take-profit / −1.5% stop for every trade regardless of instrument
   volatility.
2. **Sizing**: live sizes off the card's risk box — `qty = floor(max_loss_usd / |entry − stop|)`
   clamped by position/portfolio caps (`size_position`); the Backtester uses
   confidence-fractional sizing ($1000 / 50%) and ignores `risk_max_loss_usd` entirely.
3. **Time exit**: live computes a horizon-aware `time_exit_at` from the card's `time_horizon`
   via `time_horizon_days_map` and a trading calendar (in *trading days* — a `swing_1d_5d` card
   is held for days); the Backtester force-closes every position at a flat 4 hours. The
   Backtester is the outlier: it disagrees with both the thesis card and the live executor.
4. **Admission/risk gates**: live applies `evaluate_admission_gate` (hold/expiry/min-confidence/
   watchlist/review/duplicate-position/horizon gates) and `evaluate_risk_gate` (latching
   daily-loss kill switch, position/exposure/sector caps counting working orders); the Backtester
   has a similar-but-not-identical reimplementation (no sector cap, no latching halt, coarse
   `card_population` filter instead of the admission gate).

Consequence: current backtest P&L (negative) cannot be attributed to card quality versus rule
divergence, and every future rule change must be implemented twice or the two copies drift
further. The backtest verification methodology (`docs/design/backtest-verification-methodology.md`)
has to carry a whole suspect (S11 sim/live parity, plus the S14 horizon incoherence) to *audit*
a gap that could be closed by construction.

## Expected Behavior

The Backtester gains a **live-parity execution mode** implemented by *invoking* the
TradeExecutor's pure logic, not by re-specifying it:

- Bracket levels from `trade_executor.pipeline.construct_levels` (ATR-20d computed point-in-time
  from historical daily bars via MarketData, bars at or before entry only).
- Sizing from `trade_executor.pipeline.size_position` using the card's `risk_max_loss_usd`.
- Time exit from the trading calendar + `time_horizon_days_map`, honoring the card's
  `time_horizon` instead of a flat 4-hour stop.
- Admission and portfolio gating via `evaluate_admission_gate` / `evaluate_risk_gate`, with the
  Backtester mapping its simulated state onto `PortfolioState` / `DailyRiskState`.
- Only the pure module and calendar are invoked. `TradeExecutorService`, the broker gateway,
  repository, and Redis paths remain untouched and unused — the Backtester's "no broker, no live
  tables" boundary is preserved.
- Live-parity becomes the default execution mode for verification baselines; the existing flat-%
  `ExecutionModel` remains available as an explicit, opt-in experimental mode recorded in the
  run's `execution_model_snapshot_json`.
- Known fidelity limits are documented, not blocking: bid/ask approximation for
  `entry_limit_price` (OHLCV has no quotes), no historical watchlist snapshots (admission gate
  runs with an assume-in-watchlist flag), portfolio-state mapping differences.
- Design docs updated accordingly: backtester behavior/configuration specs describe the
  live-parity mode as invoking `trade_executor.pipeline` (replacing the "extend `ExecutionModel`
  with ATR/risk-based reimplementations" phrasing), and the verification methodology notes that
  S11 is satisfied by construction in live-parity runs (the audit remains for non-parity runs).

Ownership consequence (intended): `trade_executor` becomes the single owner of trade decision
logic; the Backtester is a consumer. Future rule changes are made once and are immediately
backtestable.

## Acceptance Criteria

- A backtest run can be executed in live-parity mode, and its trades' stop/target/quantity/time
  exit are byte-for-byte what direct calls to `construct_levels` / `size_position` /
  `trading_calendar.time_exit_at` return for the same inputs.
- In live-parity mode, a `swing_1d_5d` card is not force-closed at 4 hours; its time exit follows
  `time_horizon_days_map` in trading days.
- `risk_max_loss_usd` from the card's risk box drives sizing in live-parity mode.
- The run row's `execution_model_snapshot_json` records the mode and effective parameters; replay
  runs in the legacy flat-% mode are unchanged (regression-tested).
- No import of `trade_executor` service/broker/repository/redis modules from the Backtester —
  only `pipeline` (and the trading calendar); no cross-schema database access is introduced.
- ATR and all other inputs are derived from data at or before the simulated entry time
  (no-look-ahead preserved).
- Design docs (backtester behavior + configuration, verification methodology) reflect the
  invoke-not-reimplement decision.

## Test Plan

- Unit tests (fakes, no external deps) in `tests/product_components/backtester/`:
  - Parity: for a fixed card/bars fixture, the engine's levels, quantity, and time exit in
    live-parity mode equal direct `pipeline` / calendar calls with the same inputs.
  - Horizon: a `swing_1d_5d` card's simulated exit occurs at the calendar-computed time exit
    (multi-day), not at 4 hours, when no bracket is touched.
  - Risk-box sizing: quantity honors `max_loss_usd / stop_distance` and the notional clamps.
  - No-look-ahead: ATR inputs use only daily bars strictly before the entry session.
  - Legacy mode regression: existing flat-% engine behavior tests still pass unchanged.
- Existing TradeExecutor pipeline tests continue to pass (shared logic unchanged by the reuse).
- `uv run pytest -m "not integration"` passes.
- End-to-end: run one replay backtest in each mode over the same window; verify both complete and
  their run rows record distinguishable execution-model snapshots.

## Root Cause

The Backtester owned a separate execution-rule implementation: flat percent brackets,
confidence-fractional sizing, fixed four-hour time stops, and local risk checks. The live
TradeExecutor already exposed the required decision rules as pure functions, but the Backtester did
not consume them, so the two implementations drifted.

## Resolution

- Added `ExecutionModel.mode` with `live_parity` as the default and `legacy_flat_percent` as the
  explicit opt-in mode for old flat-percent behavior.
- Wired Backtester CLI and Monitoring UI-triggered runs through settings-derived execution/risk
  models, including TradeExecutor-aligned env defaults for ATR stops, R targets, minimum confidence,
  horizon mapping, max positions, exposure, and daily risk limits.
- Added a live-parity engine path that converts exported thesis cards to TradeExecutor `ThesisCard`
  inputs, calls the pure admission/risk/levels/sizing functions, computes ATR from prior daily bars
  only, and uses the TradeExecutor trading calendar for horizon-aware time exits.
- Preserved the legacy flat-percent simulator under `legacy_flat_percent` and updated existing
  regression tests to opt into it explicitly.
- Updated Backtester design docs and the verification methodology to describe live-parity mode and
  the remaining fidelity limits: OHLCV bid/ask approximation, assumed watchlist membership, and
  unknown historical sector exposure.

## Remaining Risks / Follow-ups

- Live-parity approximates quotes from OHLCV (`bid = ask = entry bar open`) because historical quote
  snapshots are not available to the Backtester.
- Historical watchlist and sector snapshots are not yet available, so watchlist membership is
  assumed and sector exposure is marked unknown for the risk gate.
