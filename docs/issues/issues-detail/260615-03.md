# 260615-03 Remove NewsFetcher direct database access to Shared contracts

## Problem Statement

NewsFetcher currently reads shared watchlist and alias tables directly and seeds shared instrument tables directly. That couples NewsFetcher ingestion behavior to the physical `shared` schema instead of a shared-owned contract surface.

## Verified Evidence

- `src/product_components/news_fetcher/storage_adapter.py:522` reads active rows from `shared.<watchlist_table>`.
- `src/product_components/news_fetcher/storage_adapter.py:571` joins `shared.<watchlist_table>` while building dynamic RSS feed specs.
- `src/product_components/news_fetcher/storage_adapter.py:580` reads `shared.t_instrument_aliases`.
- `src/product_components/news_fetcher/config_sync.py:207` inserts into `shared.t_instruments`.
- `src/product_components/news_fetcher/config_sync.py:234` inserts into `shared.t_instrument_aliases`.

## Expected Behavior

NewsFetcher should consume watchlist and instrument metadata through a shared Instrument Registry API or adapter. Shared instrument seeding and metadata mutation should be owned by the shared component or a shared-owned admin surface rather than NewsFetcher writing shared tables directly.

## Acceptance Criteria

- NewsFetcher runtime does not query shared watchlist or alias tables directly.
- NewsFetcher config sync does not write directly into shared instrument tables.
- Dynamic RSS feed construction uses a shared-owned contract surface for watchlist and alias data.
- Ownership of shared instrument writes is moved out of NewsFetcher or wrapped behind a shared-owned API.

- Run `uv run pytest tests/integration/test_news_fetcher_integration.py -q`.
- Add a boundary test that fails if NewsFetcher runtime SQL references `shared.` directly.
