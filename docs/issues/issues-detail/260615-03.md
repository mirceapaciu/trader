# 260615-03 Remove NewsFetcher direct database access to Shared contracts

## Problem Statement

NewsFetcher currently reads shared watchlist and alias tables directly and seeds shared instrument tables directly. That couples NewsFetcher ingestion behavior to the physical `shared` schema instead of a shared-owned contract surface.

## Verified Evidence

- `src/product_components/news_fetcher/storage_adapter.py:522` reads active rows from `shared.<watchlist_table>`.
- `src/product_components/news_fetcher/storage_adapter.py:571` joins `shared.<watchlist_table>` while building dynamic RSS feed specs.
- `src/product_components/news_fetcher/storage_adapter.py:580` reads `shared.t_instrument_aliases`.
- `src/product_components/news_fetcher/config_sync.py:207` inserts into `shared.t_instruments`.
- `src/product_components/news_fetcher/config_sync.py:234` inserts into `shared.t_instrument_aliases`.

## Expected Behavior

NewsFetcher should consume watchlist and instrument metadata through a shared Instrument Registry API or adapter. Shared instrument seeding and metadata mutation should be owned by the shared component or a shared-owned admin surface rather than NewsFetcher writing shared tables directly.

## Acceptance Criteria

- NewsFetcher runtime does not query shared watchlist or alias tables directly.
- NewsFetcher config sync does not write directly into shared instrument tables.
- Dynamic RSS feed construction uses a shared-owned contract surface for watchlist and alias data.
- Ownership of shared instrument writes is moved out of NewsFetcher or wrapped behind a shared-owned API.

## Test Plan

- Run `uv run pytest tests/product_components/news_fetcher -q`.
- Run `uv run pytest tests/integration/test_news_fetcher_integration.py -q`.
- Add a boundary test that fails if NewsFetcher runtime SQL references `shared.` directly.

## Root Cause

NewsFetcher owned the parsing of instrument seed configuration and then performed the shared table mutations itself. Its PostgreSQL storage adapter also combined NewsFetcher-owned RSS source rows with shared watchlist and alias rows in one cross-schema query, so dynamic RSS construction depended on shared physical table layout.

## Resolution

- Added a shared-owned `PostgresSharedInstrumentAdmin` adapter and `SharedInstrumentSeed` DTO for instrument and alias upserts.
- Updated NewsFetcher config sync to delegate shared instrument writes to the shared admin adapter.
- Updated NewsFetcher storage to accept an injected Instrument Registry contract and to build dynamic RSS specs by combining shared registry records with NewsFetcher-owned RSS source/rule rows in Python.
- Updated default service wiring and integration tests to construct `PostgresSharedInstrumentRegistry` explicitly.
- Added a NewsFetcher boundary test that fails on direct shared instrument/watchlist SQL in NewsFetcher runtime/config-sync files.

## Test Evidence

- `uv run pytest tests/product_components/news_fetcher -q` passed with 39 tests.
- `uv run pytest tests/product_components/thesis_builder/test_shared_adapters.py -q` passed with 3 tests.
- `uv run pytest tests/integration/test_news_fetcher_integration.py -q` passed with 4 tests.

## Remaining Risks

- `news_fetcher/main.py` still bootstraps the shared schema for local/dev startup. That is intentionally left in place because this issue targets NewsFetcher runtime/config-sync data access, not schema initialization.
