# 260729-03 Execute bounded and resumable event-taxonomy backfill jobs

## Parent Issue

`260728-01` — Add operator workflow for accepting controlled event-identity values.

## Problem Statement

Taxonomy decisions can create rows in `t_event_taxonomy_backfill_jobs`, but no worker
executes them. Historical analyses therefore retain old unmapped candidates, command
status cannot report meaningful backfill progress, and operators cannot tell whether a
decision has been applied to affected history.

## Verified Evidence

- The schema contains `t_event_taxonomy_backfill_jobs`.
- The decision transaction inserts a backfill job.
- No runtime worker claims jobs, processes bounded batches, persists a cursor, or marks
  completion/failure.
- Published-card immutability is required by `260728-01`.

## Expected Behavior

- ThesisBuilder claims one backfill job using conflict-safe database locking.
- Work is divided into bounded batches with a durable cursor and counters.
- The job selects only analyses affected by the decided dimension and proposal.
- Each analysis is re-normalized with the decision's target taxonomy revision.
- Re-running a completed batch is idempotent.
- Progress survives process restart.
- Failures record bounded error codes and retry metadata.
- Published thesis cards are never rewritten or republished.
- Evidence-window changes are disabled initially unless a separately documented,
  explicitly audited policy is implemented.
- Historical UI may show that a newer classification exists without changing the
  original published card.

## Job State

Expose at least:

- `accepted`, `running`, `completed`, `failed`;
- last processed analysis ID or equivalent stable cursor;
- matched, processed, changed, skipped, and failed counts;
- requested and target taxonomy revisions;
- started, updated, and finished timestamps;
- bounded error code.

## Acceptance Criteria

- Jobs are claimed by at most one worker at a time.
- Batch size is configurable and bounded.
- Restart resumes from the durable cursor.
- Duplicate execution does not duplicate audit data or change revision counts.
- Only matching analyses are re-normalized.
- Published cards and published signals remain byte-for-byte unchanged.
- Command status exposes the associated backfill state and counts.
- Operators can retry a failed job safely.
- Backfill produces concise progress logs without article bodies or secrets.

## Test Plan

1. Unit-test affected-row selection for every controlled dimension.
2. Test bounded batches and durable cursor advancement.
3. Test crash/restart between batch persistence and acknowledgement.
4. Test idempotent replay of the last batch.
5. Test failed-job retry.
6. Verify analysis identity and revision updates.
7. Verify published cards, review state, and signal queues are unchanged.
8. Integration-test command completion followed by backfill completion.
9. Test progress/status API serialization.

## Dependencies

- `260729-01` supplies revision-aware normalization.
- `260729-02` supplies durable command status to which the job result is attached.

## Resolution

Backfill jobs now have a durable analysis-ID cursor, bounded counters, retry metadata,
timestamps, and safe error state. ThesisBuilder claims jobs with conflict-safe row
locking, processes one configurable bounded batch per runtime cycle, reconstructs each
matching identity from lossless provenance under the target taxonomy revision, and
persists analysis identity/revision changes atomically with cursor progress.

The worker selects only the candidate dimension and proposal resolved by the decision.
It does not invoke card/window persistence or Redis signal publication, so published
cards, reviews, evidence windows, and signals remain unchanged. Stale running jobs are
recoverable after restart and failed jobs have an explicit safe retry operation.

Remaining risk: production throughput depends on the configured batch size; operators
should retain the default of 100 until Haas timing has been observed.

Runtime verification:

- A real PostgreSQL job was claimed and completed in two bounded size-1 cycles: one
  matching row followed by the terminal empty batch.
- Status reported matched `1`, processed `1`, changed `1`, skipped `0`, failed `0`.
- The historical analysis moved from taxonomy revision `1` to `2`, resolved the newly
  accepted stage, and cleared its candidate field.
- Card and evidence-window counts and checksums were identical before and after
  backfill; Redis pending count was zero.
- The durable PostgreSQL/Redis integration test reproduces command completion,
  activation, backfill, actor persistence, status lookup, and acknowledgement.
