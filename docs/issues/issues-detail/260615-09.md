# 260615-09 Remove Monitoring UI direct database access to Filter Quality Evaluator

## Problem Statement

Monitoring UI currently reads and updates Filter Quality Evaluator tables directly. That couples the UI backend to evaluator storage instead of consuming evaluator-owned APIs.

## Verified Evidence

- `src/product_components/monitoring_ui/backend/repository.py:423` and `:460` read `filter_quality_evaluator.t_filter_quality_item_assessments`.
- `src/product_components/monitoring_ui/backend/repository.py:556` and `:565` read `filter_quality_evaluator.t_filter_quality_runs`.
- `src/product_components/monitoring_ui/backend/repository.py:574` updates `filter_quality_evaluator.t_filter_quality_runs`.
- `src/product_components/monitoring_ui/backend/repository.py:803` and `:807` compose additional evaluator status SQL around `t_filter_quality_item_assessments`.

## Expected Behavior

Monitoring UI should consume evaluator runs, summaries, and drill-down results through Filter Quality Evaluator-owned APIs. Direct SQL reads and writes against evaluator tables should be removed from the UI backend.

## Acceptance Criteria

- Monitoring UI backend does not query or update `filter_quality_evaluator` tables directly.
- Filter Quality Evaluator exposes the UI-facing run and assessment data through an owning API surface.
- Monitoring UI integration tests validate the new evaluator boundary.

## Test Plan

- Run `uv run pytest tests/product_components/monitoring_ui -q`.
- Add integration coverage for evaluator status and drill-down endpoints via the replacement API surface.
- Add a boundary test that fails if Monitoring UI runtime SQL references `filter_quality_evaluator.` directly.
