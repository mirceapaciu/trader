# 260723-01 Implement versioned event_identity schema with controlled taxonomy and user-visible gaps

## Problem Statement

ThesisBuilder currently persists a nullable, unconstrained `event_type TEXT` returned by the
full-analysis LLM. It has no documented vocabulary, no structured event-instance fields, no
normalization or compatibility rules, and no workflow for values outside a known taxonomy.
Story assignment therefore still derives event identity primarily from prose and semantic LLM
judgment.

Issue `260722-01` corrected the immediate zero-token-overlap false-negative, but it did not give
ThesisBuilder a stable representation for facts such as:

- the subject instrument;
- the underlying event family;
- the fiscal/reporting period or other event-instance discriminator;
- the event occurrence time;
- counterparties and their roles;
- whether an article is the primary announcement, a preview, a reaction, a recap, or a
  correction.

Without that representation, the system cannot deterministically recognize that an official
AT&T Q2-results release and subsequent "stock rises after earnings" coverage refer to the same
event instance while keeping an earnings preview, a different quarter, or an unrelated AT&T
announcement separate.

The implementation must also remain open to events that were not anticipated when the taxonomy
was released. Unknown values must never make an otherwise valid analysis disappear, fail schema
parsing, or be silently coerced to an unrelated controlled value. Taxonomy gaps must be
persisted, visible to operators, and resolvable through an audited user decision.

## Expected Behavior

### Ownership and boundaries

- ThesisBuilder owns the `event_identity` contract, taxonomy registry, extraction,
  normalization, persistence, event-instance matching, and taxonomy-gap decisions.
- Shared continues to own canonical instruments. ThesisBuilder receives canonical instrument
  identifiers through a shared adapter; it must not add direct SQL access to Shared-owned
  tables.
- Monitoring UI displays identity and taxonomy-gap state and submits operator decisions through
  a ThesisBuilder-owned command/API contract. It must not mutate ThesisBuilder tables directly.
- Direction, sentiment, strategy, urgency, expected price impact, and trade action are
  interpretations of an event and must remain outside `event_identity`.

### Versioned `event_identity` schema

Each full analysis persists `event_identity_json` with this versioned logical schema:

```json
{
  "schema_version": 1,
  "taxonomy_version": "event-taxonomy-v1",
  "classification_status": "classified",
  "event_family": "earnings_results",
  "event_family_candidate": null,
  "event_subtype": "quarterly_results",
  "event_subtype_candidate": null,
  "event_stage": "completed",
  "coverage_role": "primary_announcement",
  "subject": {
    "instrument_id": 123,
    "ticker": "T",
    "exchange_code": "XNYS"
  },
  "participants": [
    {
      "role": "subject",
      "instrument_id": 123,
      "name_raw": "AT&T"
    }
  ],
  "period": {
    "kind": "fiscal_quarter",
    "fiscal_year": 2026,
    "fiscal_quarter": 2,
    "label_raw": "second quarter"
  },
  "occurred_at": "2026-07-22T10:30:00Z",
  "occurred_at_precision": "datetime",
  "identifiers": [],
  "attributes": {
    "result_vs_consensus": "beat"
  },
  "event_instance_key": "v1:...",
  "confidence": 0.94,
  "provenance": {
    "source": "full_analysis_llm",
    "model": "gpt-4o-mini",
    "prompt_version": "event-identity-v1",
    "extracted_from": ["headline", "summary"],
    "raw_response": {}
  }
}
```

Field requirements:

| Field | Contract |
| --- | --- |
| `schema_version` | Required integer controlling JSON shape and migration. |
| `taxonomy_version` | Required immutable taxonomy release identifier used for replay/cache keys. |
| `classification_status` | Required controlled value describing whether canonical classification succeeded. |
| `event_family` | Canonical controlled value; null only when status is not `classified`. |
| `event_family_candidate` | Lossless raw/normalized proposed value when the model cannot use an active canonical family. |
| `event_subtype` | Optional family-scoped controlled value providing specificity without proliferating top-level families. |
| `event_subtype_candidate` | Lossless proposed subtype when the family is known but no active subtype maps cleanly. |
| `event_stage` | Controlled lifecycle state of the underlying occurrence; not article sentiment. |
| `coverage_role` | Controlled relationship of this article to the occurrence. |
| `subject` | Required ticker/exchange snapshot plus canonical Shared instrument ID when available. |
| `participants` | Zero or more role-tagged canonical or raw entities. Raw names are retained when no instrument exists. |
| `period` | Structured reporting/scheduled period when relevant; null for events without a period. |
| `occurred_at` | Best known event time, preserving the existing freshness semantics. |
| `occurred_at_precision` | Distinguishes exact datetime from date/month/quarter/year/unknown precision. |
| `identifiers` | Stable external identifiers such as filing, case, trial, transaction, contract, or product IDs. |
| `attributes` | Typed, family-specific facts. Unknown attributes remain preserved but never become identity keys by accident. |
| `event_instance_key` | Versioned deterministic key only when sufficient canonical discriminators exist; otherwise null. |
| `confidence` | Extraction confidence, not trading confidence. |
| `provenance` | Model/rule/prompt source and lossless raw extraction needed for audit and replay. |

`event_identity_json` must be copied to the evidence window seeded by the analysis and to the
resulting thesis card. An existing window's canonical identity is immutable; later matching
articles may add observed aliases or missing non-conflicting facts in a separately audited
supplement, but they must not silently rewrite the event instance.

### Event-instance compatibility

Event identity comparison returns `same`, `different`, or `inconclusive`; missing fields are
never interpreted as a mismatch.

- Equal non-null `event_instance_key` values are the same occurrence.
- Conflicting canonical subject, family, period, stable external identifier, or defining
  participant roles are deterministic evidence of different occurrences.
- A subtype conflict is deterministic only when that family's versioned metadata marks the
  subtype as an event-instance discriminator; otherwise it is compatible or inconclusive.
- Compatible identities with incomplete discriminators are `inconclusive` and continue through
  semantic story assignment/confirmation.
- Coverage role does not create a different occurrence by itself. For example,
  `primary_announcement`, `results_report`, and `reaction` may share one AT&T Q2-results
  identity.
- Policy may keep `preview` from counting as results corroboration even when it references the
  same scheduled event. This is an evidence-admission rule, not an excuse to erase the shared
  event reference.
- `event_instance_key` must never include direction, sentiment, strategy, urgency, or price
  impact.

### Unknown-value preservation and user-visible gap workflow

#### 2026-07-28 implementation correction

Production card `c3b8c994-4b7e-5b33-87a7-18ce25595fdf` exposed a lossless-normalization
bug. Its corroborating analysis returned `event_family_candidate="partnership"` and
`event_stage="announcement"`, but normalization read only `event_family` and silently
replaced the unsupported stage with `unknown`. The candidates therefore never reached
`t_event_taxonomy_gaps`. Normalization must accept the candidate input fields, retain
unsupported stage, coverage-role, and participant-role values in explicit `*_candidate`
fields, and upsert each as an operator-visible taxonomy gap. Empty LLM identity objects
remain unsuggestable because they contain no proposed value.

ThesisBuilder owns versioned taxonomy tables:

1. `t_event_taxonomy_values`
   - dimension, canonical value, display name, description, status, schema/taxonomy version,
     family rules, creation/deprecation metadata.
2. `t_event_taxonomy_gaps`
   - dimension, raw value, normalized proposal, occurrence count, first/last seen,
     representative analysis IDs/headlines, status, resolution.
3. `t_event_taxonomy_decisions`
   - immutable audit log of map/accept/reject/deprecate decisions, actor, timestamp, old/new
     values, and rationale.

Allowed taxonomy-value statuses:

- `active`
- `proposed`
- `mapped_alias`
- `deprecated`
- `rejected`

For every unknown family, role, stage, participant role, or controlled attribute:

1. Preserve the raw value in `event_identity_json`.
2. Set `classification_status='unmapped'` when event family itself is unknown. Unknown
   secondary dimensions retain the classified family but mark the affected field as unmapped.
3. Upsert a bounded taxonomy-gap row with count and representative examples.
4. Continue analysis and story assignment using semantic fallback; never reject or drop the
   article solely because taxonomy coverage is incomplete.
5. Show an `Unmapped event identity` badge on the analysis and expose a ThesisBuilder taxonomy
   gaps view with dimension, proposed value, occurrence count, first/last seen, and examples.
6. Let an authorized user:
   - map the proposal to an existing active value;
   - accept it as a new canonical controlled value, supplying display name, description, and
     required identity discriminators;
   - reject it as invalid/noise.
7. Record the decision immutably, increment the taxonomy version, and backfill affected
   analyses/windows in an idempotent job. Published cards remain immutable; any historical
   reclassification is audit-only unless explicitly regenerated.

Taxonomy-gap collection must be bounded and safe against untrusted model output: normalize
case/spacing, cap raw value length and stored examples, aggregate repeated proposals, and never
create a database column, SQL identifier, route, or executable behavior from raw text.

## Acceptance Criteria

- Add a committed read-only inventory command that reproduces the attached local/Haas
  event-type and candidate-family reports, including counts, nulls, validity, and bounded examples
  without printing secrets.
- Re-run that inventory against both databases immediately before freezing `event-taxonomy-v1`;
  reconcile any drift as a baseline value or an explicitly documented unmapped proposal.
- Replace free-form `event_type` as the story-identity input with the versioned
  `event_identity` model above. Keep legacy `event_type` readable during migration.
- Extend the full-analysis structured output and parser with controlled canonical values plus a
  lossless unknown proposal path. Unknown controlled values must not make the entire LLM
  response unparseable.
- Persist `event_identity_json` on analyses, evidence windows, and cards, with query indexes for
  family, subtype, classification status, instance key, and taxonomy version.
- Obtain canonical instrument IDs through the Shared adapter boundary and preserve ticker,
  exchange, and raw participant names as point-in-time audit snapshots.
- Implement deterministic three-state event-identity comparison and integrate it ahead of
  lexical/semantic story verification.
- Preserve semantic fallback whenever identity is incomplete or unmapped.
- Seed every controlled value listed in this issue in the ThesisBuilder-owned taxonomy registry.
- Implement taxonomy gap, canonical value, and immutable decision persistence with bounded
  examples and idempotent upserts.
- Expose identity and gap state through a ThesisBuilder-owned contract and Monitoring UI:
  analysis details, aggregate gap list, examples, and audited map/accept/reject actions.
- Do not add Monitoring UI direct writes to ThesisBuilder tables.
- Include taxonomy/schema/prompt versions in LLM cache keys and regeneration inputs so live,
  reprocess, and backtest behavior remains comparable.
- Backfill historical analyses in batches without changing published cards or emitting signals.
- Update ThesisBuilder behavior/data-model/configuration docs and Monitoring UI contract docs.

## Remaining Risks and Follow-up

- A large initial enum can still miss future events; the gap workflow is therefore part of the
  minimum implementation, not a later enhancement.
- Model-generated structured identities can be wrong. Canonical fields improve auditability but
  do not eliminate the need for semantic confirmation and corpus replay.
- Dynamic user acceptance changes grouping semantics. Decisions require authorization, audit,
  taxonomy versioning, and explicit regeneration rather than silent retroactive mutation.
- Backfilling the larger local corpus may reveal aliases and subtypes that should map to existing
  families rather than expanding the top-level taxonomy.
- Event identity solves story-instance grouping. It does not prove that multiple articles are
  independent corroboration; source/event deduplication remains separately governed by
  `260709-07`.
