# 260615-07 Remove Monitoring UI direct database access to NewsFetcher

## Problem Statement

Monitoring UI currently reads and writes NewsFetcher-owned tables directly and also bootstraps the NewsFetcher schema. That makes the UI backend a cross-component SQL client instead of a consumer of NewsFetcher-owned APIs.

## Verified Evidence

- `src/product_components/monitoring_ui/backend/repository.py:104` bootstraps `src/product_components/news_fetcher/db/schema.sql`.
- `src/product_components/monitoring_ui/backend/repository.py:120`, `:175`, `:356`, `:373`, and `:590` read `news_fetcher` tables such as `t_provider_cycle_status`, `t_publication_obligations`, and `t_news_articles`.
- `src/product_components/monitoring_ui/backend/repository.py:521`, `:534`, `:662`, and `:693` writes and reads `news_fetcher.t_news_filter_configs`.
- `src/product_components/monitoring_ui/backend/repository.py:423` through `:432` joins `filter_quality_evaluator` rows to multiple `news_fetcher` tables for evaluator drill-down data.

## Expected Behavior

Monitoring UI should retrieve NewsFetcher operational status, article metrics, dead letters, and filter configuration through NewsFetcher-owned APIs. Schema bootstrapping and direct SQL against NewsFetcher tables should be removed from the UI backend.

## Acceptance Criteria

- Monitoring UI backend does not query or write `news_fetcher` tables directly.
- Monitoring UI backend no longer bootstraps NewsFetcher schema.
- NewsFetcher exposes the UI-facing operational and configuration data through an owning API surface.
- Monitoring UI integration tests validate the new API boundary.

## Test Plan

- Run `uv run pytest tests/product_components/monitoring_ui -q`.
- Run the Monitoring UI backend integration checks that cover provider status, backlog, dead letters, and filter configuration flows.
- Add a boundary test that fails if Monitoring UI runtime SQL references `news_fetcher.` directly.
