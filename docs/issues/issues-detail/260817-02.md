# 260817-02 Make the event-taxonomy database authoritative and bootstrap the complete predefined seed

## Problem Statement

ThesisBuilder currently has two competing event-taxonomy authorities:

- the in-process `DEFAULT_TAXONOMY_SNAPSHOT` assembled from constants in
  `event_identity.py`; and
- the revisioned PostgreSQL registry in `t_event_taxonomy_values`.

`EventTaxonomySnapshotProvider` starts with the Python baseline and merges database rows
into that baseline. A built-in value can therefore remain active at runtime even when it
is absent or deprecated in the database. PostgreSQL cannot faithfully reconstruct a
historical revision by itself, Monitoring UI lists can differ from runtime normalization,
and operator decisions cannot make the database truly authoritative.

The predefined v1 taxonomy seed is also incomplete in `schema.sql`. All predefined
canonical values, subtype-family relationships, and legacy aliases must be inserted into
the database during both clean bootstrap and idempotent upgrade of an existing database.
Once bootstrap completes, runtime snapshots must be built exclusively from effective
database rows.

## Verified Evidence

- The Python v1 baseline defines 50 event families, 37 event subtypes, 11 event stages,
  13 coverage roles, and 18 participant roles: 129 canonical values in total.
- The SQL bootstrap seeds all families, stages, coverage roles, and participant roles,
  but seeds only 19 of the 37 predefined event subtypes.
- A bounded, read-only comparison on Haas at taxonomy revision 3 found exactly the same
  mismatch: 37 built-in subtypes versus 19 active subtype rows in PostgreSQL.
- The 18 predefined subtypes missing from Haas are:

  - `activist_report`, `independent_research`, and `short_seller_report`;
  - `digital_asset_market_event`, `exchange_or_broker_launch`, `protocol_upgrade`,
    `stablecoin_authorization`, and `token_regulatory_action`;
  - `election`, `government_formation`, `leadership_transition`, and `referendum`;
  - `earthquake`, `extreme_weather`, `flood`, `hurricane`, `tornado`, and `wildfire`.

- Haas contains two effective database aliases (`earnings_announcement` and
  `earnings_report` to `earnings_results`), while the Python baseline also contains
  predefined legacy aliases that are not represented completely in the registry.
- Some predefined family aliases imply a subtype, for example `military action` maps to
  family `geopolitical_event` and subtype `military_action`. The current database alias
  model exposes `alias_for_value` but does not load an implied subtype from database
  metadata into `family_alias_subtypes`.
- `build_taxonomy_snapshot(..., baseline=...)` copies all baseline canonical values and
  aliases before applying database rows. It adds active values and aliases but does not
  remove a baseline value represented by a deprecated database row.
- `EventTaxonomySnapshotProvider` pre-caches the Python baseline at revision 1, so an
  explicit revision-1 request can bypass the database entirely.
- The existing integration test verifies only that all predefined event stages are
  visible through the Monitoring UI data source; it does not compare every dimension,
  subtype scope, or predefined alias.

## Expected Behavior

### One predefined seed manifest

- Define one immutable, versioned v1 seed manifest as the source for initial taxonomy
  data. It contains every predefined canonical value, display name, description where
  applicable, subtype family scope, alias target, and implied subtype for family aliases.
- Do not maintain independent hand-written canonical lists in both Python and SQL.
  Bootstrap code, default/offline test snapshots, and completeness tests must derive from
  the same manifest.
- The v1 manifest contains exactly the intended predefined values:

  - 50 event families;
  - 37 event subtypes with their family scopes;
  - 11 event stages;
  - 13 coverage roles;
  - 18 participant roles;
  - all predefined legacy aliases and any implied-subtype metadata.

- The manifest is application code, not mutable runtime state. After it has seeded a
  database, the effective database rows and taxonomy revision are authoritative.

### Complete and idempotent database bootstrap

- Separate table/schema creation from taxonomy data seeding sufficiently that the same
  seeding routine is invoked by ThesisBuilder startup and integration-test database
  bootstrap.
- Seed all predefined canonical and alias rows transactionally into
  `t_event_taxonomy_values` with `taxonomy_version='event-taxonomy-v1'` and
  `effective_from_revision=1`.
- The 18 missing subtype rows are a metadata repair, not a new semantic revision: they
  were already active in the runtime Python baseline. Adding them to existing databases
  therefore does not increment `taxonomy_revision` and does not require analysis
  backfill.
- Bootstrap is safe to rerun. Missing predefined rows are inserted, matching rows are
  left unchanged, and an incompatible collision fails startup with a bounded actionable
  error instead of silently overwriting an operator decision or corrupting history.
- Bootstrap validates that every subtype has exactly one valid family scope, every alias
  targets an effective canonical value in the same dimension, and every implied subtype
  belongs to the alias target family.
- A clean database and an upgraded existing database produce the same complete revision-1
  predefined registry.

### Database-authoritative runtime snapshots

- After successful schema and seed bootstrap, `EventTaxonomySnapshotProvider` loads a
  requested revision exclusively from `load_taxonomy_values()` results. It does not merge
  the Python seed snapshot into a database-loaded revision.
- The provider must not pre-cache a synthetic revision-1 baseline that can bypass
  PostgreSQL.
- Active canonical values, mapped aliases, deprecations, effective revision intervals,
  subtype scopes, and implied subtype mappings are all reconstructed from database rows.
- Deprecating a predefined value in a later revision actually removes it from that and
  subsequent runtime snapshots while preserving it in earlier revisions.
- Operator-added canonical values and aliases behave identically to predefined seed
  values once stored.
- Normal production analysis, reprocessing, regeneration, backfill, Monitoring UI
  canonical-value lists, and the planned LLM taxonomy prompt all consume the same
  database-derived snapshot for the selected revision.

### Failure behavior

- Initial startup must successfully bootstrap and load a complete database snapshot
  before consuming articles. If it cannot, startup fails with an actionable error rather
  than analyzing with an unverified code-only taxonomy.
- After at least one valid database snapshot has been loaded, a transient database error
  retains the last valid immutable snapshot, preserving the existing failure-safe runtime
  behavior.
- Offline unit tests may construct a snapshot from the predefined manifest explicitly;
  this is a test/default fixture and must not become an alternate production authority.

### Alias representation

- Represent ordinary aliases as `status='mapped_alias'` rows with
  `alias_for_value=<canonical value>`.
- Extend the stored/loaded metadata contract for predefined aliases that also imply a
  subtype. A suitable representation is an explicit `implied_subtype` property in
  `family_rules`, provided it is validated and converted into
  `EventTaxonomySnapshot.family_alias_subtypes`.
- Normalize alias tokens consistently with `normalize_token()`. Preserve compatibility
  with existing persisted raw responses containing spaces, such as `military action` and
  `retail event`.

## Data Repair and Deployment

1. Deploy the schema/manifest/bootstrap changes before switching the provider to
   database-only snapshot construction.
2. During startup, insert the missing predefined revision-1 rows and aliases in one
   transaction and validate the complete registry.
3. Load the current revision from PostgreSQL and compare the resulting snapshot with the
   pre-change runtime snapshot. Existing active behavior must be unchanged except where
   a committed taxonomy decision already intended a difference.
4. Enable database-authoritative snapshot construction only after the comparison passes.
5. Verify on Haas that revision remains 3, the predefined active canonical counts are
   `50/37/11/13/18`, all aliases resolve correctly, and no predefined rows are missing.
6. Verify no thesis cards, evidence windows, analyses, signals, gap resolutions, or
   decision audit rows were rewritten by the metadata repair.

The production repair must use normal deployment/bootstrap. Do not apply an untracked
manual SQL patch to Haas.

## Acceptance Criteria

- One versioned manifest defines every predefined canonical value, subtype family scope,
  alias, and implied subtype.
- Clean bootstrap creates all 129 predefined canonical rows plus all predefined alias
  rows in PostgreSQL.
- Upgrading an existing database inserts all missing seed rows without incrementing the
  taxonomy revision or changing operator decision history.
- Haas contains all 37 predefined subtype rows after deployment; the 18 currently missing
  values are present with correct family scopes.
- A database-loaded runtime snapshot is constructed without merging a code baseline.
- Explicit historical revision loading returns exactly the rows effective at that
  revision.
- A later deprecation of a predefined value removes it from the current runtime snapshot
  while leaving earlier snapshots unchanged.
- Monitoring UI and runtime normalization expose the same canonical values and aliases
  for the same revision and family scope.
- Ordinary and implied-subtype aliases resolve from database data alone.
- Initial startup fails safely on an absent, incomplete, or internally inconsistent seed;
  transient refresh failure after a valid load retains the last valid snapshot.
- The repair does not rewrite historical analyses, windows, cards, signals, gaps, or
  taxonomy decisions.
- Relevant ThesisBuilder data-model and behavior documentation is updated to state that
  PostgreSQL is authoritative after seed bootstrap.

## Test Plan

1. Unit-test manifest uniqueness, normalized token validity, canonical counts, subtype
   family scopes, alias targets, and implied subtype compatibility.
2. Bootstrap an empty integration database and assert all 129 predefined canonical rows
   and every predefined alias are present with revision-1 effective metadata.
3. Bootstrap twice and assert byte-equivalent taxonomy rows and unchanged revision.
4. Simulate the current Haas state with the 18 subtype rows absent, rerun bootstrap, and
   assert that only the missing seed metadata is inserted.
5. Seed an incompatible collision and assert bootstrap fails without partially inserting
   rows or advancing revision.
6. Replace the current stage-only Monitoring UI registry test with a parameterized check
   of every dimension and every subtype family scope.
7. Build a snapshot from database rows only and compare its canonical values, aliases,
   subtype families, and implied-subtype mappings with the manifest-derived v1 fixture.
8. Add a dynamic canonical value and mapped alias at revision 2 and verify revision 1 does
   not contain them while revision 2 does.
9. Deprecate one predefined value at revision 3 and verify it remains in revisions 1 and
   2 but is absent from revision 3 without being reintroduced by a baseline merge.
10. Test initial-load database failure versus refresh failure after a valid snapshot:
    initial load must fail, while refresh must retain the last valid snapshot.
11. Exercise normalization for every predefined alias, including family aliases that
    imply `military_action`, `military_conflict`, `sanctions`, and `other_sales_event`.
12. Run the full non-integration and integration suites, then perform the bounded Haas
    count/scope comparison after deployment.

## Dependencies and Scope

- Builds on the revisioned taxonomy registry from `260729-01` and operator decision
  workflow from `260729-02` through `260729-04`.
- Supports `260817-01`, whose LLM integration tests require the prompt and normalizer to
  consume exactly the same active taxonomy snapshot.
- This issue does not change the semantic membership of taxonomy v1, accept open gap
  proposals, or authorize manual production data mutation.
